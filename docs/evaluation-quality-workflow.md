# 평가를 검증하고 수정하는 공통 절차

## 목적과 적용 범위

사용자는 평가를 믿을 수 있게 만든 뒤 새로운 종류의 문제도 스스로 검증하고 문제점을 수정할 수 있는 흐름을 요청했다. 자동 점수 확정보다 근거 확인을 우선하고,1회 재검토 후 해결되지 않으면 점수를 보류한다. 이 문서는 문제 유형을 추가할 때 재사용할 개발 절차다. 현재 Discord의 신규 주제 출제 기능 자체를 추가한 것은 아니다.

## 문제 유형을 추가할 때

1. 문제의 업무 목표, 대상·기간·시간대, 지표 단위와 분자/분모, 결과로 판단할 수 없는 범위를 공개한다. 평가 중에 새로운 필수 기준을 만들지 않는다.
2. 공개 루브릭과 오류 담당 항목을 고정한다. 같은 계산 오류는 근거 해석 한 항목에만 배정한다. 누락·핵심 오류의 공개 기준은 required/core_error ID로 연결한다.
3. SQL을 실제 실행해 전체 결과와 조건·데이터 버전을 저장한다. 생성기에서 기대값을 독립적으로 계산해 검증한다. 모델이 만든 답이나 높은 평가 점수를 데이터 검증 근거로 사용하지 않는다.
4. 공개 arithmetic_contract에 합계/비율 검산 정의를 등록한다. 지원하는 정의가 없으면 미검산으로 남기고, 계약 형식이 잘못되면 문제 자체를 보류한다. 필터·기간·단위가 정확히 일치하는 선택 근거만 계산한다.
5. 고정 표본6종을 준비한다: 정상 보고, 계산 오류, 타당한 대안 경로, 합리적 판단 보류, 실행 근거 부족, API 실패. 표본별 기대 등급 범위를 모델 호출 전에 고정한다. 평가 모델에는 기대 등급·합격 점수를 보내지 않는다.
6. 같은 표본을3회씩 검사한다. 현재 자동 기준은 정상/대안/보류의 허위 오류 없음, 계산 오류 상한 반영, 모든 감점 계약 통과, 시스템 실패의 총점null, 점수 범위5점 이하, 누락/보류0건(의도한 시스템 실패 제외)이다.5점은 초기 운영 기준이며 통계적 신뢰도나 사람 품질 승인을 뜻하지 않는다.
7. 실패를 형식·중복·인용·검산 계약·의미 판정·API 문제로 나눈다. 형식/중복/인용은 평가당 최대1회 보완하고 재검사한다. 관련 없는 항목의 등급은 유지한다. API 실패는 평가 내에서 자동 반복하지 않는다.
8. 실패 원인에 따라 입력·공개 기준·검산기를 수정하고 같은 표본을 다시 실행한다. 실패 표본·원래 응답·수정 이력을 보존한다. 점수를 높이기 위해 표본의 기대 범위를 사후에 넓히지 않는다. 실제 기준 변경이면 새 버전과 변경 이유를 기록하고 전체 표본을 재검사한다.
9. quality_gate로 개별 결과를 다시 계산한다. 미완료, 변경된 표본/모델/코드, 저장된 pass 문자열만 있는 결과는 제공 조건을 충족하지 못한다. 통과는 등록된 표본의 자동 검사 범위이며 사람 검토는 별도pending이다.

## 감점 응답 계약

등급0~2에는 deductions 배열을 제공한다. 각 항목은 issue_id, kind, check_id, claim, evidence_refs, reason을 포함한다. claim은 현재 보고/후속 답변에서 인용한다. 없는 필수 조건의 누락만 빈 인용을 허용한다. 같은 오류 ID 또는 같은 종류·인용을 여러 항목에 배정하면 재검토한다. 다른 종류로 위장한 구성 계산 오류는 확인된 검산과 서술을 연결해 의심 사례로 재검토한다. 모든 표현의 의미적 동등성을 결정적으로 판별할 수 있다는 뜻은 아니다.

필수/상위 조건을 충족한 등급3~4에 결함이 없으면 결함을 만들어내지 않는다. 개선 문구가 없을 때는 공개 기준에서 출처를 표시한 다음 연습 안내를 제공한다. 감점은 실제 독립된 결함이 있어야 한다.

## 등록 지표 예시: 매출 합계

```json
{
  "version": "declared-metrics-v1",
  "metrics": [{
    "id": "revenue-week1",
    "label": "1주차 총매출",
    "operation": "sum",
    "unit": "원",
    "value_column": "revenue",
    "group_column": "channel",
    "conditions": {
      "metric": "revenue", "start": "2026-09-01", "end": "2026-09-08",
      "timezone": "UTC", "unit": "payment", "filters": {}, "group_by": "channel"
    }
  }]
}
```

문제의 공개 task.arithmetic_contract에 등록한다. 보고의 ‘1주차 총매출500원’ 같은 명확한 라벨·값·단위 주장을 확인한다. sum은 금액 컬럼 합계, ratio는 고유 사용자 분자 합/분모 합×100으로 계산한다. ratio에는 numerator_column·denominator_column과 단위%가 필요하다. group_value를 지정하면 해당 단일 그룹만 확인한다. 임의의 SQL·수식 코드·정규식을 실행하지 않는다. 다른 정의·기준·분해·모호한 문장은 미검산이다.

## 실행 도구

- prepare_evaluation_quality_samples.py: 현재 튜토리얼의 저장된 실제 조회 근거에서6종 표본을 준비한다. 새로운 분야는 같은 fixtures JSON 구조로 독립적으로 검증된 자료와 표본을 작성한다.
- verify_evaluation_quality.py: 명시한 표본으로 반복 평가하고 JSON을 매회 저장한다. 기본3회, 평가당 최대1회 수정, 최대30호출이다. 연속 외부 API 문제3회이면 검사 미완료로 종료한다. only/repeats1 같은 예비 검사는 전체 품질 통과가 아니다.
- replay_evaluation_quality.py: 저장 원시 응답을 최신 파서·검산·감점 검사로 재확인한다. 새 모델 호출을 하지 않으며 recorded_revalidation으로 표시해 새 반복 검사나 활성 프로필 승인으로 사용하지 않는다. 원래 코드 해시와 현재 코드 해시를 함께 보존한다.
- evaluation_quality.quality_gate: fixtures 지문, 모델, 코드 해시, 개별 결과와 고정 기대 범위를 확인한다. 미래 출제 경로에서 공개 전에 호출해 held인 문제는 초안으로 유지한다.

## 점수 제공과 프로필 등록

현재 DiscordTrainingService의 /submit에 QualityRegistry를 연결했다. 사용자가 선택한 정책대로 개별 감점 계약이 통과해도 유형 프로필이 없거나 반복 검증이 실패하면 총점은null이며 분석 피드백만 제공한다. 후보 점수는 운영 검증용 진단 자료로 보존한다. 같은 보고의 보류 재시도는 유형이 계속 보류이면 추가 모델 호출 없이 기존 피드백을 사용하고, 유형이 통과하면 새 평가를 저장한다. 기존 평가 이력은 변경하지 않는다.

프로필은 task_id·공개 과제/루브릭·난이도·도움 정책·데이터 버전·스키마·지표/기간·검산 계약으로 고정한다. 다른 문제 정의나 데이터 버전에 임의 재사용하지 않는다. 평가 모델이나 관련 코드가 변경돼도 재검증이 필요하다. 실패 검사는 아카이브하고, 모든 검사에 통과한 경우에만 활성 profile.json을 원자적으로 저장한다. 개별 점수·검산·감점 근거를 다시 계산하므로 저장된 pass 요약만으로 등록할 수 없다.

반복 검사 실행 환경에 이미 설치된 Python·Discord 의존성, PYTHONPATH=src, 지정한 모델 키 파일과 DISCORD_MODEL이 필요하다. 예시 명령:

```text
python scripts/verification/verify_evaluation_quality.py fixtures.json run.json --repeats 3 --max-calls 30 --interval 16 --register .local/evaluation-quality
```

등록 경로는 봇의 DISCORD_QUALITY_PROFILES_DIR와 일치시킨다. 기본값은 .local/evaluation-quality이며 compose.discord.yaml의 discord-quality 볼륨에 보존한다. 검증 명령은 Discord에 전송하지 않는다. 전체3회씩을 완료해도 자동 기준이 실패하면 활성 프로필을 만들지 않는다. expected_grades와 원본 결과는 검증용 자료로 보관하고 학습자 프롬프트에 넣지 않는다.

시스템 실패 표본은 의도한 공급자 장애를 주입하여 보류 동작을 확인하는 표본이다. 실제 외부 API 장애의 모든 패턴을 관측했다는 뜻은 아니다. 실제 모델의 API 오류가 다른 표본에서 발생하면 그 반복 검사는 실패로 남긴다. API 오류를 점수0으로 계산하거나 성공 결과만 선택해 승인하지 않는다.

## 수정 보고 피드백

같은 정책·선택 실행 근거에서 재검산한 경우만 해결·지속·새 오류를 비교한다. 오류 주장 삭제·모호한 표현으로 변경은 미확인이다. 다른 실행 근거·데이터·정책이면 직접 비교를 보류한다. 점수 상승과 오류 감소를 취업 역량 향상이나 학습 효과의 입증으로 표시하지 않는다.

## 사람이 필요한 판단

새 업무 목표에 맞는 공개 기준, 독립 표본의 정답 범위, 지원 밖 인과 설명과 타당한 다른 분해는 사람이 검토한다. 자동 검증 결과가 반복해서 의미적으로 어긋나면 문제·기준을 검토해야 하며 자동으로 합격 범위를 바꾸지 않는다.

게임 데이터 분석가 취업 준비에 도움이 되는지 검토할 때는 다음을 표본별로 확인한다.

| 확인할 내용 | 검토 근거 |
| --- | --- |
| 업무 질문을 이해할 수 있는가 | 공개된 목표·대상·기간·의사결정이 보고서 요구와 연결되는지 |
| 공개 데이터로 풀 수 있는가 | 요구 지표의 분자/분모·관측 기간·비교 그룹을 실제 SQL로 재현할 수 있는지 |
| 난이도와 사고 과정이 맞는가 | 초급의 정의/계산, 중급의 비교/불확실성, 고급의 대안/교란 검토가 필수 자료 누락 없이 가능한지 |
| 타당한 다른 풀이가 인정되는가 | SQL 문장 일치나 문장 길이가 아니라 같은 정의·근거와 설명 범위로 판정하는지 |
| 잘못된 분석을 고칠 수 있는가 | 피드백이 실제 인용·조회 근거·계산과 다음 수정 행동을 연결하고 고친 주장에 옛 오류를 재감점하지 않는지 |
| 평가를 믿을 근거가 있는가 | 자동 반복 결과·사람 검토·검산 지원 범위와 미확인을 구분하고 중복 감점/공급자 장애를 학습자 점수로 확정하지 않는지 |

이 검토는 자동 통과 표본만 읽는 데서 끝내지 않는다. 오류·대안·근거 부족 표본의 원래 판정과 재검토 결과도 함께 확인하고, 판단 근거와 검토자의 결론을 기록한다. 취업 효용이나 학습 효과는 실제 참가자의 수정 행동·다른 과제 적용을 확인하기 전에는 확정하지 않는다.
