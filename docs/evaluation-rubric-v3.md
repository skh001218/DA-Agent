## 평가 범위와 고정 조건

평가는 정답 SQL이나 생성된 실제 원인을 맞히는 능력보다, 업무 질문을 정의하고 자료를 연결해 검증하며 근거가 허용하는 결론을 내리는 능력을 측정한다. 과제에 공개하지 않은 테이블·추가 분석·비공개 원인·기준 SQL의 작성 순서를 요구하지 않는다. 현재 테이블 생성 한도는 변경하지 않는다.

출제 전에 적용 항목·배점·각 항목의 필수 조건·핵심 오류·인정할 한계·4등급 인정 조건을 고정하고 학습자가 이해할 수 있는 기준을 공개한다. 비공개 기준 SQL·정답 값·사건·생성 seed는 별도로 보관한다. 기존 과제의 고정 조건·배점·저장 점수를 덮어쓰지 않는다. 향후 코드 연결 시 새 평가 계약 버전을 사용하며 재평가는 별도 기록으로 남긴다.

대표 계산 과제의 배점은 문제 정의25·분석 접근25·SQL 정확성20·결과 해석20·다음 행동10을 유지한다. 다른 과제는 기존에 고정된 배점을 사용한다. 분석 설계 과제는 SQL 정확성을 미적용으로 고정하고, 출제 시 적용 항목의 배점 합을100으로 정한다. 평가 도중 배점을 재분배하지 않는다.

## 공통 등급 결정 순서

먼저 확인 가능한 판단과 확인 불가를 구분한다. 확인 불가인 필수 조건이 있으면 그 항목의 확정 등급을 보류한다. 확인된 핵심 오류는 확인 불가와 구분해서 표시한다. 모든 필수 조건을 판정할 수 있는 항목은 아래 순서로 첫 번째 해당 규칙을 적용한다.

| 순서 | 등급 | 판정 조건 |
| --- | --- | --- |
| 1 | 0 | 해당 항목의 판단·방법·계획 등 평가할 내용이 제출 어디에도 없음. 해당 항목에서 필수인 실행 근거 자체를 제출하지 않은 경우도 포함 |
| 2 | 1 | 그 항목의 공개 필수 조건에 대한 핵심 오류가 실제 문장·SQL·결과에서 확인됨. 다른 일부 조건을 잘 썼더라도 같은 항목의 핵심 오류가 우선 |
| 3 | 2 | 해당 항목에 타당한 내용이 있고 확인된 핵심 오류는 없지만, 공개 필수 조건 중 하나 이상을 누락 |
| 4 | 4 | 공개 필수 조건을 모두 충족하고, 출제 전에 명시한 해당 항목의 한계 설명·추가 검증 조건도 충족 |
| 5 | 3 | 공개 필수 조건을 모두 충족하지만 4등급 인정 조건은 충족하지 않음 |

내용을 단순히 길게 썼거나 전문 용어를 많이 사용했다는 이유로 등급을 올리지 않는다. 같은 사실 상태를 유지한 채 설명 문체만 바꿔도 등급은 유지한다. 핵심 오류의 심각성은 평가마다 새로 추정하지 않고 과제별 오류 목록에 연결한다.

| 항목 | 필수 조건 후보 | 0등급 | 1등급: 핵심 오류 | 2등급: 중요한 누락 | 3등급 | 4등급 인정 조건 후보 |
| --- | --- | --- | --- | --- | --- | --- |
| 문제 정의 | 대상, 기간·시간 기준, 집계 단위, 지표·분모, 관측 가능 조건; 비교 과제의 비교 집단·기준 | 결과를 확인했다는 주장만 있고 정의가 없음 | 세션 행을 고유 유저로 정의, 잘못된 분모·기간·비교 대상, 관측 불가능 대상 포함을 올바른 정의로 명시 | 타당한 정의 일부는 있으나 필수 기간·단위·분모·관측 조건 등 누락 | 선택된 필수 조건을 올바르게 정의 | 경계 시점·관측 제외·중복 등 관련 경계 사례의 처리까지 명시 |

| SQL 정확성 | 선택 저장한 실제 실행, 실행 성공·결과 완전성, 정의한 대상·기간·단위·지표·관측 조건 계산 | 실행 필수 과제인데 선택 저장한 실행 근거 없음; 계획 SQL만 제출 | 실행 근거에서 잘못된 집계 단위·분모·기간·JOIN 중복·계산 또는 실행 오류가 확인됨 | 실제 실행은 있고 확인 가능한 부분은 맞지만 필수 계산·출력 일부를 작성하지 않음 | 실제 결과가 고정된 계산 조건을 모두 충족 | 실제 저장 근거로 중복·경계·독립 검산 등 명시된 검증까지 확인 |
| 결과 해석 | 결론과 실제 근거 연결, 비교·차이의 의미, 관측 가능한 판단 범위 | 결과·설계의 의미를 설명하지 않음 | 근거와 반대인 결론, 실행하지 않은 결과를 확인했다고 주장, 관측 차이만으로 원인이 증명됐다고 단정 | 타당한 해석은 있으나 필수 비교·근거 연결·판단 범위 등 누락 | 근거가 허용하는 결론을 제시하고 과장하지 않음 | 관련 대안 설명·불확실성·관측 한계가 결론의 적용 범위와 연결됨 |
| 다음 행동 | 남은 질문·한계 또는 업무 결정과 연결, 구체적인 확인 대상·방법·목적; 충분한 경우 정리·제출 | 다음 행동·완료 판단이 없음 | 틀린 전제로 조치를 확정, 검증 없이 인과적 개입 효과를 보장, 가설에 맞게 자료를 수정하도록 제안 | 관련 방향은 있으나 무엇을 어떻게 확인할지 빠짐 | 실제 남은 문제에 대응하는 행동 또는 근거가 충분하다는 정리·제출 판단이 구체적 | 행동의 우선순위와 결과에 따른 다음 결정·종료 조건까지 명시 |

해당 과제에서 관측 자료만으로 원인을 확인할 수 없다면 이를 인정하고 대안 검증 방법을 제시한 것은 올바른 분석이다. 비공개 실제 원인을 맞히지 못했다는 이유로 감점하지 않는다. 목표에 필요한 자료 연결을 평가하되 JOIN 개수나 테이블 개수 자체를 점수로 사용하지 않는다.

## 계획과 실행을 분리하는 규칙

분석 접근은 제출에 실제로 적힌 방법·계획을 평가하고 SQL 정확성은 실행된 결과를 평가한다. 명시된 계획이 올바른데 SQL 구현이 잘못됐다면, SQL 오류만으로 분석 접근을 감점하지 않는다. 계획 자체에도 잘못된 단위·관계·검증 방법이 적혀 있으면 해당 계획을 근거로 분석 접근을 감점한다.

문제 정의도 작성한 정의를 평가한다. SQL이 정의를 구현하지 못한 것과 정의 자체가 틀린 것을 구분한다. 동일한 오류가 여러 항목에 영향을 준 경우 각 항목에서 오류가 나타난 구체적인 위치와 위반 조건을 각각 기록한다. 다른 항목의 낮은 등급만을 근거로 감점하지 않는다.

다음 행동은 앞 항목의 점수와 독립적으로 평가한다. 틀린 SQL을 발견하고 단위·기간·관측 조건을 바로잡는 구체적인 계획은 다음 행동의 타당한 근거다. 단지 '다시 분석한다'는 문장은 구체적인 행동을 충족하지 않는다.

## 서로 모순되는 주장 처리

평가 항목에 대응하는 제출 내용과 최종 주장·결론을 함께 읽는다. 최종 판단이 중간 설명과 충돌하면 최종 판단을 우선한다. '인과를 확정할 수 없다'고 한계에 써도 최종 결론에서 '원인이 증명됐다'고 단정하면 결과 해석의 핵심 오류로 판정한다.

같은 항목에서 서로 반대인 최종 주장을 철회·수정 없이 함께 유지하면 모순이 해결되지 않은 핵심 오류다. 명시적으로 철회하거나 수정한 이전 주장은 현재 결론으로 취급하지 않는다. 제출된 현재 보고서 버전을 평가하며 이전 보고서의 주장을 섞지 않는다.

최종 수치가 맞아도 근거 없는 원인 단정은 결과 해석에서 감점한다. 반대로 SQL이 틀렸더라도 그 오류를 정확히 인정하고 결론을 보류한 해석은 그 해석 자체를 평가한다.

## 누락·오류·확인 불가·미적용 구분

| 상태 | 의미 | 처리 |
| --- | --- | --- |
| 충족 | 제출 자료·실행 근거로 조건 충족을 확인 | 해당 조건 충족으로 계산 |
| 누락 | 요구한 정의·설명·실행 등을 제출하지 않음 | 평가할 내용이 전혀 없으면0, 일부 타당한 내용이 있으면2. 존재한다고 추정하지 않음 |
| 오류 | 제출한 내용이 고정 조건을 위반함을 확인 | 해당 항목의 핵심 오류 목록에 해당하면1. 위반 문장·SQL·결과를 연결 |
| 확인 불가 | 자료는 있지만 결과 잘림·만료·검증 계약 부재·시스템 장애 등으로 맞고 틀림을 확정할 수 없음 | 오답·누락으로 바꾸지 않음. 영향받은 조건·항목은 보류하고 필요한 확인을 제시 |
| 미적용 | 출제 전에 과제 범위에서 제외한 조건·항목 | 등급·감점 대상에서 제외. 평가 중 임의 변경 금지 |

SQL 실행은 성공했지만 결과가 잘린 경우, 보이는 행은 설명할 수 있어도 전체 비율의 정확성을 확정하지 않는다. 다른 타당한 SQL·정의의 검증 계약이 없으면 기준 SQL과 다르다는 이유로 틀렸다고 판정하지 않는다. 시스템 장애 때문에 근거를 읽지 못한 경우 학습자 오류로 기록하지 않는다. 해설 사용·힌트 사용 자체는 감점하지 않는다.

항목 보류가 있으면 최종 총점을 확정하지 않는다. 확정 가능한 항목별 점수·확인된 배점 범위와 보류 사유를 표시한다. 보류를0점으로 치환하거나 나머지 배점을100으로 환산하지 않는다. 모든 적용 항목이 확정된 경우에만 `sum(weight × level / 4)`를 소수 첫째 자리로 반올림해 총점을 계산한다.

## AI 판별과 서버 계산의 역할

AI는 각 조건의 충족/누락/오류/확인 불가와 이유를 판별하고, 제공된 현재 제출의 필드·주장·저장 실행 출처 경로를 선택한다. 등급·배점·총점은 생성하지 않는다. 서버가 해당 출처의 실제 원문을 발췌해 붙이며 AI에게 원문 재작성을 맡기지 않는다. 발췌는 최대2000자로 표시하고 잘림 여부를 기록한다. 근거 검산은 원본 전체 결과를 사용한다. 존재하지 않거나 빈 출처, 충족/오류의 근거 누락은 차단한다. 서버가 직접 계산하는 SQL 조건과 오류 없음 판정은 출처 필수 규칙의 예외다.

서버는 출제 시 고정된 조건 ID·허용 상태·근거 참조를 검증한다. 실제 실행 완전성·계산 검증 결과와 충돌하는 AI 판단은 확정하지 않는다. 조건 상태를 위 결정 순서에 따라 등급으로 변환하고 고정 배점으로 점수를 계산한다. 판별과 총점 산출을 위해 별도 AI 호출을 늘리지 않고 한 평가 응답을 사용한다.

같은 조건 상태가 입력되면 서버는 항상 같은 등급·점수를 반환해야 한다. AI의 조건 상태 판별 편차까지 자동으로 사라지는 것은 아니므로 실제 표본과 사람 판정이 필요하다. 같은 요청의 중복은 기존 결과를 재사용하고, 새 평가 요청의 결과는 별도 기록으로 보존한다. 평균 점수로 실패 회차를 숨기지 않는다.

## 구현·검증 완료 조건

새 과제는 request-review-v3로 조건 판별·보류·서버 등급 변환을 사용한다. 기존에 출제된 request-review-v2 과제와 저장 리뷰는 소급 변경하지 않는다. 실제 실행 중인8087 화면은 별도 작업에서 수정 중이므로 덮어쓰지 않았으며, 현재 소스는 별도8088 환경에서 검증했다. 최종 화면 브랜치와 통합·배포할 때 v3 보류/미적용 표시를 함께 반영해야 한다.

1. 새 계약에 조건 목록·오류 목록·4등급 조건·버전을 출제 전에 고정하고, 기존 패키지·평가 읽기를 유지한다.
2. 조건별 판별 응답·근거 검증·서버 등급 계산·항목 보류와 총점 미확정을 구현한다.
3. 위 경계 사례에 대해 예상 상태·등급을 사전에 고정하고, 상태가 같으면 점수가 같음을 자동 확인한다.
4. 실제 대표 표본과 기존 core_error 표본을 동일 입력으로3회 평가한다. 항목별 상태·등급 변화와 총점 범위를 함께 기록한다. 기존 max-min10점 기준을 유지하고 핵심 오류 등급 변화는 총점 범위 이내라도 조사한다.
5. 실제 화면에서 확정·보류·미적용·실패·저장·새로고침을 확인한다. 사람은 계획/실행 구분, 대안 인정, 최종 모순, 불필요한 추가 요구, 비공개 노출을 검토한다.

기준 문서 작성이나 단일 모델 응답 성공만으로 점수 편차 개선·구현 완료·사람 승인을 선언하지 않는다.

## 구현 연결

- `evaluation_v3.py`: 공개 조건 선택, 응답 스키마, 출처 원문 연결, 결정 규칙, 확정/보류 점수.
- `task_planner.py`·`adaptive_tasks.py`·`evaluation.py`: 출제 시 공개 조건과 불변 해시 고정. 접속과 요청별 합성 과제에 적용.
- `reviews.py`·`api_provider.py`: 같은 평가 호출에서 조건 응답을 요청·검증. Gemini에는 구조/허용 값 스키마를 전달하고 길이·개수 제한은 서버에서 확인한다. 평가만 출력 토큰 상한8192, 자동 재시도0·호출 수·테이블 한도는 유지.
- `app.js`·`quality.js`: 총점 보류, 확정 배점, 설계 SQL 미적용 표시. `learning_state.py`의 기존 점수 없는 항목 제외 규칙으로 보류를0점 역량 관측으로 만들지 않는다.
- [응답 예시](../template/evaluation-response-v3.json): 실행 근거 없는 제출의 조건별 누락 예시. 실제 조건 목록은 과제별 고정 계약을 따른다.

## 항목별 입력과 조건 일관성 보완

최신 구현은 condition-review-v3-scoped-inputs이며 [후속 검증](../tests/reports/verification-v3-failure-fixes-2026-10-05.md)을 따른다. 항목별 우선 입력과 다른 칸의 보조 내용, 자유 서술을 함께 인정한다. 정의·계획·다음 행동의 판단에 SQL 원문/실행 검산을 감점 출처로 사용할 수 없다. 해석에는 최종 주장과 실제 결과를 연결한다.

정의의 공개 필수 요소가 모두missing이면 내용 존재 여부와 무관하게 실제 정의가 없으므로 content도missing으로 맞춘다. 일부 필수 정의를 제시한 경우에는2등급을 유지한다. 이 정규화는 의미적 오답을 정답으로 바꾸거나 기존 저장 리뷰를 수정하는 규칙이 아니다. 같은 서술에서 내용 존재met/missing만 변한 점수 편차를 막는다.

현재 보고서에서 명시 철회한 주장은 감점하지 않으며, 내용 없음·틀린 내용·검증 불가를 구분한다. 보류 총점에서도 항목 등급 변화가 있으면 반복 품질 검사에 실패로 표시한다. 실제 모델18회의 최신 서버 재계산 및 보완 경계6회에서 기대 등급 일치를 확인했지만, 전 유형·서술·사람 의미적 품질은 검증 대기다.
