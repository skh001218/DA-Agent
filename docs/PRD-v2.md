# Game Data Analyst Trainer 요청 기반 분석 훈련 PRD

- 작성일: 2026-10-04 / 마지막 갱신일: 2026-10-05 (Asia/Seoul)
- 버전: 2.3
- 상태: 요청 기반 첫 사용 구간 구현, 신규 전체 범위 진행 중
- 기존 구현 확인 기준: `7cecdd7`, Spec 001~005와 기존 검증 기록
- 이전 문서: [1차 PRD](./PRD-v1.md)

사용자가 게임 데이터 분석 문제를 요청하면 에이전트가 원하는 난이도와 학습 목표에 맞는 과제와 데이터를 준비하고, 사용자의 풀이에 따라 질문·힌트·추가 분석·평가를 제공하는 훈련 도구를 만든다. 사용자는 분석 방향과 결론을 결정하고, 에이전트는 데이터로 확인 가능한 상황과 피드백을 제공한다. 난이도는 문제의 모호함을 주된 기준으로 삼으며, 운영 로그와 사람·학습자 판정으로 제품 품질 지표를 수집한다.

이 문서는 기존의 고정 문제 중심 개발 계획을 대체한다. 문제 2·3은 별도 기능으로 착수하지 않으며, MVP 구현 진행도 80% 이후 두 문제를 추가한다는 기준도 폐기한다. 튜토리얼·리텐션은 향후 출제 가능한 주제의 예시로만 남긴다. 문제 번호나 고정 목록이 제품의 개발 단위가 되지 않는다.

## 1 사용자 판단과 제품 목적

사용자는 문제 형식이 고정되면 같은 형식만 반복해서 풀 가능성이 크고 에이전트가 수동적으로 작동한다고 판단했다. 이에 따라 자연어 요청, 다양한 분석 과제, 풀이에 따른 상호작용을 핵심 기능으로 삼는다. 사용자 판단의 원문과 근거는 [판단 기록](../나의판단과근거.md)에 보존한다.

제품은 SQL 정답 암기를 넘어 업무 요청 해석, 지표 정의, 분석 설계, 실제 계산, 대안 설명 검토와 근거 있는 결론을 연습하게 한다. 문제의 문장이나 숫자만 바꾸는 것은 다양성 충족으로 인정하지 않는다.

대상은 기본 SQL을 사용할 수 있는 게임 데이터 분석 학습자다. 사용자가 밝힌 수준을 우선하고 풀이에서 드러난 이해 수준은 도움과 다음 과제를 제안하는 근거로 사용한다. 평가 점수는 학습 안내이며 채용 역량 인증이 아니다.

### 남은 검증의 담당과 필요한 협조

`검증 대기`는 완료 조건을 아직 확인하지 못했다는 상태이며, 모든 검증을 사용자에게 맡긴다는 뜻이 아니다. 에이전트가 수행할 수 있는 구현 보완·자동 검사·실제 화면 검증은 에이전트가 계속 담당한다. 아래 담당 구분을 추가한 것은 검증 수행이나 승인에 해당하지 않으므로 구현 진행도 5/11은 유지한다.

| 구분 | 남은 항목 | 담당과 필요한 협조 | 완료 증거 |
| --- | --- | --- | --- |
| 에이전트가 수행 | 남은 유형별 화면·장애·수정/재개 흐름, 추천 변경에서 실제 출제까지 연결, 반복 평가 편차 개선·재검증 | 에이전트가 코드와 검증 도구를 보완하고 실행한다. 확인 가능한 항목을 사용자에게 넘기지 않는다 | 실행 환경·버전·표본·성공/실패·화면 결과와 회귀 기록 |
| 사람의 의미적 판단 | 과제 간 사고의 차이, 모호함·난이도 적합성, 코칭·평가의 오진/미탐·대안 인정·비공개 노출, 신규 생성 규칙 승인 | 사용자 또는 별도 검토자가 실제 표본을 읽고 판단한다. 에이전트가 표본·비교 결과와 판정 기록 수단을 준비한다 | 검토자·표본 ID·규칙 버전·이유·판정·시각. 자동 판정을 사람 승인으로 대신하지 않는다 |
| 환경 준비와 실행 | 다른 PC·ARM에서 요청·SQL·리뷰·재개 | 사용자가 별도 장비나 접근 가능한 환경을 준비하고, 에이전트가 재현 절차·가능한 실행·결과 정리를 담당한다 | 장비·아키텍처·설치/실행 버전·핵심 흐름 결과와 제한 |
| 실제 참가자 관찰 | 학습자 5명 파일럿과 학습 효과 확인 | 사용자가 참가자를 모집하거나 참여를 조율하고, 에이전트가 관찰 양식·지표 집계·분석을 준비한다 | 실제 참가자별 완료·수정 행동·개선 관측 및 목표 달성 여부 |

현재 반복 평가의 핵심 오류 표본은 점수 편차 12.5로 기준 10을 초과한다. 이는 에이전트의 개선·재검증 대상이다. 네 생성 규칙의 세 수준 표본 총 12개는 실제 DB 검증을 마쳤으며, 의미적 검토와 승인은 사람의 판단을 기다린다. 장비·참가자 협조가 필요한 검증은 준비되지 않은 이유를 기록하고, 에이전트가 독립적으로 진행할 수 있는 다른 검증은 계속 수행한다.

## 3 범위와 지원 한계

로컬 단일 학습자 웹 환경, HTML·CSS·JavaScript, Python·FastAPI, Psycopg 3, 분리된 PostgreSQL 학습·기록 DB와 Docker Compose를 유지한다. 현재 AI 제공자는 Gemini이며 자동 제공자 전환은 하지 않는다. 기존 ChatGPT 로그인 경로의 접근 거부는 별도로 추적하고 새 핵심 흐름의 필수 경로로 두지 않는다.

핵심 범위는 자연어 요청, 맞춤 출제, 검증된 데이터 준비, 난이도 조절, 실제 SQL 분석, 능동적인 코칭, 근거 중심 평가, 기록·재개, 다음 훈련 제안이다. 공개 서비스·다중 사용자·결제·디스코드 봇·외부 데이터 API 연동은 이후 범위다.

문제 형식과 출제 내용은 유연하게 구성하지만 지원하지 않는 데이터 분야까지 즉시 출제할 수 있다고 약속하지 않는다. 지원 가능한 분야는 데이터 생성·검증 기능에 의해 결정되고 화면과 응답에 표시한다. 요청을 처리할 수 없으면 이유와 지원 가능한 대안을 제안하고 조용히 다른 주제로 바꾸지 않는다.

초기 구현은 기존 접속 데이터에서 여러 사고 과제를 제공하는 것으로 제안한다. 이탈률 계산 외에도 지표 정의 검토, 잘못된 분석 수정, 관측 조건 비교 등을 제공할 수 있다. 매출·전투·경제·튜토리얼 등은 필요한 생성·검증 기능을 갖추면서 확장한다. 모든 로그를 처음부터 구축하거나 특정 문제 번호를 구현하는 계획은 두지 않는다. 초기 지원 분야의 최종 범위는 관련 Spec 작성 시 확정한다.

## 4 사용자 흐름

1. 사용자가 “게임 데이터 분석 문제 내줘. JOIN까지 할 수 있고 중급 리텐션 분석을 연습하고 싶어”처럼 요청한다.
2. 에이전트가 주제·수준·목표를 해석한다. 출제에 꼭 필요한 정보가 부족하면 짧게 묻고, 합리적으로 정할 수 있는 조건은 안내한다.
3. 에이전트가 과제 목표·필요 데이터·난이도·완료 조건을 설계하고 데이터를 준비·검증한다. 화면에 진행 상태와 실패 원인을 표시한다.
4. 검증된 과제의 업무 상황, 데이터 사전, 공개 조건과 제출 기대 수준을 제공한다. 비공개 생성 사건과 평가 기준 원문은 숨긴다.
5. 사용자가 질문하고 지표·가설을 정하며 실제 SQL을 실행한다. 에이전트는 풀이에 맞춰 확인 질문·힌트·추가 분석을 제안한다.
6. 사용자가 타당한 다른 분석 경로를 선택하면 목표와 공개 데이터의 범위 안에서 이어간다. 새 데이터가 필요한 변경은 새 과제 또는 새 버전으로 구분한다.
7. 사용자가 근거를 연결해 제출하고 리뷰를 받는다. 필요하면 수정 제출하거나 명시적으로 해설을 공개한다.
8. 에이전트가 확인된 강점·보완점·도움 이력을 근거로 다음 훈련을 제안한다. 사용자는 수준과 주제를 바꿀 수 있다.

새로고침·서버 재시작 후 원래 과제·데이터·평가 버전과 저장된 맥락으로 재개한다. 최신 콘텐츠로 자동 교체하지 않는다.

## 5 요청 해석과 과제 설계

요청에서 관심 분야, 요청 난이도, 알려진 SQL 수준, 학습 목표, 원하는 문제 형식과 선택적인 시간 조건을 구분한다. 모든 항목을 필수 질문으로 만들지 않는다. 사용자가 형식을 지정하지 않으면 최근 훈련과 목표를 참고해 에이전트가 제안한다.

과제 계획에는 학습 목표, 요구 판단, 공개 상황·조건, 필요한 데이터, 난이도 근거, 기대 제출물, 평가 기준, 데이터 검증 방법을 포함한다. 이 계획은 검증과 실제 진행의 공통 기준이며 사용자에게는 학습에 필요한 부분만 공개한다.

| 가능한 사고 과제 예시 | 사용자가 연습할 판단 |
| --- | --- |
| 지표 계산 | 대상·기간·분모·중복·관측 조건을 적용 |
| 이상 현상 조사 | 변화가 큰 집단·구간과 대안 설명을 탐색 |
| 모호한 업무 요청 구체화 | 확인 질문, 지표·비교 기준과 분석 우선순위 결정 |
| 분석 설계 | 필요한 데이터와 확인 방법, 결론의 한계 제시 |
| 보고서·SQL 검토 | 잘못된 집계·근거 부족·인과 과장을 찾아 수정 |

이 표는 고정 문제 목록이 아니라 설계 예시다. 최근 과제의 목표·요구 판단·데이터 상황을 비교해 형식 반복을 감지한다. 단순 제목·숫자·seed 변경을 새로운 사고 과제로 인정하지 않는다. 사용자가 같은 유형의 반복 연습을 요청한 경우에는 그 요청을 우선한다.

## 6 난이도와 학습 상태

2026-10-04 사용자 결정에 따라 난이도는 문제의 모호함을 주된 기준으로 정한다. 초급은 문제 상황과 해야 할 분석이 명확하게 보인다. 고급으로 갈수록 실무에서 있을 법한 업무 요청을 제시하고, 무엇이 문제인지와 그 원인을 직접 알려주지 않는다. SQL 복잡도·데이터량은 수행 가능성을 조절하는 보조 조건이며 난이도를 올리는 주된 기준이 아니다.

모호함은 업무 목표, 분석 대상·기간·지표, 비교 기준, 원인 후보가 얼마나 명시되어 있는지로 설명한다. 과제 계획에 요청 수준·제공한 정보·사용자가 판단할 정보·난이도 이유와 난이도 규칙 버전을 기록한다. 단순 문장 축약이나 필수 데이터 누락을 고급 난이도로 취급하지 않는다.

| 수준 예시 | 과제 요구 |
| --- | --- |
| 초급 | 문제 상황·대상·지표·기간·비교 기준을 명확히 제공. 사용자는 정해진 문제를 정확히 계산·설명 |
| 중급 | 관측된 현상과 업무 목표를 제공하되 분석 조건·비교 집단·원인 후보 일부를 직접 제시하지 않음. 사용자가 탐색·가설 검증 |
| 고급 | 실무형 업무 요청·불완전하거나 상충하는 신호를 제공. 문제 정의와 원인이 직접 보이지 않으며 사용자가 질문·지표·우선순위를 정하고 여러 설명을 검토 |

예를 들어 초급은 “지정 기간 신규 유저의 D7 리텐션을 계산하세요”, 중급은 “업데이트 이후 재방문율이 낮아졌습니다. 어느 유저 집단에서 변화가 큰지 확인하세요”, 고급은 “최근 업데이트 반응이 좋지 않다는 의견이 있습니다. 데이터를 보고 무엇을 확인하고 대응해야 할지 제안하세요”처럼 상황의 명확성을 다르게 구성한다. 이는 형식 예시이며 고정 문제 목록이나 생성된 데이터의 사실을 뜻하지 않는다.

고급에서도 질문으로 확인할 수 있는 업무 조건, 분석 가능한 공개 데이터와 근거를 제공한다. 에이전트는 정의 확인 질문에 답하되 비공개 원인을 정답으로 알려주지 않는다. 원인을 확정할 수 없는 경우 근거 있는 후보·한계·추가 확인 방법을 인정한다. 사람 검토에서 상황의 모호함과 실제 분석 가능성을 함께 확인한다.

사용자가 요청한 수준을 우선한다. 한 번의 점수로 능력을 확정하지 않고 풀이·수정·도움 사용에서 관측한 근거를 기록한다. 에이전트는 다음 과제의 난이도나 도움을 조정하는 이유를 설명하며 사용자가 변경할 수 있다. 힌트를 썼다는 이유만으로 일률 감점하거나 도움 수준을 강제로 높이지 않는다.

## 7 데이터와 출제 전 검증

LLM은 과제 계획과 설명을 구성하고, 데이터·기준 수치는 생성 코드와 실제 DB 계산으로 관리한다. 학습자 SQL은 공개 테이블의 읽기 전용 조회로 제한한다. 출제 엔진의 적재·검증 권한은 학습자 권한과 분리한다.

출제 준비는 요청 접수, 설계, 데이터 준비, 검증, 출제 가능, 실패, 취소 상태를 관리한다. 상태와 완료된 작업을 저장하며 요청 재전송으로 같은 작업이 중복 생성되지 않게 한다. 실패한 데이터는 학습 문제로 공개하지 않는다. 이미 시작한 훈련의 데이터는 수정하지 않는다.

필수 검증은 기본 키·외래 키·시각·이벤트 일관성, 동일 seed와 버전의 재현성, 공개 테이블만으로 분석 가능함, 기준 집계의 실제 실행, 필요한 현상과 표본 존재 여부다. 확정 답이 있는 계산은 독립 집계 또는 별도 검산으로 대조한다. 열린 과제는 하나의 정답 문장 대신 공개 근거로 가능한 결론·불가능한 단정·허용 가능한 대안을 검증한다.

분석 설계·보고서 검토 과제도 제공 자료의 수치와 주장이 검증 가능해야 한다. 증거가 부족한 상황 자체를 훈련할 때는 불확실성 식별을 목표로 명시하고, 알 수 없는 원인을 정답으로 강요하지 않는다.

과제별 공개 테이블 목록과 데이터 사전을 검증된 패키지에서 읽는다. 현재 SQL 정책의 고정 테이블 목록과 문제 1 전용 검증을 범용화하되 쓰기·외부 접근·시스템 객체 제한을 유지한다. 데이터·문제·평가 자료·생성기·검증 규칙의 버전과 해시를 기록한다.

## 8 능동적인 훈련 진행

에이전트는 사용자 요청, 공개 과제, 누적 대화·결정, 서술 초안, 명시적으로 연결된 근거와 도움 이력을 바탕으로 다음 행동을 판단한다. 이미 확인한 내용을 반복 질문하거나 타당한 분석을 정해진 순서로 되돌리지 않는다.

| 풀이 상황 | 가능한 행동 |
| --- | --- |
| 지표·대상이 불명확 | 가장 중요한 정의를 확인하는 질문 |
| 집계 단위·관측 조건 오류 | 오류 근거와 한 가지 확인 행동 제안 |
| 가설과 결과가 충돌 | 다른 비교나 대안 설명의 확인 제안 |
| 다른 타당한 경로 선택 | 이유·근거를 확인하고 그 경로로 진행 |
| 충분한 근거 확보 | 결론·한계 정리와 제출 제안 |
| 막힘 또는 도움 요청 | 현재 시도에 맞는 단계적 힌트 |

위 행동을 직접 실행할 도구와 검증된 서버 결과를 사용한다. 실행하지 않은 SQL·조회하지 않은 수치를 실행 사실처럼 말하지 않는다. 사용자 대신 분석 방향을 확정하거나 학습용 SQL을 무단 실행하지 않는다. 추가 분석 제안과 사용자가 수행한 분석을 구분한다.

2026-10-04 사용자가 추천 방향을 채택했다. 질문·분석 결과 확인·제출 같은 의미 있는 행동이 끝났을 때 필요한 다음 행동을 제안하고, 타이핑 중 AI를 반복 호출하지 않는다. 능동 코칭의 켜기·끄기와 도움 수준을 제공한다. 세션 시작 시 자동 코칭 호출 여부와 비용 가능성을 안내한다. 최대 생성 시도·응답 시간·AI 호출 한도와 재시도 정책은 설정값으로 관리하며 구체적인 값은 관련 Spec에서 정한다. 한도 종료·실패를 안내하고 무한 반복하지 않는다. 기존 PRD의 사용자 요청 시에만 AI 호출하는 규칙은 이 정책에 맞게 변경한다.

## 9 힌트와 평가

힌트는 방향·지표·SQL 구조 등의 도움 수준을 유지할 수 있으나 현재 시도와 과제에 맞게 구성한다. 일반 코칭에는 비공개 생성 사건·기준 SQL·정답 자료를 전달하지 않는다. 전체 해설은 명시적 공개 이후 제공하고 사용 여부를 기록한다.

평가는 문제 정의, 분석 접근, 계산 정확성, 결과 해석, 다음 행동을 공통 관점으로 활용하되 과제별 필수 조건·적용 항목·배점을 출제 전에 고정한다. 분석 설계처럼 계산이 필수가 아닌 과제에 SQL 미제출을 자동 감점하지 않는다. 사용자에게 공개하는 평가 관점과 숨겨야 하는 정답 자료를 구분한다.

대안 SQL·다른 결론은 실제 근거와 과제 목표에 맞으면 인정한다. 생성 과정에서 알고 있는 사건을 학습자가 관측 데이터로 입증할 수 있는 사실과 혼동하지 않는다. 실행 결과로 계산을 확인하고, AI는 설명·접근·한계·액션을 검토하며 불확실한 판정을 표시한다.

리뷰에는 적용 기준, 항목별 이유, 연결 근거, 잘한 점, 보완점과 다음 행동을 제공한다. 수준·가중치의 유효성과 참조 ID를 서버에서 검사하고 총점을 계산한다. 평가 기준·모델·프롬프트 버전을 보존한다. 현재 형식 실패·오진·정답 노출·점수 편차를 개선하고 사람 검토로 통과를 확인한다.

## 10 기록과 화면

출제 요청과 확정 계획, 과제·데이터 버전, 생성·검증 상태, 사용자가 결정한 정의와 방향, 저장 가능한 대화, 도움 이력, 학습 상태의 근거, 보고서·리뷰·다음 과제 추천 이유를 저장한다. 보관·삭제와 학습 상태 수정 정책은 관련 Spec에서 정한다. 다중 사용자 회원 시스템은 추가하지 않는다.

미저장 SQL·결과는 영구 기록·대화·파일럿 이벤트로 우회 저장하지 않는다. SQL과 결과는 명시적으로 선택 저장한 실행만 근거로 연결한다. 대화에 붙여 넣은 SQL·결과도 자동 영구 저장하지 않도록 저장 가능한 메시지와 임시 근거를 구분하는 입력·저장 정책이 필요하다. 미저장 자료를 포함한 원문을 제거하는 범위를 서버에서 검증하고, 자동 판별이 불확실하면 임시 처리 또는 명시적 저장 선택을 요구한다. 재개 시 임시 자료가 사라졌음을 표시하고 그 자료를 확인한 것으로 간주하지 않는다.

| 화면 | 필요한 경험 |
| --- | --- |
| 훈련 요청 | 자연어 요청, 원하는 난이도, 지원 범위, 이전 훈련 이어하기 |
| 출제 준비 | 설계·데이터·검증 진행, 실패 안내, 취소·재시도 |
| 분석 작업 | 대화, 현재 과제·목표, 데이터 사전, SQL·결과, 다음 행동 제안 |
| 제출·리뷰 | 과제에 맞는 제출물, 주장별 근거, 평가·수정·해설 |
| 학습 이력 | 대화·결정·도움과 버전 복구, 다음 훈련 제안 |

과제 목표와 입력 안내는 유형에 맞게 바꾸고 기존의 이탈률 전용 문구를 제거한다. 고정 탭이 있어도 모든 과제에 같은 사고 순서를 강제하지 않는다. 오류가 나도 현재 입력을 유지하고 저장 실패·AI 실패·출제 실패·SQL 오류를 구분한다.

## 11 구현 순서와 연결 명세

1. 요청 해석·과제 계약·난이도와 평가 기준을 정의하고 기존 리뷰 품질을 개선한다.
2. 기존 데이터로 서로 다른 사고 과제를 설계하고 생성·적재·검증·출제를 연결한다.
3. 대화·학습 상태와 진행 판단을 구현하고 상황별 힌트·평가를 연결한다.
4. 요청부터 수정 제출·재개까지 화면을 연결하고 다음 훈련 추천·반복 방지를 구현한다.
5. 다양한 요청·형식·난이도·오류 흐름을 검증하고 다른 PC 실행과 학습자 파일럿을 진행한다.
6. 필요한 데이터 분야를 생성·검증 기능 단위로 확장한다.

품질 로그의 공통 계약을 1단계에서 정의하고 기능을 구현할 때 해당 이벤트·시간·사용량·판정을 함께 연결한다. 출시 직전에 로그를 덧붙이는 방식으로 진행하지 않는다.

이 순서는 권장 구현 순서다. 기능별 Spec은 별도로 작성하며 이 PRD 작성만으로 Spec 생성이나 구현 완료를 선언하지 않는다. [Spec 001](../specs/001-new-user-churn.md)은 기존 계산 검증 사례, [Spec 002](../specs/002-training-data-packages.md)는 패키지 계약, [Spec 003](../specs/003-training-record-contracts.md)은 기록 기반, [Spec 004](../specs/004-local-technology-stack.md)는 실행 환경, [Spec 005](../specs/005-quality-and-pilot.md)는 검증 도구의 기반으로 활용한다. 새 요구사항과 충돌하는 계약은 관련 Spec을 갱신하고 기존 기록의 호환성을 검증한다.

초기 파일럿은 대상 학습자 5명을 제안한다. 기존 도구로 직접 개입 여부, 중단 지점, 다음 수정 행동, 최초·수정 제출 비교를 기록한다. 4명 이상이 직접 개입 없이 한 과제를 리뷰까지 완료하고 수정할 행동을 설명하며, 과반이 놓친 핵심 조건을 수정 제출에 반영하는 것을 초기 목표로 둔다. 추가로 과제 형식이 반복된다고 느끼는지, 에이전트의 제안이 도움인지 방해인지와 그 이유를 수집한다. 학습 효과는 점수 상승만으로 확정하지 않는다.

## 14 품질 지표 수집과 로그 관리

출제 성공률, 문제 다양성, 난이도 적합성, 코칭 적절성, 평가 신뢰성, 독립 수행, 수정 효과, 대기·사용량을 측정한다. 운영 이벤트만으로 학습 효과·의미적 품질을 확정하지 않으며 필요한 사람·학습자 판정을 별도로 수집한다. 최종 목표 수치는 기존 12절의 초기 검증 제안을 참고하고 실제 측정 후 확정한다.

| 지표 | 필요한 이벤트·판정 | 집계 정의 |
| --- | --- | --- |
| 출제 성공률 | 출제 시도·검증 통과·공개 완료·실패·취소 | 최초 실제 출제 시도가 시작된 요청 중 출제 완료 비율. 재시도는 같은 요청으로 묶고 실패·취소를 각각 표시. 진행 중은 별도 표시 |
| 문제 다양성 | 주제·학습 목표·요구 판단·과제 형식·중복 판정 | 같은 주제의 연속 과제를 비교한 사람 판정에서 의미 있는 차이가 확인된 비율. 사용자 요청 반복은 별도 분류 |

공통 이벤트에는 event_id, event_type, schema_version, occurred_at(UTC), operation_id, parent_operation_id, 요청·훈련·과제 식별자, 적용 가능한 콘텐츠·난이도·평가·모델 버전, 상태·고정 오류 코드·처리 시간을 기록한다. 필요한 필드만 사용하는 이벤트별 허용 목록과 타입을 정의한다. 화면에는 Asia/Seoul 기준 시각을 표시한다. 실패 전에 과제 ID가 없을 수 있으므로 요청 ID로도 추적한다.

서버에서 생성·검증·AI·제출 상태를 기록하고, 화면 행동은 신뢰 가능한 서버 이벤트와 구분한다. 재전송은 event_id로 중복 방지하고 요청·작업 ID로 재시도를 연결한다. 서버 재시작으로 종료가 누락된 작업은 중단·미완료로 표시하며 성공으로 추정하지 않는다. 사람 판정에는 검토자·대상 ID·판정 기준 버전·시각을 기록하고 변경 이력을 보존한다.

AI 호출은 성공·실패·시간 초과·형식 실패·재시도를 각각 기록한다. 제공자가 토큰 사용량을 반환하면 저장하고 미반환·알 수 없는 값은 null과 누락 이유로 남긴다. 실패 요청의 사용량을 0으로 간주하지 않는다. 비용은 모델별 단가·통화·기준일이 설정된 경우에만 추정하고 실제 청구와 구분하며 무료 사용을 추정하지 않는다.

운영 지표 로그는 별도의 기록 테이블 또는 저장 계층에서 관리하고 학습 데이터 DB에 넣지 않는다. API 키·토큰, SQL 원문·결과 행, 대화·프롬프트·응답 원문을 지표 로그에 넣지 않는다. 의미적 품질 판정은 명시적으로 저장한 근거와 별도 검증 표본을 참조하며 저장하지 않은 자료를 로그로 수집하지 않는다. 필요한 자유 서술·학습 기록은 운영 지표 이벤트와 구분해 기존 저장 계약을 따른다.

로컬 운영자에게 기간·분야·난이도·모델·규칙 버전별 집계 조회와 구조화 JSON 또는 CSV 내보내기를 제공한다. 지표 정의 버전, 분모·표본 수·미판정·결측·실패·취소·진행 중을 함께 표시한다. 로그 수집 실패를 감지·표시하고 불완전한 집계를 완전한 측정으로 보여주지 않는다. 로그 보관 기간과 삭제 정책은 구현 Spec에서 정하고 훈련 삭제 시 연결 기록의 처리와 집계 영향을 검증한다.

현재 quality.py의 파일럿 이벤트는 연결된 참가자의 SQL 상태·단계 이동만 수집한다. API 제공자는 현재 토큰 사용량을 결과로 전달하지 않는다. 이 기반만으로 위 지표가 모두 수집된다고 보지 않으며, 공통 이벤트 저장·AI 사용량 전달·사람 판정·집계 경로를 추가 구현해야 한다.

## 15 구현 전 검토에서 채택한 운영 기준

2026-10-04 사용자가 추천안을 채택했다. 아래 기준은 앞 절의 요구사항을 구체화하며, 이 문서 작성은 구현·검증 완료를 뜻하지 않는다.

1. 출제 전에 처음 공개할 정보, 질문하면 제공할 업무 조건, 해설 전 숨길 원인·정답을 구분해 버전과 함께 고정한다. 대화 중 새로운 업무 사실을 만들어내지 않는다. 계획에 없는 사실을 질문받으면 확인할 수 없음을 밝히고 가능한 분석 범위를 안내한다.
2. 모호함 검토는 목표·지표·비교 기준·원인 후보 중 사용자가 판단할 부분을 확인한다. 필수 데이터 부족은 고급 난이도가 아니라 출제 오류다. 원인 확정이 불가능하면 근거 있는 후보·한계·추가 확인 방법도 좋은 풀이로 인정한다.
3. 검증된 생성 기능과 평가 규칙의 지원 범위에서는 개별 과제를 자동 검증 후 출제한다. 새로운 생성 기능·평가 규칙은 사람 검토로 사용 가능 상태를 확인한 뒤 자동 출제에 사용한다. 매 문제의 사람 승인을 요구하지 않는다. 자동 검증은 분석 가능성과 수치·구조를 확인하며 의미적 품질 통과를 대신하지 않는다.
4. 선택 저장 전의 실제 실행 결과도 현재 훈련 화면에서 임시 코칭 근거로 연결할 수 있다. 훈련·버전·유효기간을 확인하고 서버가 보유한 결과를 사용한다. 임시 SQL·결과와 이를 그대로 재현할 수 있는 코칭 원문은 영구 대화·로그에 넣지 않는다. 만료·새로고침 후 자료를 확인한 것으로 간주하지 않으며 보고서 연결·재개에는 선택 저장을 요구한다. 동일 행동의 재전송으로 자동 코칭을 중복 요청하지 않는다.
5. 과제별 필수 판단·필요 근거·인정 가능한 한계·평가 항목·배점을 출제 전에 고정한다. 풀이 도중 필수 조건을 추가해 감점하지 않는다. 목표 변경이 필요하면 이유를 안내하고 별도 과제·버전으로 구분한다.
6. 반복 방지의 초기 비교 범위는 최근 5개 과제로 두고 설정값으로 관리한다. 사용자가 명시적으로 요청한 반복은 별도 분류한다.
7. 지표는 난이도·과제 형식·모델·규칙 버전별로 구분한다. 로그 자동 집계와 사람·학습자 판정을 구분하며 미판정은 성공으로 세지 않는다. 출제 성공률·시간·사용량 목표는 측정 후 조정하되 검증 실패 과제 공개·허위 수치 제시·해설 전 정답 노출·미저장 근거 영구 저장은 검증 표본에서 허용하지 않는다.

## 16 순차 작업과 병렬 작업 계획

공통 계약을 먼저 확정하고 그 계약을 기준으로 작업을 나눈다. 개발 작업이 병렬이라는 이유로 실제 출제의 데이터 검증·공개 순서를 생략하지 않는다. 아래는 초기 의존성 검토 결과다. 첫 사용 구간은 Spec 006·007에 구현했으며, 2026-10-04 후속 전체 구현 명세는 [Spec 안내와 요구사항 연결표](../specs/README.md)의 008~013을 따른다. 후속 명세 작성은 구현 완료로 세지 않는다.

### 먼저 순차적으로 정할 공통 계약

요청·과제 계획 → 공개 정보·질문 시 정보·비공개 평가 분리 → 근거·대화 저장 경계 → 작업 상태·식별자·버전 → API·로그 이벤트 순서로 검토한다. 앞 계약을 바꾸면 뒤 계약에도 영향이 있으므로 공통 검토 지점을 한 곳에 둔다. 필드의 상세 정의와 초기 설정값은 첫 공통 Spec에서 정한다.

계약에는 요청·훈련·과제·작업 ID, 모호함 조건, 필수 완료 조건·배점, 공개 테이블, 임시·저장 근거 참조, 취소·실패·재시도·중복 처리, 이벤트 허용 필드를 포함한다. 새 계약에서 기존 저장 패키지·훈련을 읽는 호환 방식과 DB 변경 순서도 함께 정한다.

### 공통 계약 이후 병렬로 준비할 작업

| 작업 묶음 | 포함하는 신규 작업 | 먼저 필요한 것 | 병렬 개발의 범위 |
| --- | --- | --- | --- |
| 출제와 데이터 | 자연어 요청, 문제 설계·다양성, 난이도, 생성·적재, 출제 전 검증 | 과제·정보 공개·평가·패키지 계약 | 기록·로그·화면과 별도 모듈로 개발. 요청 해석→계획 확정→생성→검증→공개는 묶음 안에서 순차 연결 |
| 기록과 로그 | 대화·학습 상태, 이벤트 저장·집계·내보내기, 기존 기록 호환 | 저장 경계·ID·상태·이벤트 계약 | 출제 실물이 없어도 계약 표본으로 저장·재개·중복·집계 검증 가능. 실제 이벤트 연결은 각 기능과 통합할 때 확인 |
| 코칭과 평가 | 진행 판단, 상황별 힌트·평가, 기존 품질 개선 | 공개 정보 분리·완료 조건·근거·대화 계약 | 고정 검증 표본과 대체 기록 인터페이스로 개발 가능. 실제 임시 근거·누적 상태 연결은 기록 기능 이후 |
| 학습·운영 화면 | 요청·출제 상태·대화·SQL·제출·로그 조회 화면 | API·상태·오류·근거 계약 | 모의 API로 화면 개발 가능. 실제 DB·AI·저장·재개 흐름 완료는 통합 이후 |

다음 훈련 추천은 과제 메타데이터와 검증된 수행·도움 이력이 필요한 후속 작업이다. 계약 표본으로 로직을 준비할 수 있지만 실제 출제·평가·학습 기록 연결 후에 완료를 판정한다. 사람 검토 표본과 판정 화면은 공통 평가 계약 이후 병렬로 준비할 수 있다.

### 통합 시 지킬 순서

1. 공통 계약·기록 변경·이벤트 저장 기반을 연결하고 기존 패키지와 훈련의 재개를 확인한다.
2. 요청 해석→계획 확정→데이터 생성·적재→검증→과제 공개를 실제 DB로 확인한다. 완료 조건과 평가 자료를 데이터 검증 결과에 대조해 고정한다.
3. 공개 과제→실제 SQL→임시·선택 저장 근거→대화·진행 판단을 연결한다. 비공개 정보와 임시 원문의 저장 경계를 확인한다.
4. 제출→리뷰→수정 제출·재개를 연결하고 이벤트·토큰·처리 시간 수집을 확인한다.
5. 실제 이력 기반 다음 과제 추천·최근 5개 비교와 지표 집계를 확인한다.
6. 전체 화면·장애·사람 품질 판정·다른 PC·파일럿을 검증한다. 모의 API 성공을 실제 제품 완료로 세지 않는다.

각 작업의 단위·계약 검증은 병렬로 준비할 수 있다. 실제 DB·화면 검증은 패키지·훈련·요청 ID를 분리하고, 동일 앱 상태를 바꾸는 취소·재시작·삭제 검증은 독립 환경 또는 순차 실행을 사용한다.

### 실행 중 병렬화할 수 있는 부분

하나의 출제 요청은 계획·조건 고정, 데이터 준비, 실제 검증, 공개 순서를 지킨다. 계획 고정 후에는 공개 설명·힌트 초안 준비와 데이터 생성의 독립 부분을 병렬로 처리할 수 있지만 최종 수치와 평가 자료는 검증 결과에 대조한 뒤 확정한다. 한 훈련의 상태 변경·저장·제출·리뷰는 버전·중복 방지 조건으로 순서를 관리한다.

다른 훈련의 독립 작업은 허용 동시 수와 DB·AI 한도 내에서만 병렬화한다. 현재 GeminiProvider.review는 공유 잠금으로 호출을 직렬화하므로 현재 코드가 AI 요청을 병렬 실행한다고 가정하지 않는다. 동시 수·호출 상한·취소 후 완료 응답의 처리 방식은 구현 Spec에서 명시하고 검증한다.

### Spec 작성 순서와 변경 충돌 관리

공통 계약 Spec을 먼저 작성·검토한 뒤 출제·데이터, 기록·로그, 코칭·평가, 화면의 세부 Spec을 독립적으로 작성할 수 있다. 다음 훈련 추천·통합 검증 Spec은 앞 계약과 결과를 참조한다. 2026-10-04 신규 Spec 008~013을 작성했다. 접속 데이터의 작은 신규 생성부터 완성하고 다른 분야는 이후 추가한다는 사용자 결정을 반영했다. 기본값·계약 확장·선행 의존성·PRD 11개 항목의 연결은 [Spec 안내](../specs/README.md)에 기록했다.

contracts.py, app.py, store.py, api_provider.py와 DB 변경은 여러 작업이 공통으로 참조하므로 변경 담당과 적용 순서를 정한다. 세부 기능은 별도 모듈로 나누고 공통 API 연결은 통합 단계에서 조정한다. 같은 파일·같은 검증 DB를 동시에 수정하거나 초기화하지 않는다. 구현·검증 후의 상태는 2절과 Spec 008~013 상단에서 추적한다.
