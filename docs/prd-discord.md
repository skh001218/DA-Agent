# DA-Agent Discord 대화형 데이터 분석 훈련 PRD

- 작성일 / 마지막 갱신일: 2026-10-06 (Asia/Seoul)
- 버전: 0.3
- 상태: Discord MVP 코드 구현·격리 DB 검증, 실제 서버·모델 검증 대기
- 기존 제품: [요청 기반 분석 훈련 PRD](PRD-v2.md)
- 사용자 결정과 근거: [판단 기록](../나의판단과근거.md)

Discord 안에서 가상의 데이터팀 구성원들과 대화하며 분석 과제를 끝내는 훈련 환경을 만든다. 첫 버전에서는 사용자가 자연어로 조회를 요청하면 에이전트가 SQL을 생성·검사·실행하고 실제 결과를 제공한다. 사용자는 분석 질문, 가설, 결과 해석과 대응 방안을 결정한다. 직접 SQL을 작성하는 훈련은 별도 명령으로 제공하는 후속 범위다.

## 1. 목적과 사용자 결정

### 1.1 해결하려는 문제

기존 웹 앱은 데이터 분석 과제 생성, SQL 실행, 코칭, 보고와 평가를 제공한다. 사용자는 이를 Discord에서 사용하는 에이전트로 확장하고 싶다고 밝혔다. 원하는 경험은 다음 두 가지다.

1. 가상의 데이터팀에서 동료들과 일하는 경험.
2. 웹으로 이동하지 않고 간단하게 사용하는 경험.

Discord에서 긴 SQL을 직접 작성하면 문법 오류 확인과 실행 결과를 보면서 수정하는 과정이 불편할 수 있다는 우려가 있었다. 이에 따라 첫 버전은 자연어 조회 결과를 바탕으로 원인을 분석하고, SQL 작성 연습은 별도 명령으로 분리하는 방향을 제안했다.

### 1.2 결정 상태

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 핵심 목적 | 사용자 확정 | 가상의 데이터팀 경험과 웹 이동 없는 간편한 사용 |
| 사용자 인터페이스 | 사용자 확정 | 학습자의 핵심 훈련은 Discord 안에서 완료 |
| 첫 버전의 훈련 방식 | 사용자 제안, 본 PRD의 MVP 기준 | 자연어 조회 → 실제 실행 결과 → 사용자 원인 분석 |
| SQL 직접 작성 | 사용자 제안, 후속 범위 | 별도 명령으로 SQL 작성·실행·피드백 훈련 |
| 역할 수·스레드·명령 구성 | 설계안 | 봇 하나, 세 역할, 과제별 전용 스레드를 기본안으로 사용 |
| 공개 범위·운영 비용·배포 환경 | 출시 전 결정 필요 | 13절 참조 |

첨부된 ChatGPT 대화의 모든 제안을 사용자 확정 사항으로 취급하지 않는다. 이 PRD는 기존 PRD 전체를 폐기하거나 기존 웹 기능 삭제를 요구하지 않는다. 기존 분석 엔진을 재사용하는 Discord 제품 범위를 정의한다.

## 2. 대상 사용자와 훈련 목표

주 대상은 게임 데이터 분석을 연습하려는 학습자다. 첫 버전의 대화형 분석은 SQL 문법 숙련을 필수 진입 조건으로 두지 않는다. 다만 지표의 의미와 계산 기준을 이해하고 자신의 질문·결론을 설명하는 활동은 필요하다.

훈련 목표는 업무 요청 구체화, 비교 대상과 지표 정의, 가설 설정, 추가 분석 선택, 대안 설명 검토, 불확실성 표현과 대응 결정이다. 에이전트가 대신 계산한 SQL의 정확성을 사용자의 SQL 작성 역량으로 평가하지 않는다.

데이터의 정의·수집 상태·관측 가능성을 점검하고 그 숫자를 판단에 사용할 수 있는지 설명하는 능력도 훈련한다. 시스템이 SQL을 정확히 실행하는 것과 학습자가 분석 데이터의 신뢰성을 판단하는 것은 별도로 확인한다.

사용자는 분석 방향과 결론을 결정한다. 에이전트는 요청한 계산을 수행하고 질문·피드백을 제공하되, 사용자의 입력 없이 원인 조사와 최종 보고를 자동 완료하지 않는다.

### 2.1 게임 과제 범위와 대표 과제

다음 표는 과제의 교육 범위이며 모든 범주를 MVP에서 구현한다는 의미는 아니다. 과제마다 게임 장르·규칙, 업무 결정, 필요한 이벤트와 계산 단위를 공개한다. 특정 장르의 지표 기준을 모든 게임에 공통으로 적용하지 않는다.

| 범주 | 업무 질문 예시 | 핵심 훈련 |
| --- | --- | --- |
| 튜토리얼·성장 구간 | 어느 단계에서 이탈이 늘었는가 | 단계별 퍼널, 소요 시간, 관측·수집 상태 점검 |
| 리텐션·이벤트 | 업데이트 후 재방문 하락을 어떻게 설명할 것인가 | 코호트, 관측 완료, 유입 구성·기간 비교 |
| 결제·상품 | 매출 변화가 구매자 수와 구매 금액 중 무엇과 연결되는가 | 구매 전환·반복 구매·환불과 구성 변화 |
| 재화·경제 | 공급·소모 변화가 어떤 집단에 영향을 주는가 | 흐름과 잔액 구분, 집단 비교, 게임 규칙 해석 |
| 전투·밸런스 | 승률 차이를 밸런스 문제로 볼 수 있는가 | 숙련도·장비·매칭 등 대안 설명, 표본과 불확실성 |

MVP에서는 현재 데이터 생성 범위 안에서 대표 과제 하나를 선정해 전체 흐름을 검증한다. 선정 조건은 실제 계산 가능성, 최소 하나의 대안 설명 비교, 데이터 신뢰성 확인, 업무 대응 보고다. 생성·공개 전에 조건 충족 여부를 확인하며 현재 데이터로 충족하지 못하면 필요한 보완을 알리고 출시 완료로 처리하지 않는다. 테이블 한도 확대는 별도 결정 사항이다.

대표 과제에는 학습 목표, 공개 필수 조건, 타당한 분석 경로 예시, 인정할 한계, 평가 기준 버전, 도움 정책과 사람이 검토할 표본을 고정한다. 특정 조회 순서를 정답으로 강제하지 않는다. 최소 교육 완료 기준은 다음과 같다.

1. 업무 목표와 연결된 지표·비교 대상·기간을 정의한다.
2. 관련 데이터 정의와 관측·수집 한계를 점검한다.
3. 가설과 그 가설을 약화시킬 수 있는 결과를 설명하고 확인 가능한 비교를 선택한다.
4. 실행 근거에 따라 가설을 유지·수정·기각하거나 판단을 보류한다.
5. 확인된 사실과 가능한 설명을 구분해 대응·추가 확인 사항을 보고한다.

이 기준은 공개된 자료로 수행 가능한 범위에서 적용한다. 초급은 안내된 기준을 이해·적용하는 활동, 중급은 스스로 기준과 대안을 선택하는 활동, 고급은 교란·관측 한계와 후속 검증을 설계하는 활동을 중심으로 한다.

## 3. MVP와 후속 범위

### 3.1 Discord MVP 포함 범위

- 자연어 주제·목표로 훈련 시작, 난이도 선택 및 필요한 추가 질문.
- 기존 출제·합성 데이터·검산 기능을 사용한 분석 가능한 과제 제공.
- 과제별 Discord 전용 공간과 사용자별 기록·접근 권한.
- 자연어 조회 요청의 기준 확인, SQL 생성, 읽기 전용 실행과 결과 제공.
- 결과를 근거로 한 가설·해석 대화, 요청 시 멘토 도움.
- 대표 게임 과제의 공개 교육 기준, 수준별 도움, 데이터 신뢰성 점검 활동.
- 최종 보고, 업무 담당자 후속 질문, 수정 제출, 분석 평가와 다음 훈련 추천.
- 기준 과제와 유사한 새 과제에서 분석 행동을 관측해 학습 성장 기록.
- 기록 재개, 실패·중복 처리, 호출량·실행량 기록.

### 3.2 후속 범위

- 별도 SQL 연습 명령과 사용자 SQL 실행·피드백.
- 운영 데이터에 따라 역할 세분화, 추가 품질 검토자, 더 다양한 과제.
- 공동 분석 훈련은 별도 참여·소유권·평가 계약을 정한 후 검토.

### 3.3 MVP 제외 범위

실시간 SQL 에디터, 사용자가 연결하는 실무 DB, 실제 기업 비공개 데이터, 음성 분석, 역할마다 별도 Discord 봇, 사용자 없는 에이전트 간 무제한 토론, 벡터 DB, 여러 모델 제공자 자동 라우팅은 포함하지 않는다. CSV 파일을 제공하더라도 파일 다운로드가 핵심 훈련의 필수 단계가 되어서는 안 된다.

기존 다중 테이블 생성 제약 변경은 사용자 판단 기록의 보류 결정을 유지한다. 이 PRD 작성만으로 데이터 생성 범위를 확대하지 않는다. 현재 데이터로 답할 수 없는 요청은 한계를 안내한다.

| 역할 | 책임 | 개입 시점 | 제한 |
| --- | --- | --- | --- |
| 업무 담당자 PM / Stakeholder | 배경·업무 목표 제시, 자원·우선순위 질문 | 시작, 사용자 보고 후 | 새로운 업무 조건을 사실처럼 즉석에서 추가하지 않음 |
| 멘토 Senior DA | 질문 구체화, 사고를 돕는 질문·힌트 | 도움 요청 또는 진행에 필요한 확인 | 정답·내부 기준 SQL·최종 결론을 먼저 제공하지 않음 |
| 리뷰어 | 제출된 근거·해석·한계·대응 평가 | 중간 검토 요청, 최종 제출 | AI가 작성한 SQL을 사용자 작성 역량으로 채점하지 않음 |

조회 실행은 공통 도구 기능이며 별도의 발언 역할을 추가하지 않는다. 학습 기록·추천은 평가 후 기능으로 시작한다. 역할명과 문구는 명확히 표시하되 사용자가 매번 담당 역할을 선택할 필요는 없게 한다.

역할 수는 모델 프로세스 수나 봇 수와 동일하지 않다. 봇 하나와 간단한 진행 제어를 기본안으로 사용한다. 역할별로 공개 업무 정보, 사용자 풀이, 실행 결과, 평가 기준에 대한 접근을 구분한다. 사용자 대화에 숨겨진 정답·출제용 원인 정보·내부 기준 SQL을 포함하지 않는다. 평가 서비스는 필요한 기준을 내부적으로 사용하되 이를 그대로 노출하지 않는다.

기본 흐름은 `에이전트 → 사용자 → 에이전트`다. 애매한 조회의 확인 질문과 조회 실행은 자동 처리할 수 있으나 사용자가 요청하지 않은 연속 분석은 수행하지 않는다.

### 4.1 도움 수준과 개입 조건

분석 난이도와 도움 수준은 별도로 저장한다. 초급 기본안은 선택지를 포함한 안내, 중급·고급 기본안은 사용자의 정의와 이유를 먼저 묻는 방식이다. 어느 수준이든 사용자가 도움을 요청하면 단계적으로 제공한다.

| 응답 유형 | 조건과 행동 | 학습 기록 |
| --- | --- | --- |
| 요청 확인 | 의미가 모호할 때 분모·기간 등의 의도를 질문하고 실행 보류 | 질문, 도움 전 사용자 답변, 확정 조건 |
| 개념 힌트 | 사용자가 설명을 요청하거나 확인 질문에 답하기 어려워함 | 설명한 개념과 적용 역량 |
| 분석 방향 힌트 | 사용자가 도움을 요청하면 비교 후보와 검토 이유 제안 | 제공 후보와 사용자의 선택·이유 |
| 중간 피드백 | 검토 요청 시 현재 근거의 누락·논리 문제를 지적 | 지적 항목과 이후 사용자 수정 |

“비율의 분모는 무엇인가요?”는 의도를 묻는 확인이다. “저번 주 접속자를 분모로 잡아보세요”는 개념·분석 도움이며 확인으로만 기록하지 않는다. 선택지가 정답 방향을 알려주면 도움 이력에 포함한다. 도움 이후 올바른 답을 했다는 이유로 도움 전 역량도 확인됐다고 기록하지 않는다.

초급에는 선택지와 쉬운 설명을 제공할 수 있다. 중급·고급은 먼저 사용자가 정의·이유를 답하게 하고, 답하기 어렵거나 명시적으로 도움을 요청한 경우 선택지를 제공한다. 실행에 필요한 조건이 확정되지 않았다고 틀린 기준으로 실행하지 않는다. 이미 명확한 요청에는 형식적인 확인을 반복하지 않는다.

에이전트는 매 조회마다 가설 입력을 요구하지 않는다. 첫 분석 방향 선택, 사용자의 해석, 방향 변경 또는 보고 시점에 이유와 예상·반박 결과를 묻고 기록한다. 사용자가 가설을 이미 설명했다면 다시 묻지 않는다. 멘토의 제안을 거절하거나 다른 타당한 경로를 선택했다는 이유로 감점하지 않는다.

## 5. 핵심 사용자 흐름

1. 사용자가 Discord에서 훈련 시작 명령과 원하는 주제·난이도를 입력한다.
2. 준비 상태를 안내하고 검증된 과제·데이터가 준비되면 전용 스레드에 업무 요청, 관측 기간, 데이터 사전, 목표를 제공한다.
3. 사용자가 자연어로 비교·집계·세분화 조회를 요청한다.
4. 계산 기준이 모호하면 추가 질문으로 확인한다. 기준이 명확하면 생성 SQL을 검사하고 실행한다.
5. 실제 결과와 기간·분모·필터·제한을 표시하고 실행 SQL을 확인할 수 있게 한다.
6. 사용자가 데이터의 신뢰성과 가설·해석을 설명하고 다음 조회를 선택한다. 필요하면 기록되는 멘토 도움을 받는다.
7. 사용자가 저장된 실행 결과를 근거로 결론·한계·대응 방안을 보고한다.
8. 업무 담당자가 우선순위·실행 가능성 등에 대한 후속 질문을 한다. 사용자는 답변하거나 추가 분석 후 보고를 수정한다.
9. 사용자가 최종 제출하면 리뷰어가 분석 과정과 최종 보고를 평가하고 사용자별 학습 상태와 다음 추천을 갱신한다.
10. 종료 또는 중단 후에도 기록과 원래 분석 기준을 재개할 수 있다.

### 대화 예시

> **업무 담당자:** 신규 유저 D7 리텐션이 하락했습니다. 어느 집단에서 하락했는지 확인하고 먼저 검토할 대응을 제안해주세요.
>
> **사용자:** 이번 주와 저번 주 접속 유저 비율을 보여줘.
>
> **에이전트:** 주별 고유 접속자 수의 증감률인가요, 저번 주 접속자 중 이번 주에도 접속한 비율인가요?
>
> **사용자:** 저번 주 접속자 중 이번 주에도 접속한 비율이야.
>
> **에이전트:** 확정한 두 기간과 분모·분자를 표시하고, 실제 DB 조회 결과를 제공합니다. 이 결과는 주간 재방문율이며 신규 유저 D7 리텐션과는 다른 지표임을 안내합니다.
>
> **사용자:** D7을 볼 수 있는 관측 완료 신규 가입 코호트로 바꾸고 유입 채널별로 비교해줘.
>
> **에이전트:** 코호트와 D7 정의를 확인한 뒤 실제 결과를 제공합니다.
>
> **사용자:** 광고 유입 구성 변화가 전체 하락에 영향을 줬을 가능성을 확인하려고 해.

예시에는 가상의 실행 수치를 넣지 않는다. 제품 응답의 숫자는 실제 조회 결과에서 가져온다. 데이터가 해당 분석을 지원하지 않으면 마지막 조회를 실행 가능한 것처럼 표현하지 않는다.

## 6. 기능 요구사항

### 6.1 시작과 명령

명령명은 구현 전 조정 가능한 설계안이다. 일반 대화로 분석을 이어가고 명령은 시작·재개·종료 같은 분명한 행동에 사용한다.

| 명령 / 버튼 예시 | 행동 |
| --- | --- |
| `/훈련` | 주제와 난이도로 대화형 분석 과제 시작 |
| `/재개` | 자신의 과제 선택 후 기존 스레드 또는 복구 공간 안내 |
| `도움 요청` | 현재 질문·가설·근거에 대한 멘토 도움 |
| `실행 SQL 보기` | 해당 조회에 실제 사용한 SQL 확인 |
| `보고서 근거로 선택` | 성공한 조회 결과를 보고서 근거에 연결 |
| `보고 작성` / `최종 제출` | 보고 초안·수정과 최종 평가를 구분 |
| `/종료` | 현재 훈련 중단 또는 종료 상태 저장 |

과제 준비 실패 시 임의로 다른 주제로 대체하지 않는다. 난이도는 단순 표·컬럼 수보다 비교, 불확실성, 교란과 의사결정 요구로 구분한다. 공개하지 못한 과제를 정상 시작으로 표시하지 않는다.

### 6.2 자연어 조회 계약

조회 요청은 질문 원문, 참조한 이전 조회, 지표, 계산 단위, 분자·분모, 비교 기간, 시간대, 필터, 그룹 기준과 필요한 테이블을 구조화한다. 사용자가 확정한 조건과 에이전트가 제안한 조건을 구분해 저장한다.

비율의 분모, 고유 사용자와 이벤트 수, 신규·기존 사용자 기준, 달력 주와 최근 7일, 진행 중인 주와 완료된 주처럼 값에 영향을 주는 모호함은 실행 전에 확인한다. 이전에 확정한 정의는 같은 과제에서 재사용하고 의미가 달라질 때만 다시 묻는다.

“왜 감소했어?”처럼 분석 목표를 묻는 질문과 구체적인 조회 요청을 구분한다. 분석 목표에는 가능한 비교 후보를 제안하고 사용자가 방향을 선택하게 한다. 사용자가 요청하지 않은 여러 조회를 연속 실행해 결론을 완성하지 않는다.

D7 리텐션은 과제에 정의된 가입 코호트 중 가입 7일 후에 접속한 사용자 비율로 다룬다. 시간대·날짜 경계·관측 완료 여부는 과제 계약을 따른다. 7일 이내 접속, 주간 재방문, 전체 주간 접속자 증감과 혼동하지 않는다. 분모가 0이거나 관측이 완료되지 않았으면 수치를 0%로 단정하지 않는다.

### 6.3 SQL 생성·검사·실행

- SQL 생성에는 해당 과제의 공개 스키마·데이터 사전·확정 조회 조건만 전달한다.
- 실제 공개 테이블·컬럼과 관계를 확인하고 기존 SQL 정책 및 DB 읽기 전용 권한을 거친다.
- 허용되지 않은 테이블, 다른 과제 데이터, 쓰기·스키마 변경·시스템 정보 조회는 실행하지 않는다.
- 구문 검사를 통과해도 의미가 맞는지 별도 검증한다. 조인 중복, 고유 사용자 수, 날짜 경계, 분모와 NULL 처리는 대표 기준 결과로 대조한다.
- 자동 수정은 같은 조회 의도와 확정 조건을 유지할 때만 허용한다. MVP 기본안은 최초 실행 후 1회 수정까지다. 실패 이력과 최종 SQL을 보존하고 재실패하면 이유와 다음 행동을 안내한다.
- 질문 의도가 바뀌는 수정은 사용자 확인을 받는다. 실행하지 않은 결과를 모델이 추정해 숫자로 제공하지 않는다.

현재 Settings 기본값은 쿼리 제한 시간 5초, 최대 수집 1,000행·1 MiB, 실행 결과 미리보기 200행이다. Discord 메시지 표시는 이보다 적은 행으로 시작하고 메시지 구성에 맞춰 분할한다. 구현 시 설정값을 읽어 표시하며 실제 값과 다른 고정 안내를 하지 않는다.

### 6.4 결과 표시와 근거 보존

응답에는 요청 요약, 확정 기간·시간대, 계산 기준·필터, 컬럼·단위, 실제 결과 미리보기, 실행 성공 여부와 실행 ID를 포함한다. 숫자의 설명은 결과가 말하는 범위로 제한한다. 집단 차이를 곧바로 인과관계로 단정하지 않는다.

표시 행만 줄인 경우와 실행 수집 한도로 결과가 불완전한 경우를 구분한다. 전체 행 수를 알 수 없으면 전체 건수처럼 표시하지 않는다. CSV는 실제 수집 결과만 제공하고 불완전한 결과를 전체 데이터라고 부르지 않는다. 핵심 비교 결과는 Discord 메시지에서 이해할 수 있어야 한다.

성공한 조회의 SQL·실행 조건·결과·데이터 버전을 영구 기록으로 보존하는 것을 기본안으로 한다. `보고서 근거로 선택`은 저장된 조회를 보고에 연결하는 행동이다. 기존 SQL 실행의 임시 메모리와 만료 시간만으로 Discord 근거를 보관하지 않는다. 빈 결과도 정상 실행 기록으로 저장하되 오류·시간 초과 결과는 성공 근거로 선택할 수 없게 한다.

### 6.5 보고·평가·학습 상태

보고에는 분석 질문, 핵심 발견, 선택한 실행 근거, 가설과 대안 설명, 한계, 대응과 추가 확인 사항을 포함한다. 짧은 초안부터 대화로 보완할 수 있게 하고 긴 입력은 이어 쓰거나 입력창을 통해 제출할 수 있게 한다.

업무 담당자의 후속 질문은 이미 공개된 업무 조건과 사용자의 보고에 근거한다. 새로운 데이터나 제약이 필요하면 추가 정보임을 명시하며 처음부터 있었던 평가 기준처럼 적용하지 않는다.

대화형 분석 평가 항목은 문제 정의, 지표·비교 설계, 가설·대안 검토, 근거 해석, 한계·의사결정이다. 데이터 신뢰성 점검은 관련 지표 설계·근거 해석 항목에 명시하고 동일 결함을 임의로 여러 항목에서 중복 감점하지 않는다. 각 평가에는 제출 근거와 개선 행동을 연결한다. 기존 SQL 평가 점수를 그대로 전용하지 않는다.

#### 공개 평가 계약과 판단 근거

[기존 평가 기준의 공개 조건·근거 중심 원칙](evaluation-rubric-v3.md)을 따른다. Discord 분석 모드에는 별도 평가 계약 버전을 사용한다. 적용 항목·배점·필수 조건·핵심 오류·인정할 한계·상위 등급 조건을 출제 전에 고정하고 사용자에게 공개한다. 점수를 사용할 경우 배점 합을 100으로 정하며 평가 도중 새 기준을 추가하거나 배점을 바꾸지 않는다. 실제 배점과 합격 기준은 대표 과제 계약에서 정한다.

| 항목 | 관측할 분석 행동 | 공개 조건으로 지정할 핵심 오류 예시 |
| --- | --- | --- |
| 문제 정의 | 업무 목표와 질문의 연결, 대상·기간·지표 정의 | 주간 재방문율을 D7 리텐션으로 해석 |
| 지표·비교 설계 | 분모·단위·관측 완료·비교 가능성, 데이터 정의 점검 | 세션 수를 고유 사용자 수로 정의, 미관측 코호트 포함 |
| 가설·대안 검토 | 예상·반박 결과 설명, 타당한 추가 비교, 가설 수정 | 결과와 충돌하는 가설을 근거 없이 확정 |
| 근거 해석 | 실행 결과 인용, 수집·표본 한계 점검, 사실과 설명 구분 | 누락 가능성을 무시한 해석, 집단 차이만으로 인과 단정 |
| 한계·의사결정 | 불확실성과 대응 우선순위, 검증 방법·후속 지표 | 검증되지 않은 설명만으로 근거 없는 대응 확정 |

초안뿐 아니라 중간 질문·가설 수정·기각·추가 조회 선택도 평가 근거로 연결한다. 평가 결과에는 근거가 된 메시지·실행·보고 버전, 판정 조건과 개선 행동을 함께 기록한다. 문장 길이, 전문 용어 수, 조회 횟수는 역량 점수의 대체 기준으로 사용하지 않는다.

판정은 기존 공통 등급 원칙에 따라 평가할 내용 없음(0), 확인된 핵심 오류(1), 타당한 내용이 있으나 필수 조건 누락(2), 필수 조건 충족(3), 공개된 추가 검증·한계 조건까지 충족(4)을 구분한다. 시스템 실행 실패·근거 손실처럼 판정 자체가 불가능하면 해당 조건을 `판정 보류`로 표시하고 0점으로 처리하지 않는다. 필수 항목이 보류이면 전체 확정 총점도 보류한다. 사용자가 가능한 필수 근거를 제출하지 않은 경우와 시스템 문제로 확인할 수 없는 경우는 구분한다.

#### 가설 검토와 인과 판단

- 출제자가 설정한 비공개 원인·정답 SQL·조회 순서를 맞히는 것을 목표로 두지 않는다. 공개 데이터와 업무 조건으로 뒷받침할 수 있는 분석을 평가한다.
- 틀린 초기 가설도 타당하게 검증하고 수정·기각했다면 해당 분석 행동을 인정한다.
- 서로 다른 타당한 경로와 결론을 인정한다. 관측 자료로 판단할 수 없다는 결론도 한계와 다음 검증이 타당하면 인정한다.
- 연관성, 가능한 설명, 인과 근거를 구분한다. 상관·전후 비교만으로 인과 효과를 확인했다고 평가하지 않는다.
- 자료가 부족하면 필요한 추가 로그·비교 집단·실험과 확인할 지표를 제안할 수 있다. 실행되지 않은 실험 결과를 근거로 사용하지 않는다.
- 합성 데이터의 생성 원인은 내부 검산·과제 설계 정보다. 그 원인이 공개 관측 자료에서 유일하게 식별되는지는 별도 검토하며, 식별 불가이면 원인 확정을 필수 조건으로 삼지 않는다.

도움 요청·힌트·중간 검토 이력을 함께 표시한다. 도움을 받아 개선한 최종 결과와 독립적으로 보여준 분석 행동을 구분하고, 이를 하나의 무보조 역량 점수로 표현하지 않는다. 사용자별 추천은 해당 사용자의 과제·평가 이력만 사용한다. 기존 사람의 의미적 품질 승인 절차는 유지한다.

### 6.6 데이터 신뢰성 점검 훈련

조회 도구의 구문·권한·검산과 별도로, 사용자가 데이터의 정의와 수집·관측 상태를 점검하도록 한다. 과제마다 공개 데이터 사전과 필요한 품질 정보를 제공한다. 공개 정보로 판단할 수 없는 품질 문제를 숨겨진 정답으로 요구하지 않는다.

| 점검 대상 | 학습자의 확인 행동 | 사례 |
| --- | --- | --- |
| 이벤트 정의·단위 | 이벤트가 무엇을 뜻하며 사용자/세션/도전 중 어떤 단위인지 확인 | 튜토리얼 시작과 완료, 재도전 중복 |
| 수집 누락·중복 | 버전·기간·기기별 수집 상태 또는 중복 여부 확인 | 업데이트 후 완료 이벤트 누락 가능성 |
| 시간·관측 가능성 | 시간대·날짜 경계·D7 관측 완료 여부 확인 | 아직 가입 후 7일이 지나지 않은 코호트 |
| 비교 집단·표본 | 분모·집단 구성·표본 수·제외 조건 확인 | 작은 집단의 비율 급변, 유입 구성 변화 |

대표 과제는 적어도 하나의 품질 점검 판단을 포함한다. 정상 데이터라면 정상임을 확인하는 근거를 설명하게 할 수 있으며 모든 과제에 결함을 인위적으로 넣을 필요는 없다. 결함 사례를 사용할 때는 사람이 검토한 고정 표본이나 기존 허용 범위의 데이터·공개 품질 정보를 활용한다.

가령 튜토리얼 완료율 하락에서 로그 수집 여부를 확인하지 못했다면 사용자는 실제 이탈 증가와 수집 누락을 구분할 수 없음을 설명하고 필요한 로그·수집 상태를 요청할 수 있다. 도구는 품질 조회를 수행할 수 있지만 사용자가 점검을 선택·해석한 행동과 에이전트가 먼저 알려준 내용을 구분해 기록한다.

## 7. 상태와 저장 계약

훈련 상태의 기본안은 `준비 중 → 추가 질문 필요 / 분석 중 → 보고 중 → 후속 질문 → 최종 평가 중 → 완료`다. `실패`, `중단`도 별도로 기록한다. 분석 중 조회는 `기준 확인 필요 → 실행 대기 → 실행 중 → 성공 / 실패` 상태를 갖는다. 사용자 입력 없이 단계가 반복되거나 평가 완료를 중복 처리하지 않는다.

| 저장 대상 | 주요 정보 |
| --- | --- |
| 사용자 | Discord 사용자 ID, 서버별 접근 권한, 학습 설정 |
| 훈련 연결 | session_id, owner_user_id, guild_id, channel_id, thread_id, 기존 request_id·attempt_id, 상태 |
| 과제 | 과제·데이터 버전, 공개 조건, 내부 검증 결과 |
| 대화 | 사용자 원문·도움 전 답변, 메시지·이벤트 ID, 역할, 시각, 도움 유형·수준·대상 역량 |
| 조회 | 자연어 원문, 확정 조건, SQL 버전, 실행 ID·상태·결과·제한·데이터 버전 |
| 보고·평가 | 보고 버전, 선택 근거 ID, 가설 수정·품질 점검·후속 답변, 최종 제출본, 공개 조건·평가 기준 버전·도움 이력 |
| 학습 상태 | 사용자별 역량 관찰·도움 전후 판단·기준/후속 과제 비교·추천과 변경 이력 |

서버 ID와 스레드 ID는 대화 연결 정보이며 소유권 검사를 대신하지 않는다. 학습 상태와 과제 접근은 매 요청에서 사용자 권한을 확인한다. 메시지를 수정해도 이미 실행한 조회와 제출본은 덮어쓰지 않고 새 요청·버전으로 처리한다.

프로세스 재시작 후 대화와 성공 조회를 복원한다. Discord 스레드가 보관되거나 삭제돼도 DB 기록을 자동 삭제하지 않는다. 접근 가능한 복구 공간을 안내하고 원래 기록과 연결한다. 기록 삭제·보관 기간과 관리자 접근 정책은 출시 전에 확정한다.

## 8. 기술 구성과 기존 기능 재사용

```text
Discord 사용자
    ↓
Discord Bot / 이벤트·명령 처리
    ↓
진행 제어와 소유권 검사
    ├─ 업무 담당자 / 멘토 / 리뷰어
    ├─ 자연어 조회 계약 → SQL 생성 → SQL 검사·실행
    └─ 보고·근거·사용자별 학습 상태
    ↓
기존 DA-Agent 기능 + 모델 API + PostgreSQL
```

기존 Python 모듈과 PostgreSQL을 재사용한다. 현재 설정·검증 경로인 Gemini를 초기 후보로 두되, 제공 모델 변경이나 자동 라우팅을 MVP 필수 작업으로 추가하지 않는다. Discord 토큰은 서버 환경에서 관리하고 메시지·로그에 노출하지 않는다.

### 8.1 재사용 분류와 추가 개발 범위

2026-10-06 현재 코드와 기존 검증 기록을 기준으로 분류한다. `거의 그대로 활용`은 핵심 처리 로직을 유지할 수 있다는 뜻이며 Discord 호출 연결과 실제 검증을 생략한다는 뜻이 아니다. `수정 후 재사용`은 저장·평가 계약이나 입력·소유권·진행 제어를 변경해야 한다. `신규 개발`은 기존 기반을 호출할 수 있어도 해당 제품 기능의 중심 로직을 새로 구현해야 한다.

| 기능군 | 재사용 판단 | 현재 기반 | 추가 작업 |

| Discord 연결·사용자 권한·역할 진행 | 신규 개발 | 기존 FastAPI·과제 기록을 내부 서비스 기반으로 활용 | Bot·이벤트·스레드·식별자 연결, 매 요청 소유권 검사, 역할별 상태 전환 |
| 교육용 도움 정책·성장 비교 | 신규 개발 | 기존 대화·힌트·평가·학습 관찰 기록을 활용 | 도움 유형·수준 계약, 독립적인 역량 관측, 기준/후속 과제 비교·자료 부족 판정 |

분류 합계는 12개 기능군 중 거의 그대로 활용 2개, 수정 후 재사용 7개, 신규 개발 3개다. 기능별 개발량·위험·검증 비용이 다르므로 이 수치를 재사용 코드 비율, 일정 절감률 또는 구현 진행률로 환산하지 않는다. 구현 진행도 표의 12개 작업과 기능군의 12개는 일대일 대응하지 않는다.

### 8.2 재사용의 핵심 제약

- SQL 실행은 이미 가능하지만 자연어 SQL 생성은 별도 기능이다. 기존 출제용 지표 검산도 모든 임의 조회의 의미 정확성을 보장하지 않는다. MVP는 기간 비교·집단별 집계·비율·공개 관계 조인을 우선 후보로 삼고 대표 과제에서 지원 연산·지표를 고정한다. 범위 밖 요청은 지원 한계를 안내한다.
- 실행 결과는 임시 메모리에 보관되는 경로와 영구 저장 경로가 구분되어 있다. 기존 save_execution 기능을 재사용하되 Discord의 성공 조회 자동 저장은 추가 연결해야 한다. 임시 실행 만료 후 근거가 사라지는 흐름을 방지한다.
- 코칭은 공개 정보와 출처 ID를 사용하는 기반이 있지만 역할별 응답과 수준별 도움 정책은 완성되어 있지 않다. 요청 확인에 분석 힌트가 포함되면 도움 이력으로 분류하는 로직도 추가한다.
- 평가와 학습 관찰에는 기존 항목 이름과 보고 입력 범위에 의존하는 코드가 있다. SQL 항목을 단순히 숨기거나 배점만 변경하지 않고 새 분석 항목·중간 대화 근거·도움 이력의 전체 연결을 검증한다.
- 학습 상태는 현재 공통 기록이며 추천은 공통 상태와 과제 목록을 참조한다. 사용자별 상태·이력·추천과 과제 소유권을 함께 분리해야 한다.
- 기존 요청/행동 ID의 중복 방지는 활용하되 Discord 이벤트 ID와 연결하고 중간 실패·재시작 시 일관성을 검증한다. 일부 대화 경로의 공통 잠금이 여러 사용자의 응답을 막지 않는지도 확인한다.
- 사용량·재시도 제한 기반이 있어도 Discord 사용자별 일별 한도와 비용 정책이 이미 구현된 것으로 보지 않는다. 공급자가 토큰을 보고하지 않은 경우와 단가 미확정도 구분해 기록한다.

## 9. Discord 운영과 실패 처리

Discord 명령·버튼 Interaction은 수신 후 3초 안에 최초 응답해야 하며 후속 응답 토큰은 15분 동안 유효하다. 출제·모델 호출에는 지연 응답을 사용하고, 장시간 작업은 저장된 상태와 과제 메시지로 완료 여부를 안내한다. [Discord 공식 응답 문서](https://github.com/discord/discord-api-docs/blob/main/developers/interactions/receiving-and-responding.mdx)

스레드는 부모 채널의 권한 영향을 받으며 스레드 발언 권한도 확인해야 한다. 전용 스레드라는 이유만으로 비공개라고 간주하지 않는다. MVP 기본안은 소유자·허용 운영자 중심의 제한된 과제 공간이며, 실제 서버의 권한·지원 조건을 확인하고 적용한다. 서버 관리자 접근 가능성도 사용자 안내에 포함한다. [Discord 공식 스레드 문서](https://github.com/discord/discord-api-docs/blob/main/developers/topics/threads.mdx), [권한 문서](https://github.com/discord/discord-api-docs/blob/main/developers/topics/permissions.mdx)

일반 메시지 수신에 필요한 Discord 설정·권한을 검증한다. 자연스러운 대화가 불가능한 환경에는 명령·버튼·입력창으로 같은 분석 요청을 제출하는 경로를 제공한다. 스레드 밖 대화나 다른 봇 메시지에는 훈련 응답을 자동 생성하지 않는다.

| 상황 | 기대 처리 |
| --- | --- |
| 정의가 모호함 | SQL 실행 전 선택지·확인 질문, 호출 근거 저장 |
| 지원하지 않는 데이터·분석 | 한계와 가능한 조회 안내, 없는 컬럼·결과 생성 금지 |
| 모델 오류·API 호출 제한 | 현재 단계 보존, 재시도 가능 여부·이유 안내 |
| SQL 차단·실행 실패·시간 초과 | 실패로 표시, 같은 의도의 제한된 수정 또는 사용자 안내 |
| 빈 결과·분모 0 | 해당 상태 표시, 원인이나 0% 결과로 임의 해석 금지 |
| 결과 제한 | 미리보기와 불완전 수집을 구분, 전체 결과라고 표시하지 않음 |
| 이벤트 재전송·버튼 중복 | 이벤트 ID로 중복 방지, 조회·평가·비용 중복 발생 방지 |
| 같은 과제의 동시 입력 | 확정 조회 조건과 보고 버전이 섞이지 않도록 순서 제어 |
| 권한 부족·스레드 접근 실패 | 기록 보존, 조치 가능한 안내와 복구 경로 제공 |
| 다른 사용자 요청 | DB 조회·변경 전에 소유권 차단 |
| 사용자별 사용 한도 초과 | 새 유료 작업 중단, 기록 열람과 재개 정보 유지 |

모델 호출 수·토큰·조회 실행·지연·재시도와 실패를 작업별·사용자별로 기록한다. 단가를 확인할 수 없으면 비용을 0원이라고 보고하지 않는다. 호출 한도와 알림 기준은 13절에서 결정하며 무제한 호출을 기본 운영 정책으로 두지 않는다.

## 10. 후속 SQL 연습

명령 예시는 `/sql연습`이다. 자연어 분석 모드와 시작 시점부터 구분하고 다음 흐름을 제공한다.

1. 사용자가 주제·난이도를 고르거나 완료한 분석에서 SQL 연습을 요청한다.
2. 에이전트가 필요한 데이터 사전·지표 정의·분모·관측 기간과 쿼리 작성 과제를 제공한다.
3. 사용자가 직접 SQL을 제출한다. 제출 전 정답 SQL을 자동 생성해 공개하지 않는다.
4. 기존 검사·실행 기능으로 실제 결과를 제공하고 오류 수정·재제출을 지원한다.
5. 구문·계산 의미·중복·기간·분모를 평가하며 동등한 결과를 내는 타당한 다른 쿼리를 인정한다.

예를 들어 D7 과제라면 관측 완료 신규 가입 코호트의 D7 리텐션을 계산하는 문제로 정의한다. 주간 재방문율을 연습한다면 그것이 D7과 다른 보조 지표임을 명시한다. 이전 대화형 분석에서 SQL을 열람했는지 기록하고, 같은 쿼리의 재현을 독립적인 SQL 역량 증거로 단정하지 않는다.

SQL 연습의 상세 평가·입력 UX·완료 기준은 별도 Spec에서 정한다. Discord MVP 출시 조건에는 포함하지 않는다.

## 11. 검증과 출시 완료 기준

자동 검증에서는 자연어 요청 → 확정 조건 → SQL → 실제 결과의 연결을 기준 데이터로 확인한다. 최소 사례는 모호한 비율, 고유 사용자와 이벤트 수, 조인 중복, 날짜 경계, D7 관측 미완료, 분모 0, 빈 결과, 없는 컬럼, 권한 차단, 실행 제한, 모델 실패와 중복 이벤트다. 구문 검사만 통과한 SQL을 정확한 분석으로 인정하지 않는다.

교육 검증에서는 다음 표본을 대표 과제 계약에 연결해 준비한다. 적용 조건과 예상 판정을 고정하고 실제 응답·저장 기록을 대조한다. 자동 확인과 사람의 의미 검토 결과를 구분한다.

- 같은 모호한 질문에 대해 초급은 안내를 받고, 중급·고급은 먼저 자신의 정의를 답하며 이후 요청 시 도움을 받는 사례.
- 중립적인 요청 확인과 정답 방향을 알려주는 선택지가 다른 도움 유형으로 기록되는 사례.
- 초기 가설을 타당하게 기각·수정한 답, 다른 타당한 결론, 합리적인 판단 보류를 인정하는 사례.
- 같은 사실과 근거를 다른 문체로 보고해도 판정이 유지되는 사례와, 집단 차이를 인과로 단정해 공개 핵심 오류로 판정되는 사례.
- 데이터 품질이 확인된 사례와 공개 정보만으로 수집 누락 가능성을 해소할 수 없어 추가 확인을 제안하는 사례.
- 시스템 실행 실패 때문에 확인할 수 없는 근거를 사용자 오류로 감점하지 않는 사례.

실제 Discord에서는 다음을 확인하고 결과를 `tests/reports/`에 기록한다.

- 사용자 A가 시작 → 자연어 조회 → 기준 확인 → 결과 비교 → 도움 요청 → 보고 → 후속 답변 → 최종 평가까지 웹 이동 없이 완료.
- 사용자 B가 별도 과제를 수행하고 A의 기록·근거·학습 상태가 섞이지 않음. B가 A의 조작 경로를 사용해도 차단됨.
- 재시작·중단 후 조회 근거와 보고 초안을 복원하고, 스레드 접근 실패를 안내.
- 중복 입력·버튼·API 실패·빈 결과·결과 제한에서 실제 메시지와 DB 상태가 일치.
- 학습자가 역할의 차이, 조회 기준, 표시 제한과 피드백을 이해할 수 있는지 확인.
- 대표 게임 과제의 교육 완료 기준을 사람이 검토하고, 평가가 중간 분석 행동과 최종 보고의 실제 근거를 인용하는지 확인.
- 기준 과제와 유사한 새 과제에서 도움 전 답변·오류·가설 검토 행동을 수집하고 비교할 수 있는지 확인. 데이터가 부족하면 성장 판정을 유보하는지 확인.

출시 완료는 위 핵심 흐름·오류·소유권 검증과 사람의 과제·피드백 품질 검토를 모두 통과했을 때로 정의한다. 기존 웹 브라우저 검증을 Discord 검증으로 대체하지 않는다. 실제 서버 확인이 제한되면 미확인 항목과 필요한 사용자 확인 행동을 보고하고 해당 작업을 `검증 대기`로 유지한다.

기능 출시 검증과 학습 효과 검증은 분리한다. 파일럿에서는 성장 관측 경로와 판정의 타당성을 확인하되 작은 표본에서 교육 효과가 입증됐다고 주장하지 않는다. 완료 기록만으로 교육 목표 달성을 선언하지 않고 과제별 기준 충족·미충족·판정 보류를 표시한다.

### 12.1 학습 성장 관측

첫 과제를 기준 관측으로 삼고, 같은 역량·유사한 난이도를 요구하되 상황·데이터·수치가 다른 새 과제로 후속 관측한다. 처음부터 숫자만 바꾼 동일 문제로 전이를 판단하지 않는다. 관측 시점, 적용 평가 조건, 도움 수준, SQL 열람·힌트 이력과 근거를 보존한다. 과제의 비교 가능성은 사람이 검토한다.

무보조 관측은 관련 도움을 제공하기 전 답변·행동을 대상으로 한다. 도움 요청을 막지 않으며 도움 이후 결과는 별도 표시한다. 난이도·도움·평가 조건이 달라 직접 비교하기 어려우면 점수 차이를 성장으로 해석하지 않는다.

지표는 평가 가능한 항목·관측 기회만 분모로 사용하고 실제 건수를 함께 표시한다. 시스템 실패, 과제에 해당 조건이 없음, 미응답 등 제외 사유를 별도로 보고한다. 증거가 부족하면 `성장 판단 자료 부족`으로 표시하고 완료율로 보충하지 않는다.

추천은 확인된 취약점과 도움 이력에 연결한다. 독립적인 기준 정의가 어려웠다면 지표 정의 연습, 품질 점검을 놓쳤다면 이벤트·관측 점검, 인과 단정이 반복됐다면 대안 설명·검증 설계 과제를 제안한다. 추천에는 해당 사용자의 관측 근거와 아직 확인되지 않은 역량을 구분해 표시한다.

개발 전에 대표 과제의 공개 교육·평가 계약과 도움 정책을 고정한다. 구현은 사용자별 기록과 과제 연결 → Discord 시작·전용 공간 → 기준 확인과 자연어 조회 → 실제 결과·근거 → 역할별 보고·평가 → 성장 관측과 실제 Discord 검증 순서로 진행한다. 처음부터 여러 과제와 역할을 늘리기보다 과제 하나의 전체 흐름을 확인한다. 기존 데이터 검산은 첫 구현부터 유지하고 추가 AI 검토자는 이후 필요에 따라 도입한다.
