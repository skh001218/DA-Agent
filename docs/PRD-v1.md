주니어 게임 데이터 분석가가 가상 RPG의 데이터를 직접 분석하고, 근거에 기반한 피드백을 받는 훈련 도구를 만든다. MVP는 문제 1(신규 유저 이탈률 계산)의 훈련 흐름과 피드백 품질에 집중한다. 문제 2·3은 MVP 구현 진행도가 80% 이상이 되면 착수하는 콘텐츠 확장으로 분리한다. 이 문서는 제품 목적, MVP 요구사항, 데이터와 평가 기준, 출시 검증 조건을 정의한다.

확장 아이디어는 [향후 확장 계획](future-roadmap.md)에 별도로 보관한다. 해당 문서의 항목은 1차 구현 범위나 출시 약속이 아니다. 수치 목표는 초기 제안이며 구현과 파일럿 결과로 조정한다. 기술 구성은 13절과 연결 명세에서 확정한 방향을 따르고 실제 동작은 구현 후 검증한다.

## 1. 해결하려는 문제

SQL 문법을 배워도 모호한 업무 요청을 지표로 정의하고, 비교 대상을 고르고, 결과를 해석하는 경험은 부족할 수 있다. 정답 쿼리만 보여주는 학습 방식으로는 분석의 분모, 관측 기간, 세그먼트, 대안 설명을 충분히 연습하기 어렵다.

사용자가 분석을 수행하고 에이전트가 다음 판단을 돕도록 한다. 제품의 핵심 가치는 문제의 개수보다 실제 결과를 근거로 제공하는 피드백의 품질이다.

## 2. 대상 사용자와 학습 목표

대상은 기본 SELECT, JOIN, GROUP BY를 사용할 수 있고 게임 데이터 분석 직무를 준비하는 학습자다. SQL 입문 강의 전체를 대체하지 않는다.

한 번의 훈련을 마친 사용자는 다음을 수행할 수 있어야 한다.

- 업무 요청을 대상 유저, 기간, 지표, 비교 기준으로 구체화한다.
- 가설을 세우고 검증에 필요한 테이블과 세그먼트를 선택한다.
- 유저 단위 중복과 관측 기간을 고려해 SQL을 작성한다.
- 결과 수치를 근거로 발견사항을 설명하고 상관관계와 인과 주장을 구분한다.
- 결론의 한계와 다음 분석 또는 실행 제안을 작성한다.

운영 가정은 로컬에서 한 명의 학습자가 사용하는 웹 인터페이스다. 웹 화면은 훈련 에이전트를 이용하는 첫 번째 인터페이스이며, 향후 디스코드 봇에서도 같은 문제 출제, 코칭, 평가 기능을 활용할 수 있도록 설계한다. 디스코드 봇 구현은 MVP 이후 범위다. 현재 프로토타입의 LLM 연결은 Gemini API를 사용한다. 제품 자체의 다중 사용자 회원 시스템, 결제, 외부 공개 배포는 이후 범위다. MVP는 문제 1의 기초 계산을 다루고, 문제 2·3 확장에서 중간 수준의 원인 탐색을 추가하며 Advanced 업무 요청은 보류한다.

## 4. 사용자 흐름

1. 문제 목록에서 학습 목표와 난이도를 확인하고 시작한다.
2. 상황을 읽고 분석 대상, 기간, 지표, 비교 기준을 작성한다.
3. 가설과 필요한 데이터를 선택한다.
4. 스키마를 탐색하고 SQL을 실행한다.
5. 결과를 해석하고 필요하면 가설과 SQL을 수정한다.
6. 발견사항, 결과 근거, 한계, 다음 분석과 액션을 제출한다.
7. 리뷰를 읽고 보고서를 수정하거나 해설을 확인한다.

단계는 사고를 돕는 안내로 사용한다. 이전 단계 수정과 추가 쿼리 실행을 허용하며, 에이전트의 동의를 얻어야 다음 단계로 넘어가는 구조는 만들지 않는다.

## 6. 고정 훈련 시나리오

문제 1은 MVP 필수 콘텐츠다. 문제 2·3의 아래 정의는 확장 방향으로 보존하며 MVP 출시의 필수 조건은 아니다. MVP 구현 진행도가 80% 이상이 되면 데이터 기간·규모·생성 조건과 평가 기준을 확정하고 구현에 착수한다. 확장을 시작해도 MVP의 남은 검증과 파일럿을 중단하지 않는다.

아래 사건은 데이터 생성용 설정이다. 학습자에게는 상황과 지표 정의만 공개하고 원인과 기대 발견사항은 별도 평가 자료에 둔다. 각 시나리오는 동일한 가상 RPG의 공통 표 구조를 재사용하되 문제별 필요한 표를 선언한다. 고정 seed·생성기 버전과 검증된 데이터 스냅샷을 보존한다. 이후 문제 유형·데이터 상황을 바꾸는 변형을 추가하며, 숫자만 바꾸는 반복 연습과 새로운 분석 목표를 구분한다.

| --- | --- | --- |
| 1. 신규 유저 이탈률 계산 | 지정된 가입 기간의 신규 유저 중 가입 다음 날부터 7일 동안 한 번도 재접속하지 않은 유저의 비율을 구하세요. | 가입 코호트, 유저 중복 제거, 재접속 여부, 분모와 관측 시간 |
| 2. 튜토리얼 완료율 감소 분석 | 업데이트 전후 신규 유저 튜토리얼 완료율이 낮아졌습니다. 어떤 유저와 단계에서 변화가 큰지 분석하세요. | 플랫폼과 가입 버전 비교, 단계별 이탈, 유입 구성 변화 확인 |
| 3. D7 리텐션 하락 분석 | 업데이트 이후 신규 유저 D7 리텐션이 하락했습니다. 관련 현상과 추가 확인할 사항을 보고하세요. | D7 관측 가능 코호트, 날짜 단위 재방문, 퍼널과 리텐션의 관계, 인과 주장 제한 |

문제 1은 정해진 정의로 신규 유저 이탈률을 정확히 계산하는 문제다. 게임뿐 아니라 다른 서비스에서도 발생하는 문제를 훈련하려는 사용자의 선택을 반영한다. 세부 조건은 [문제 1 지표·관측 조건 명세](../specs/001-new-user-churn.md)를 따른다. 문제 2는 업데이트 후 Android 신규 유저의 튜토리얼 4단계 성공 확률을 낮추는 사건을 설정한다. 유입 채널 구성 변화도 함께 넣어 전체 평균만으로 결론을 내리기 어렵게 한다.

문제 3은 동일 계열의 튜토리얼 변화와 재방문 확률 변화를 설정한다. 튜토리얼 미완료 유저의 낮은 리텐션은 관련성을 보여주는 근거다. 완료 유저와 미완료 유저는 원래 성향이 다를 수 있으므로 그 비교만으로 난이도 변경의 인과 효과를 입증했다고 평가하지 않는다.

각 문제는 직접 실행한 기준 쿼리와 데이터 검증을 통과한 후 공개한다. 표시할 변화 수치는 생성과 검증 이후 확정하며, 임의의 감소율을 먼저 정답으로 고정하지 않는다.

## 7. 데이터와 지표 정의

학습 목표와 문제를 먼저 정하고 아래 최소 테이블을 설계한다. MVP는 users·sessions를 사용하고 tutorial_attempts는 문제 2·3 확장 시 추가한다. 아래 튜토리얼·D7 지표 정의는 확장 시 사용할 기준으로 보존한다. 경제, 구매, 성장, 일반 전투 전체 로그는 MVP에 추가하지 않는다.

| 테이블 | 행 단위 | 최소 컬럼 |
| --- | --- | --- |
| users | 유저 1명 | user_id, signup_at, platform, country, acquisition_channel, signup_app_version |
| sessions | 접속 세션 1회 | session_id, user_id, login_at, logout_at, app_version |
| tutorial_attempts | 튜토리얼 단계 시도 1회 | attempt_id, session_id, user_id, step_id, started_at, ended_at, result |

튜토리얼 시도의 버전은 연결된 세션에서 확인한다. 업데이트 전후 코호트 구분에는 가입 시 버전을 사용하고, 세션 버전과 혼동하지 않도록 데이터 사전에 설명한다. 실패와 재시도를 기록하고 최종 단계 성공을 튜토리얼 완료로 정의한다.

- 날짜 기준은 Asia/Seoul로 통일한다. 저장 형식과 날짜 변환 방법을 SQL 환경 안내에 명시한다.
- 가입일을 D0으로 정의한다. D7은 가입일에서 7일 뒤의 달력 날짜에 로그인 세션이 한 번 이상 있는 유저의 비율이다.
- 문제 1의 신규 유저 이탈률은 D1~D7에 로그인 세션이 없는 고유 유저 수 / 같은 기간을 온전히 관측한 가입 코호트의 고유 유저 수다. 관측 구간은 Asia/Seoul 기준 D1 00:00 이상, D8 00:00 미만이며 수집 완료 경계가 D8 00:00 이상인 유저만 포함한다. D0 접속은 재접속으로 세지 않고, 기간 내 접속 횟수와 관계없이 한 명으로 집계한다. D7 당일 미접속 비율과 구분한다.
- 데이터 종료일 전체가 수집되었다는 가정 아래, 가입일 + 7일이 종료일 이하인 유저만 D7 분모에 포함한다. 한 유저가 여러 번 접속해도 분자는 1명이다.
- 튜토리얼 완료율은 가입 후 24시간 이내 최종 단계에 성공한 고유 유저 수 / 가입 코호트의 고유 유저 수다. 가입 후 24시간이 온전히 관측된 유저만 포함한다.
- 단계별 도달률은 24시간 이내 해당 단계에 시도한 고유 유저 수 / 같은 가입 코호트 유저 수다. 단계 간 전환율은 직전 단계 도달자를 분모로 사용하며 별도 이름으로 표시한다.
- 가입 기간은 시작 이상, 종료 미만으로 표현한다. 분모가 0인 결과는 계산 불가로 표시한다.
- 완료율 60%에서 48%로의 변화는 12%p 하락이며 상대 감소율은 20%다. 두 표현을 구분한다.

데이터 종료 시각과 관측 기준은 문제 화면에서 확인할 수 있어야 한다. 초기 생성 규모는 문제당 유저 수천 명 수준으로 시작하며, 이벤트 수는 품질 검증 후 조정한다.

## 8. 데이터 품질과 정답 자료

데이터 생성은 확률과 조건을 설정한 코드로 수행하고 LLM이 행과 결과 수치를 즉석에서 만들어 제공하지 않는다.

공개 자료에는 학습 DB, 스키마, 데이터 사전, 시나리오 상황, 가입 범위와 수집 완료 경계를 포함한다. 비공개 평가 자료에는 생성 사건, 기준 쿼리, 검증된 결과, 기대 발견사항, 허용 가능한 대안 분석, 힌트, 평가 기준을 포함한다. 공개 데이터·문제·비공개 평가 자료는 하나의 훈련 패키지로 묶으며 동일한 package_id와 배포 버전을 사용한다. 데이터·문제·평가 자료의 버전을 일치시키고 파일 해시와 기준 결과를 검증한 패키지만 출제한다. 세부 스키마와 연결 정보는 [학습 데이터·패키지 명세](../specs/002-training-data-packages.md)를 따른다.

공개 전 확인할 조건은 다음과 같다. 튜토리얼과 문제 2·3 전용 조건은 해당 확장 콘텐츠를 공개할 때 적용하며 MVP 문제 1의 출시를 막는 조건으로 사용하지 않는다.

- 기본 키의 유일성, 외래 키 관계, 가입 이후 접속, 시작 이전 종료 없음, 단계 순서와 재시도 일관성.
- 같은 seed와 버전에서 같은 데이터와 기준 결과 재현.
- 문제 2의 Android 4단계 변화와 유입 구성 변화가 충분한 표본에서 관측됨.
- 문제 3의 D7 하락과 관측 미완료 유저가 데이터에 존재하며, 미완료 유저 제외 후에도 설정한 현상을 확인할 수 있음.
- 기준 결과에 코호트별 분모와 분자가 포함되고 학습자가 공개 테이블만으로 재계산할 수 있음.
- 문제 1은 D0 접속만 있는 유저, D1~D7 재접속자, 경계 시각의 접속, 관측 미완료 유저, 반복 접속, 분모 0 사례를 기준 쿼리로 검증함.

생성 과정에서 알고 있는 원인과 관측 데이터가 지지하는 결론의 강도를 구분한다. 유일한 정답 문장이나 기준 SQL과의 문자열 일치로 평가하지 않는다.

## 9. SQL 실행과 코칭 요구사항

| 구분 | 요구사항 |
| --- | --- |
| 실제 계산 | SQL은 DB에서 실행하고 결과와 오류를 그대로 전달한다. 실행하지 않은 수치를 결과로 제시하지 않는다. |
| 조회 제한 | 학습자는 공개 테이블에 대한 읽기 전용 조회만 할 수 있다. 쓰기, 외부 파일 접근, 확장 기능 실행은 차단한다. |
| 결과 관리 | 실행과 저장을 분리하고 사용자가 선택한 실행만 SQL·결과·버전·상태와 함께 저장한다. 미저장 실행은 현재 화면에서만 유지한다. 잘린 미리보기와 전체 결과 건수를 구분한다. |
| 실행 제한 | 초기 제안은 쿼리당 5초, 결과 미리보기 200행이다. 제한 초과 시 원인을 알리고 입력을 유지한다. |
| 코칭 근거 | 현재 단계, 사용자 입력, 공개 스키마, 사용자의 실행 결과, 힌트 이력을 바탕으로 피드백한다. |
| 오류 분류 | 문법 오류는 문법 안내, 중복 집계는 집계 단위 안내, 방향 혼란은 비교 기준 안내로 구분한다. |
| 장애 대응 | LLM 연결 실패 시에도 SQL 실행, 입력 저장, 고정 힌트 사용이 가능하다. 리뷰는 재시도 상태로 남긴다. |

정상 SQL 실행은 분석이 올바르다는 뜻이 아니다. SQL 검증은 결과와 집계 정의를 확인하고, LLM은 가설, 해석, 한계, 액션의 적절성을 검토한다. 임의 SQL의 의미를 완벽히 자동 판정할 수 있다고 약속하지 않는다.

## 10. 힌트와 해설 정책

에이전트는 처음부터 전체 해답을 제공하지 않고, 사용자의 시도에서 막힌 부분을 짚어 한 가지 다음 행동을 제안한다. 질문만 반복하거나 이미 확인한 내용을 다시 요구하지 않는다.

| 수준 | 제공 내용 | 예시 |
| --- | --- | --- |
| 방향 | 비교 관점 | 전체 평균 변화가 모든 플랫폼에서 동일한가요? |
| 지표 | 확인할 집계 | 플랫폼과 가입 버전별 4단계 도달률과 완료율을 비교해보세요. |
| SQL 구조 | 필요한 집계 구조와 부분 예시 | 유저별 완료 여부를 먼저 만든 뒤 코호트별로 집계하는 CTE 구조를 안내한다. |

사용자는 힌트 수준을 직접 선택할 수 있다. 실패 횟수만으로 힌트를 강제로 높이지 않는다. 정답 요청에는 다음 힌트를 제안하되, 명시적으로 해설 보기를 선택하면 기준 SQL과 해설을 공개한다. 해당 시도는 해설 참조로 기록하며 힌트 사용 자체를 일률적으로 감점하지 않는다.

일반 코칭 입력에는 숨겨진 원인과 기준 SQL 전체를 넣지 않는다. 최종 리뷰는 별도 평가 경로에서 비공개 자료를 참조할 수 있으며, 전체 해설은 해설 보기 이후에만 제공한다. 사용자 입력이 내부 자료 공개를 요구해도 일반 코칭 경로에서 공개되지 않아야 한다.

## 11. 최종 보고와 평가

최종 보고는 문제 정의, 가설 및 접근, 주요 발견, 실행 결과 근거, 결론의 한계, 추가 분석 및 액션으로 구성한다. 사용자는 중요한 주장마다 실행 결과를 연결한다.

| 평가 항목 | 배점 | 판단 기준 |
| --- | --- | --- |
| 문제 정의 | 25 | 대상, 기간, 분모, 지표, 비교 기준이 명확하고 관측 조건을 고려했는가 |
| 분석 접근 | 25 | 가설과 데이터 선택이 연결되고 세그먼트와 대안 설명을 확인했는가 |
| SQL 정확성 | 20 | 실행 결과가 정의에 맞고 중복, 재시도, 날짜와 관측 기간을 처리했는가 |
| 결과 해석 | 20 | 실제 결과를 정확히 인용하고 상대 변화와 %p, 관련성과 인과를 구분했는가 |
| 추가 분석과 액션 | 10 | 발견에 연결된 확인 방법과 실행 제안을 제시했는가 |

각 항목은 0~4 수준으로 평가하고 항목 점수는 배점 × 수준 / 4로 계산한다. 소수점은 총점을 합산한 뒤 한 자리로 표시한다.

| 수준 | 공통 의미 |
| --- | --- |
| 0 | 제출 내용이 없거나 평가할 근거가 없음 |
| 1 | 시도했으나 핵심 오류로 주장을 지지하기 어려움 |
| 2 | 일부 근거가 있으나 중요한 조건이나 검증이 빠짐 |
| 3 | 핵심 기준을 충족하며 제한적인 보완이 필요함 |
| 4 | 핵심 기준과 관련 한계를 근거로 설명함 |

시나리오별 명세에서 이 수준을 구체적인 제출 예시로 보완한다. 다른 쿼리와 결론도 공개 데이터의 근거가 적절하면 인정한다. 기준 쿼리의 결과와 다를 때는 정의 차이와 실제 오류를 구분한다.

리뷰는 항목별 수준과 이유, 잘한 점, 놓친 점, 다음 단계로 구성하며 제출 문장 또는 실행 결과를 근거로 연결한다. 검증할 근거가 부족하면 그 사실을 표시하고 추측한 오류를 확정적으로 지적하지 않는다. 점수는 학습 안내용이며 채용 역량 인증으로 사용하지 않는다.

## 12. 기록과 재개

훈련 시도별로 패키지 ID·배포 버전·데이터셋 ID·문제 ID, 단계별 입력, 가설 수정, 사용자가 선택 저장한 SQL 실행 기록, 힌트 수준, 해설 공개 여부, 보고서 버전, 리뷰를 저장한다. 시작 시 콘텐츠 버전을 고정하고 SQL 결과·보고서·리뷰에 같은 연결 정보를 사용한다. 새로고침 후 같은 시도를 이어갈 수 있어야 한다. 새 콘텐츠 버전이 배포되어도 기존 시도는 원래 자료로 재개하며 최신 자료로 자동 교체하지 않는다. 배포된 콘텐츠는 덮어쓰지 않고 변경 시 데이터·문제·평가 자료의 배포 버전을 함께 올려 다시 검증한다.

서술 초안은 자동 저장하지만 SQL 편집기·미저장 실행 결과는 제외한다. SQL·결과는 실행별 저장 선택 후에만 영구 기록으로 남긴다. 미저장 실행은 새로고침 후 복구하지 않으며 로그·코칭 이력으로 우회 저장하지 않는다. 보고서 근거로 연결할 실행은 먼저 명시적으로 저장해야 한다. 세부 입출력과 저장 경계는 [훈련 기록 명세](../specs/003-training-record-contracts.md)를 따른다.

수정 보고서는 이전 버전과 별도로 저장하고 기존 리뷰를 덮어쓰지 않는다. 코칭 규칙과 평가 기준의 버전도 기록해 같은 제출물의 리뷰 차이를 추적한다. 저장 실패는 사용자에게 알려 저장되지 않은 입력이 사라지지 않도록 한다.

## 13. 확정 기술 구성

웹 화면은 HTML·CSS·JavaScript, 처리 서버는 Python + FastAPI, DB 연결은 Psycopg 3를 사용한다. 학습 데이터와 학습 기록은 별도의 PostgreSQL DB에 둔다. 웹 서버와 PostgreSQL은 Docker Compose로 실행하고 Git으로 코드·실행 설정을 관리한다. 학습자 SQL 연결은 공개 데이터에만 접근하는 전용 최소 권한 계정과 읽기 전용 트랜잭션을 사용한다. 실행·인증·이식성 검증 조건은 [기술 구성 명세](../specs/004-local-technology-stack.md)를 따른다.

현재 프로토타입의 AI 코칭·리뷰는 사용자가 선택한 Gemini API 경로를 사용하며 모델 기본값은 `gemini-3.5-flash-lite`다. 3.8 Flash에서 실제 코칭·리뷰 완료를 확인한 뒤 모델을 변경했고, 현재 모델에서는 코칭 완료만 확인했다. 모델별 실제 리뷰와 평가 품질 검증을 구분한다. API 사용 설정은 [Gemini 안내](gemini-setup.md)를 따른다. 기존 Sign in with ChatGPT·Responses API 어댑터는 보존하지만 실제 계정의 조직 앱 접근 거부는 미해결이다. 제공자 간 자동 전환은 하지 않으며, AI 연결 실패에도 SQL·선택 저장·보고서·고정 힌트는 유지한다.

문제 출제, 힌트, 코칭, 평가, 훈련 기록을 처리하는 핵심 기능은 웹 화면과 분리한다. 웹 인터페이스와 향후 디스코드 봇은 이 공통 기능을 호출하고, 각 환경에 맞게 입력을 받거나 결과를 표시한다. 시나리오, 지표 정의, 평가 기준은 인터페이스별로 중복 구현하지 않는다. 첫 버전에서 디스코드 연동 코드를 미리 구현할 필요는 없지만, 핵심 기능이 웹 화면의 상태나 브라우저에 직접 의존하지 않도록 한다.

학습 DB에는 정답과 루브릭을 넣지 않는다. 비공개 평가는 서버에서 읽고 API 응답과 클라이언트 번들에 원문이 포함되지 않게 한다. 로컬 파일에 접근하는 프로젝트 소유자에게 비밀을 완전히 숨기는 것은 목표가 아니며, 제품 사용 경로에서의 해답 노출을 방지한다.

Gemini API 키는 로컬 비밀 파일과 Compose secret으로 서버에 전달하며 Git·브라우저 저장소·학습 기록·일반 로그에 넣지 않는다. 기존 OAuth 경로의 인증 정보는 보호된 별도 인증 저장소에서 관리한다. 새 PC는 해당 환경에서 선택한 제공자의 연결 정보를 설정한다. 리뷰 요청에는 필요한 결과만 전달하고, 전체 이벤트 로그를 매번 보내지 않는다. 사용자의 요청 시에만 AI를 호출한다.

## 15. 파일럿과 성공 지표

초기 파일럿은 대상 학습자 5명으로 제안한다. 수치 목표는 제품 효과가 입증된 사실이 아니라 검증을 위한 가설이다.

참가자 코드와 훈련 연결, 도움 여부·중단 지점·다음 수정 행동·사람 판정 기록, 최초·수정 보고서 비교와 내보내기는 Spec 005에서 구현했다. 실제 학습자 파일럿은 미실행이다. 화면 검증용 참가자 기록은 실제 참가자로 집계하지 않도록 검증 후 정리했다.

- 5명 중 4명 이상이 개발자의 직접 개입 없이 문제 하나를 시작부터 리뷰까지 완료한다.
- 같은 4명 이상이 리뷰에서 수정할 다음 행동을 한 가지 이상 구체적으로 설명한다.
- 사람의 전후 보고서 검토에서 과반이 최초 제출 때 놓친 핵심 조건을 수정 보고서에 반영한다.
- 오류 발생, 중단 단계, 힌트 수준, 해설 사용을 기록해 막히는 구간을 찾는다.

완료율이나 점수 상승만으로 학습 효과를 확정하지 않는다. 해설 참조와 독립 수행을 구분하고, 서로 다른 문제 사이의 학습 전이는 이후 검증한다.

## 16. 구현 순서와 남은 결정

1. MVP 필수 콘텐츠를 문제 1로 한정하고 지표 정의를 확정한다.
2. 최소 스키마, 생성기, 고정 데이터, 기준 쿼리와 품질 검증을 만든다.
3. SQL 실행, 데이터 탐색, 기록과 재개를 구현한다.
4. 단계별 입력, 고정 힌트, LLM 코칭을 연결한다.
5. 최종 보고, 평가 자료, 시니어 리뷰를 구현한다.
6. 핵심 흐름과 평가 표본을 검증하고 파일럿을 진행한다.
7. MVP 구현 진행도가 80% 이상이 되면 문제 2·3 확장을 시작하고, 남은 MVP 작업을 병행한다.

현재 문제 1은 위 순서의 1~5단계를 구현했고, 6단계의 핵심 흐름 확인까지 진행했다. 평가 표본·파일럿은 남아 있으며 문제 2·3은 별도 콘텐츠 구현이 필요하다. 기술 구성은 Docker Compose, HTML·CSS·JavaScript, Python + FastAPI, PostgreSQL 학습·기록 DB, Psycopg 3와 Gemini API를 사용한다. 검증 환경은 Python 3.12.10·PostgreSQL 17.4이며 Python 의존성은 requirements.lock.txt에 고정했다. 문제 1의 초기 표본은 패키지당 200명, 결과 미리보기는 200행, 선택 저장은 1,000행/1MiB, 임시 실행은 10분/최대 100개로 구현했다.

MVP에서 남은 결정은 평가 검증을 거친 모델 사용 기준이다. 문제 2·3의 데이터 기간·규모·생성 조건과 기준 자료는 80% 기준 충족 후 확장 착수 시 결정한다. 다른 PC 실행·현재 모델 리뷰·평가 품질은 추가 검증한다. 다중 사용자나 공개 서비스가 필요해지는 경우 운영 범위를 다시 정의한다. 자동 시나리오 생성은 검증된 고정 문제를 확보한 뒤 별도 PRD로 다룬다.

### 16.1 MVP 구현 진행도와 확장 착수 기준

2026-10-03 사용자 결정: MVP를 먼저 최대한 달성하고, 구현 진행도가 80% 이상이 되면 문제 2·3을 추가한다. 80%는 확장 착수 기준이며 MVP 출시 완료를 의미하지 않는다.

- 계산: 완료 작업 수 / 전체 MVP 구현 작업 수 × 100. 아래 10개 작업 중 8개 이상 완료하면 확장에 착수한다.
- 완료 판정: 구현과 해당 완료 조건의 검증을 모두 마친 작업만 센다. 화면 기능은 실제 동작 확인을 포함한다. 구현만 끝난 작업은 검증 대기로 두며 문서 작성만으로 진행도를 올리지 않는다.
- 분모: 아래 문제 1 중심의 구현 작업 10개로 고정한다. 문제 2·3과 다른 후속 확장은 분모에 넣지 않는다. 작업 범위 변경 시 변경 이유와 새 분모를 기록하고 진행도를 재계산한다.
- 출시 검증: 평가 품질, 다른 PC 실행과 파일럿은 14·15절에 따라 별도로 추적한다. 구현 진행도 80%만으로 이 검증을 완료 처리하지 않는다.
- 현재 진행도: 산정 전. 아래 작업별 코드와 기존 검증 결과를 대조해 상태와 근거를 기록한 뒤 첫 수치를 확정한다. 이번 문서 변경만으로 80% 달성을 선언하지 않는다.

각 작업의 상태와 검증 근거를 갱신할 때 완료 작업 수, 백분율, 마지막 갱신일과 남은 작업을 함께 기록한다. 기준 충족 전에는 문제 1 MVP를 우선하며, 충족 후 문제 2·3용 Spec과 검증된 콘텐츠 패키지를 추가한다.

## 17. 향후 디스코드 봇 활용

MVP의 훈련 흐름과 평가 품질을 확인한 뒤, 디스코드에서 문제를 받고 분석 과정과 결과를 제출하며 코칭·평가를 받는 사용 방식을 추가한다. 별도 웹 화면을 열지 않고도 대화 중심으로 훈련할 수 있게 하는 것이 목적이다. 이 항목은 향후 확장 방향이며 1차 출시 검증 조건에 포함하지 않는다.

| 훈련 기능 | 디스코드에서의 활용 방향 |
| --- | --- |
| 문제 출제 | 문제 목록에서 선택하거나 문제를 요청해 상황, 학습 목표, 데이터 안내를 받는다. |
| 단계별 코칭 | 문제 정의, 가설, 분석 접근을 대화로 제출하고 다음 분석 행동을 안내받는다. |
| 힌트 | 기존의 방향, 지표, SQL 구조 수준을 선택해 도움을 받는다. |
| 분석 결과 제출 | SQL, 실행 결과, 해석을 메시지나 파일로 제출하고 주요 주장에 결과 근거를 연결한다. |
| 최종 평가 | 발견사항, 근거, 한계, 다음 액션을 제출하고 공통 평가 기준에 따른 리뷰를 받는다. |
| 기록과 재개 | 학습자와 훈련 시도를 구분해 이전 대화와 제출 기록을 바탕으로 이어서 훈련한다. |

봇 구현 전에는 SQL을 봇을 통해 실제 DB에서 실행할지, 사용자가 외부 분석 도구에서 실행한 결과를 제출할지 결정한다. 외부 결과를 받는 경우 Agent가 직접 실행·검증한 결과와 구분하고, 검증하지 못한 수치를 확정적으로 승인하지 않는다.

디스코드 사용자와 훈련 기록의 연결 방식, DM 또는 서버 내 전용 대화 공간의 사용 방식, 제출 자료와 리뷰의 공개 범위, 봇 운영 환경과 호출 비용은 연동 설계 단계에서 결정한다. 웹과 디스코드 사이의 기록 공유는 사용자 연결 방식이 정해진 뒤 범위를 확정한다. 기존 힌트·해설 공개 정책과 근거 중심 평가 원칙은 디스코드에서도 동일하게 적용한다.
