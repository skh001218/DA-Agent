- 브랜치: `codex/improve-task-quality`
- 정확한 입력: **실제 게임 업계 실무에서 발생하는 문제를 분석하고 싶어**
- 설정: 같은 문장에 중급/고급만 각각 선택. 모델은 기존 `gemini-3.5-flash-lite` 유지.

## 구현 및 검증

1. `business_case`에 배경·관측·기간·결정·에이전트 가정·근거를 연결한 질문을 저장하고 화면 설명 및 고정 평가에 반영했다. 사용자가 도메인 설명을 길게 작성하지 않아도 요청을 확장한다.
2. 중급의 비교·불확실성·결정, 고급의 대안·교란까지 필수 검사한다. 기존 저장 패키지는 기존 계약으로 재개할 수 있다.
3. 원본 테이블의 공개 FK를 따라 many-to-one 조인을 구성한다. 그룹별 집계, 조건부 분자/분모 비율을 독립 Python 결과와 PostgreSQL 결과로 대조한다. 임의 모델 SQL을 실행하지 않는다. 관측 비교 집단이 하나뿐인 과제, 잘못된 근거, 실행 불가능한 조인, 데이터 없는 진단 조건을 차단한다.
4. 질문과 분석 지표를 연결하고, 전체 행 수 같은 검산도 함께 참조할 수 있게 했다. 정의 없는 이탈·잔류 주장과 의미 없이 덧붙인 표를 차단한다. 기간·교란의 실제 적합성은 구조 검사에 더해 생성 데이터 미리보기를 전달한 독립 모델 검토로 확인한다.
5. 대안 비교 결과를 고정 계약과 대조한다. 검산할 계약이 없는 타당한 다른 분석은 `unverified`로 남기며 자동 오답으로 확정하지 않는다. 숫자 문자열, 결과 행 순서, 추가 출력 컬럼을 처리한다.

최종 명령 `docker exec da-agent-task-quality python scripts/verification/verify_request_training.py tests/automated`: **306 passed, 2 warnings**, 93.89초. 경고는 기존 FastAPI TestClient/httpx 사용 관련이다. 격리 recorder 스키마를 사용하고 테스트 종료 후 정리했다. 정상 조인·비율, 오류/누락/단일 집단/빈 분모, 기존 패키지, 고정 계약과 실제 DB 저장 결과를 포함한다. `git diff --check` 통과.

브라우저에서 요청 입력→실제 모델 출제→자료 사전→SQL 실행→선택 저장을 확인했다. 중급은 새 탭에서 재개 후 저장 근거 선택을 확인했다. 고급은 장비별 층화 SQL과 기간 비교 SQL을 실행하고 저장했다. 편집기 자동화 중 두 SELECT를 붙여 넣은 요청이 읽기 전용 단일 SELECT 규칙에 의해 차단되는 것도 확인했으며, 내용을 교체한 뒤 성공했다. 실패 실행은 성공 근거 선택 목록에서 제외된다.

기본 8087 서비스도 `docker compose up -d --build app`으로 반영했다. 반영 후 기존 중급 기록과 새 고급 기록의 API 읽기, 기본 서비스의 실제 고급 화면 및 저장한 성공 근거 2개 복원을 확인했다. 별도 8089 검증 컨테이너는 종료·제거하고 공유 패키지와 기록 DB는 유지했다.

## 비용과 개발 실패 이력

| 표본 | 모델 호출 수 | 입력 토큰 합계 | 출력 토큰 합계 |
| --- | ---: | ---: | ---: |
| 이전 중급 | 3 | 11,710 | 1,963 |
| 이전 고급 | 2 | 6,619 | 1,142 |
| 개선 중급 | 4 | 31,906 | 6,894 |
| 개선 고급 | 2 | 12,673 | 2,903 |

가격/청구 금액을 추정하지 않았고 provider가 보고한 토큰만 집계했다. 개선 중급은 두 번의 설계 수정이 포함된 표본으로, 최종 코드의 평균 사용량을 뜻하지 않는다. 개선 고급은 최종 수정 후 설계 1회·의미 검토 1회로 성공했다. 테이블 최대 4개, 요청당 모델 호출 최대 6회 한도는 유지했다. 입력·출력이 늘어 비용이 줄었다고 주장할 수 없다.

최종 두 표본 외 개발 중 정확한 입력으로 14개 요청, 40회 모델 호출이 있었다. 그중 실패 11개, 추가 확인 상태 1개, 출제 2개였으며 출제된 2개도 자료와 이탈/잔류 문구 불일치가 있어 최종 품질 성공 표본에서 제외했다. 여러 코드 버전에 걸친 개발 기록이라 최종 버전 성공률로 계산하지 않는다. 별도 공급자 진단 호출도 있었으므로 표의 토큰 합계를 이번 작업 전체 청구량으로 해석하면 안 된다.

실패 원인은 날짜/의존 컬럼 누락, 계산 요약의 잘못된 generator, 질문과 지표 연결 누락, 난이도 역량 누락, 과도하게 복잡한 API 응답 스키마 등이었다. 한 차례 API 스키마 변환에서 `title`/`description`이라는 실제 필드명을 삭제하는 오류도 수정하고 회귀 테스트를 추가했다. 최종 스키마는 생성기별 필수 입력·질문의 metric_names·지표 purpose·선택 난이도를 지정하며 서버의 상세 검증은 유지한다. 조사 표본은 모델이 추측한 최소치 대신 고정 데이터에서 조건에 해당하는 행이 실제 존재하는지도 검사한다.

## 남은 품질 한계

- **실제 회사 사건을 검색·인용하는 기능은 이번 2~5번 범위에 포함되지 않았다.** 두 결과 모두 가상 업무·합성 데이터라고 표시한다. 사용자 본래 의도 중 실제 업계 사례 확보는 별도 구현이 필요하다.
- 모델의 “큰 차이”, “비정상적으로 높음” 같은 현상 표현에는 여전히 기준이 충분하지 않을 수 있다. 자동 의미 검토를 사람 품질 승인으로 취급하지 않는다.
- 장비 점수·성공·시간은 합성 관측 값이며 이번 고급 표본은 조건부 인과 효과를 심어 검증한 자료가 아니다. 교란/적응 여부를 검토할 수 있지만 반드시 특정 원인을 찾아야 하는 과제로 사용하면 안 된다. 기간 집단 차이만으로 같은 계정의 학습 효과를 확정할 수 없다.
- 장비별 집단은 10~24회 시도로 작은 편이다. 계정의 반복 도전과 표본 불확실성을 검토해야 하며 통계적으로 충분한 실험 설계나 인과 분석을 보장하지 않는다.
- 임의 장비 구간이나 기간 정의에 대한 자동 수치 검산은 계약에 없으면 확인 불가로 남는다. 고정 기본 지표는 검산하지만 모든 타당한 고급 SQL을 자동 채점하지 않는다.
- 대표 중급/고급 생성 성공과 306개 회귀 통과는 대규모 반복 출제, 사람의 교육 효과 평가, 모든 주제의 안정성을 대신하지 않는다.
