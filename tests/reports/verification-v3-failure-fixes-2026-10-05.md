# 평가·코칭 실패 원인 수정 검증

- 날짜: 2026-10-05 (Asia/Seoul)
- 평가: request-review-v3 / evaluation-rubric-v3 / condition-review-v3-scoped-inputs
- 코칭: coaching-v2 / cumulative-coach-v4-conflict-guard
- 범위: 사용자 승인한 평가 입력 분리, 누락·오류 기준, 최종 주장, 가설 충돌 처리, API 실패 진단. 테이블 생성 한도는 변경하지 않았다.
- 실행: 일반 앱8087의 다른 화면 작업은 보존하고 소스 연결 검증 앱8088에서 확인했다. 일반 앱 배포·화면 브랜치 통합은 아직 하지 않았다.

## 수정 내용

1. 정의·계획·해석·다음 행동의 우선 입력을 구분했다. 계획·정의·다음 행동에는 SQL 원문이나 실행 검산을 평가 근거로 허용하지 않는다. 해석은 최종 주장과 실제 결과를 함께 읽고, SQL 정확성은 서버의 실행 검산을 따른다. 한 호출 안에 항목별 입력을 묶으며 모델 호출 수와 토큰 상한은 이전v3와 같다. 실제 입력/출력 토큰이 동일하다는 뜻은 아니다.
2. 다른 보고서 칸에 작성한 타당한 내용도 supporting_report로 인정한다. 자유 서술 report_text는 각 항목의 우선 입력에도 포함한다. 칸 위치 자체를 새로운 필수 조건으로 추가하지 않는다.
3. 없음=missing, 명시된 내용이 공개 조건·근거와 모순=error, 자료가 있으나 검증 계약·잘림으로 확인 불가능=unverifiable를 명시했다. 정의의 필수 요소가 전부missing이면 content도 서버가missing으로 맞춰0등급을 적용한다. 일부 정의를 제시한 경우에는2등급을 유지한다. 내용 부재를 핵심 오류로 바꾸지 않는다.
4. 현재 보고서의 최종 결론을 평가하고 명시적으로 철회·수정한 이전 주장에는 감점하지 않는다. 경계 예시를 프롬프트에 넣었다.
5. 현재 질문 또는 현재 초안에 가설·관측 충돌이 명시되어 있으면 서버가suggest_analysis로 전환한다. 충돌 해결·해소·가설 철회를 명시한 현재 질문은 이 규칙에서 제외한다. 명시되지 않은 의미적 충돌을 모두 탐지하는 기능은 아니다.
6. Gemini 실패에 로컬 요청UUID, 처리 단계, HTTP 상태 코드, 시간 초과 여부를 붙이고 ai_finished 이벤트에 저장한다. 인증 정보, 요청 본문, 모델 원문, 예외 문자열은 진단에 포함하지 않는다. timeout/transport/http/response를 구분하되 모든 네트워크 장애의 세부 원인까지 알아내는 것은 아니다.
7. 보류 총점 뒤에 숨은 등급 변화도 level_variation으로 실패 처리한다. 기존 핵심 오류 조건 변동 검사와 함께 유지한다. 과거 원본 평가·점수는 덮어쓰지 않았다.

## 사용자가 직접 확인할 사항

- 타당한 계획인데 SQL 실행이 틀리면 계획은 인정하고 SQL을 별도로 평가하는 기준이 의도에 맞는지 확인한다.
- 정의가 전혀 없으면0, 일부 정의가 있으면2, 잘못된 정의가 있으면1이라는 구분을 확인한다.
- 실제 근거 없이 계산·원인이 확인됐다고 주장한 경우 해석1이 적절한지, 철회된 인과 주장은 감점하지 않는지 확인한다.
- 명시된 미해결 가설 충돌에 제시하는 비교 행동이 학습에 도움이 되는지 확인한다.

## 남은 작업과 판정

이번 실패 표본과 경계 사례에서 개선을 확인했다. 전 과제 유형·난이도·다양한 서술의 반복 검증, 다른 화면 브랜치 통합/일반 앱 반영, 사람 품질 판정과 파일럿은 남는다. PRD5/11과Spec010 상위2/5 및v3 세부4/5는 유지한다. 최신 국소 판정은 기술 검사 통과·사람 의미 품질 검증 대기다. 모든 AI 판별의 일관성이 보장됐다고 완료 처리하지 않는다.
