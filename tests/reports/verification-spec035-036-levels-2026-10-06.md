# Spec 035와 036 요구사항 점검 및 난이도 비교

SQL 연습은 난이도에 따라 실제 집계 구조가 달라진다. 그러나 고급의 검산 설명 요구를 평가하지 않으므로 교육적 난이도 차이를 충분히 검증했다고 볼 수 없다. 텍스트 분석 연습은 실제 Gemma 출제가 실패해 난이도별 문제 내용을 비교할 수 없었다. 구조 검사에는 고급 역량 이름만 추가한 설계를 통과시키는 빈틈이 있다.

- 점검일: 2026-10-06, Asia/Seoul
- 대상: 현재 e8e3 체크아웃의 Spec035, Spec036과 관련 소스
- 구조: docs, scripts, specs/examples, src, template, tests 모두 존재. 폴더 생성·파일 이동 없음.
- 실행 범위: 전체 pytest, 격리 PostgreSQL의 Discord 회귀, 동일 SQL 요청의 세 난이도 실행·평가, 계약 위반 재현, 실제 Gemma의 두 요청·세 난이도 출제.
- 운영 봇·운영 DB·명령 등록·Discord 메시지 전송은 변경하지 않았다. 실제 Discord 입력·답장·게시·재개 화면은 검증 대기다.

## 동일 SQL 요청의 난이도 차이

고정 요청은 `튜토리얼 신규 가입자 3단계 완료율`, 도움 수준은 세 난이도 모두 `independent`다. 본 데이터의 SHA256은 모두 `e660a4eabab7d6d989d441222dedb91af3842ed18187e01666a215772386c640`로 같다. 각 난이도에 맞는 기준 SQL을 학습자 제출 경로로 실행하고 평가했다. 기준 SQL 제출은 기능 검사이며 학습자의 실제 수행 능력 검사는 아니다.

| 난이도 | 요구 집계 | 실행 결과 | 추가 계산 구조 |
| --- | --- | --- | --- |
| 초급 | 전체 1행 | 40명 중 30명, 75% | 전체 고유 가입자·완료자 비율 |
| 중급 | 채널별 2행 | ads 14/20=70%, organic 16/20=80% | 채널별 GROUP BY |
| 고급 | 가입 주차×채널별 4행 | 1주 ads 4/5=80%, organic 12/15=80%; 2주 ads 10/15≈66.67%, organic 4/5=80% | 가입일로 주차 계산 및 2차원 GROUP BY |

**판정:** 단순 난이도 이름 변경은 아니다. 결과의 집계 단위와 필요한 SQL 계산이 명확히 달라진다. 반면 고유 사용자·중복·기간·분모 처리의 핵심 로직은 세 수준에서 같고, 검증용 데이터 사례도 같은 네 범주다. 고급의 주요 차이는 주차 계산과 집계 차원 추가이며, 더 깊은 검증 판단까지 확인한 것은 아니다.

고급 과제에는 “중복과 기간 경계를 스스로 검산하세요”가 있지만 설명 입력·검증 방법의 기록·전용 평가 항목이 없다. 세 수준 모두 SQL 한 번만 제출했고 보고 설명이 없었는데 평가 5항목이 전부 충족됐다. Spec035 4절의 “검증 방법도 설명하도록 요구”와 간극이 있다.

## 동일 분석 요청의 실제 출제 결과

모델은 모든 호출에서 `gemma-4-26b-a4b-it`, practice는 analysis, 도움 수준은 independent다. 각 요청 안에서는 문장을 그대로 유지하고 난이도만 바꿨다. 요청 ID와 데이터 seed는 원래 서비스 구조상 새 세션마다 달라진다. 성공했더라도 한 번씩의 생성은 엄밀한 난이도 인과 실험이 아니며 여러 seed와 반복 표본이 필요하다.

| 요청 | 초급 | 중급 | 고급 |
| --- | --- | --- | --- |
| 튜토리얼 완료율 하락을 분석하고 싶어 | HTTP500 | HTTP500 | HTTP429 |
| 반복 행동 계정의 활동량과 정상 반례를 비교하고 싶어 | HTTP429 | HTTP429 | HTTP429 |

각 건은 설계 호출 1회로 failed가 됐다. 수정·적합성 검토·자료 적재·조회·보고·제출에 도달하지 않았다. 모델 전환이나 고정 문제 대체는 없었다. 따라서 **분석 연습의 세 난이도가 확연히 다른지는 판정할 수 없다. 실패 안내의 유사성을 문제 내용의 유사성으로 해석해서도 안 된다.**

429 응답은 `GenerateContentInputTokensPerModelPerMinute-FreeTier`, 제한 16000을 명시했고 재시도 대기 시간도 제공했다. 첫 비교를 짧은 간격으로 실행했으므로 호출 속도가 429에 영향을 줬을 수 있다. 이 결과로 특정 난이도나 요청이 더 불안정하다고 결론 내리지 않는다. 별도 중급 요청도 429였고 18초 대기 안내가 있었다. HTTP500의 내부 원인은 응답 정보만으로 확정할 수 없다.

## 문제점과 해결 방안

### 1 고급 난이도를 의미적으로 검증하지 못함

`task_quality.py`는 고급에 alternatives/confounding 역량, 조인·그룹 지표, count 외 연산이 있는지 확인한다. 실제로는 중급 fixture의 avg/FK/1차원 지표를 그대로 두고 alternatives와 confounding 질문을 모두 “플랫폼별 평균 활동량만 계산”, 완료 조건을 “표 한 개 제시”로 추가해도 통과했다. 중급과 이 고급 설계의 지표 구조는 모두 `avg:True:1`이다.

해결: 역량 이름 대신 질문별 검증 계약에 **비교 차원·필터·통제 조건·필수 판단·관측 가능한 근거·인정할 한계**를 고정한다. 고급의 교란 검토에는 필요한 조건부 비교 또는 교란을 식별할 수 없다는 타당한 보류 경로를 명시하고, 그 계약과 실제 지표·표본을 검사한다. 이번처럼 같은 집계만 요구하는 고급 설계를 거부하는 반례 검사를 추가한다. 전체 JSON 검증을 유지하며 모델 검토 결과만으로 승인하지 않는다.

### 2 고급 SQL의 검산 설명이 평가에서 빠짐

`discord_sql_practice.py:169`의 evaluate는 SQL 실행 결과만 대조한다. 검산 설명을 요구·저장·평가하는 경로가 없어 고급의 공개 요구와 평가 근거가 다르다.

해결: 고급 SQL 제출에 검산 설명을 연결하고 **중복을 어떻게 확인했는지, 기간 경계를 어떻게 검증했는지, 분모·NULL 처리가 왜 타당한지**를 공개 완료 조건으로 고정한다. 쿼리 정확성과 설명 확인을 구분해 결과에 표시한다. 설명 평가를 구현하지 않을 경우 Spec의 고급 설명 요구와 안내를 현재 SQL 결과 검사 범위에 맞게 조정해야 한다. 고급 SQL만 맞고 설명은 없는 사례가 전부 충족으로 나오지 않도록 검증한다.

### 3 미지원 SQL 요청을 완료율 과제로 바꿀 수 있음

`discord_service.py:62`의 키워드 조건은 '튜토리얼'과 '완료율 또는 3단계'만 본다. `튜토리얼 완료율 대신 D7 리텐션을 계산해줘`를 넣으면 거부하지 않고 채널별 완료율 SQL 과제를 만든다. Spec035/036의 미지원 요청 거부·조용한 고정 문제 대체 금지와 맞지 않는다.

해결: 지원 문제 ID와 요청 지표를 명시적으로 매핑한다. D7·주간 재방문·다른 지표 또는 여러 지표가 섞인 요청은 적합성을 확인하거나 지원 범위를 안내하며 중지한다. 부정 표현·복합 지표·완료 분석 연결에서도 의도를 확인하고, 거부 시 세션·자료 생성이 없는지 검사한다.

### 4 필수 practice 검증이 경로마다 다름

SDK에서는 practice 필수지만 `discord_service.py:60`의 text 경로는 None을 허용한다. 재현 요청은 practice 없이 accepted 세션을 만들었다. text가 없는 legacy 경로는 누락을 거부한다. 정상 슬래시 UI에서는 필수 선택이 있으므로 직접 서비스 호출·내부 연동에 해당하는 간극이다.

해결: 신규 생성 진입점은 text 유무와 관계없이 practice를 반드시 검사한다. 과거 기록 복원과 신규 요청 검증을 분리하고, 내부 fixture도 practice를 명시한다. 누락 요청에서 이벤트·세션·자료·모델 호출이 발생하지 않는 것을 검사한다.

### 5 실제 출제 안정성과 난이도 비교가 API 제한에 막힘

현재 Gemma 응답은 실제 문제 생성에 이르지 못했다. 기존 수동 재시도와 요청별 호출 상한만으로는 사용자 간 공유되는 분당 토큰 제한을 피하기 어렵다.

해결: 모델·프로젝트별 공유 호출 큐와 예상 입력 토큰 예산을 두고, 429의 retry_delay를 재시도 가능 시각과 함께 저장·표시한다. 배치 감사 도구에도 간격과 호출 예산을 적용한다. 500은 별도 장애로 기록해 제공자 진단 ID·상태·시각을 근거로 조사한다. 다른 모델로 몰래 대체하거나 검증을 완화하지 않는다. 가용성 회복 후 두 요청×세 난이도를 여러 표본으로 다시 출제한다.

### 6 Spec의 이전 명령 설명과 현재 계약이 혼재됨

Spec035 2절에는 topic 기반 명령과 text 없는 예시가 남고 말미 통합 절에서 practice/text 필수라고 정정한다. Spec036 “목적과 현재 구현”에는 topic choices가 현재 코드인 것처럼 남아 있다. 실제 SDK는 practice와 text가 필수다.

해결: 본문을 현재 통합 명령에 맞춰 정리하고 기존 topic 설명을 변경 전 배경으로 표시한다. 내부 legacy 호출과 공개 슬래시 계약을 구분한다. 문서 예시·도움말·등록 스키마가 일치하는지 검사한다.

## 개선 순서와 재검증 완료 조건

1. 요청 의도와 필수 선택을 먼저 보장한다. practice 누락과 D7 대체 재현이 모두 거부되고 자료 생성이 없어야 한다.
2. SQL 고급의 설명 계약과 분석 고급의 의미 계약을 보강한다. 이름만 고급인 반례는 차단하고 타당한 조건부 비교·판단 유보는 인정해야 한다.
3. 공유 API 호출 속도·토큰 예산·재시도 가능 시각을 적용한다. 지정 모델로 설계·검토·실제 DB 검산까지 성공해야 한다.
4. 같은 요청·help_level·공통 데이터 또는 seed 묶음으로 난이도를 비교한다. 초급의 대상/기간/기준 제공, 중급의 비교 선택, 고급의 질문/우선순위·대안·교란/한계 판단이 문제와 평가 모두에 드러나야 한다. 질문 수·문장 길이·집계 열 수만으로 구분하지 않는다.
5. 현재 코드를 반영한 테스트 Discord 환경에서 입력→문제→조회/SQL→오류 수정→제출→재개→결과 게시를 화면으로 확인한다. 운영 배포와 사용자 메시지 전송은 별도 작업이다.

참가자가 화면에서 먼저 확인할 행동: 현재 코드 반영 후 `/training practice:sql text:튜토리얼 신규 가입자 3단계 완료율 difficulty:advanced help_level:independent`를 실행해, 봇의 SQL 틀에 작성한 코드 블록으로 답장했을 때 실제 실행 결과가 돌아오는지 확인한다. 이 한 번의 확인만으로 전체 Discord 검증을 완료한 것으로 계산하지 않는다.
