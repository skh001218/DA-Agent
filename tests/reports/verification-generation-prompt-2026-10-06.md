# 출제 이력 영향과 추상적 요청 프롬프트 점검

- 확인일: 2026-10-06 (Asia/Seoul)
- 범위: 현재 adaptive 출제 경로, 최근 이력 조회, 모델 입력 구성, 구조적 중복 차단, 생성·수정·적합성 지침.
- 결과: 이전 과제가 새 출제에 영향을 주는 경로가 있다. 추상적 요청을 에이전트가 구체화한다는 사용자 결정은 유지되어 있다. 프롬프트의 편향·상충 지침과 검증 범위 공백은 남아 있다.
- 이번 검사는 실제 DB와 현재 함수에 대한 읽기·직접 실행이다. 새 모델 호출이나 문제 생성은 하지 않았으며, 앱 코드도 변경하지 않았다.

## 사용자가 정했던 기준

[판단 기록](../../나의판단과근거.md)의 2026-10-05 기록은 간단한 요청만으로 문제를 제공하고 선택 조건은 필요할 때 요청문에 넣는다는 결정과 이유를 보존한다. [Spec 016](../../specs/016-simple-training-request.md)은 이를 화면에 적용했고, [Spec 018](../../specs/018-business-task-quality.md)은 상세 업무 상황을 사용자에게 요구하지 않는다고 명시한다.

실제 출제 프롬프트 첫 단락에도 다음 지시가 있다.

> 짧은 요청을 사용자가 도메인 설명을 작성하지 않아도 구체적인 업무 문제로 확장하세요.
> 광범위한 '게임 업계 실무 문제' 요청은 에이전트가 구체적 상황을 선정해야 합니다. 상세 상황 미입력만으로 clarify하지 마세요.

따라서 이번 실패를 사용자의 추상적인 입력 탓으로 처리하면 기존 계약과 어긋난다. 모순되는 핵심 의도·실제 서비스의 필수 사실이 필요한 경우에는 질문할 수 있지만, 연습용 가상 상황의 팀·대상·기간·조건은 에이전트가 설정하여 공개해야 한다.

## 이전 과제가 전달되는 경로

1. `TaskGeneration.recent()`는 `training_plans`와 `attempts`를 연결하여 started_at 내림차순 최근 5개를 읽는다. 훈련 완료·풀이 제출 여부가 아니라 공개된 과제 계획이 대상이다.
2. 공개 계획의 `semantic_signature`만 가져온다. 주제, 목표, 유형, 수준, 분석 구조, 상황 식별자, 품질 버전 등이 포함된다.
3. `planning_messages(data, recent)`의 user JSON에 현재 request, recent, schema가 함께 들어간다. 이력은 프롬프트에 '최근 과제와 단순 제목/컬럼만 다른 반복을 피하라'는 지시와 결합된다.
4. `check_quality(recipe, self.recent(), intentional_repeat)`에서 기존 과제와 동일한 난이도·목표 문자열·분석 구조·품질 버전이면 차단한다.

이 경로는 이전 문제의 본문·정답·SQL·코칭 대화·점수·실패 원문을 전달하지 않는다. 실패하여 과제 계획/attempt가 공개되지 않은 요청은 recent 목록에 들어가지 않는다. GeminiProvider는 매 호출에 받은 messages로 contents/systemInstruction을 새로 구성하며 이전 대화 식별자를 사용하지 않는다. 같은 요청 안의 설계 수정 단계에서는 해당 요청의 직전 생성 응답과 검증 사유를 전달한다.

현재 최근 5개는 보스 레이드 과제 4개와 가입일별 신규 이용자 집계 1개다. 실패했던 중급 요청과 이번 초급 실패는 이 목록에 없다. 초급·중급·고급이 recent에는 함께 포함되지만, 서버의 정확 중복 차단은 같은 난이도끼리 적용된다.

## 직접 확인한 검사

| 검사 | 결과 |
| --- | --- |
| 이력 [] / 현재 최근 5개로 같은 요청의 입력을 구성 | developer 지침은 동일, user JSON의 recent만 다름 |
| 실제 저장된 고급 recipe와 동일한 과제 서명 | 반복 과제로 차단 |
| 동일 서명 + intentional_repeat=true | 통과 |
| 과거 서명의 난이도만 다른 경우 | 통과 |
| 과거 서명의 목표 문구만 바꾼 경우 | 같은 구조여도 통과 |

현재 화면의 startTraining은 intentional_repeat=false를 고정 전송한다. 사용자가 '같은 상황에서 난이도만 비교'하려 해도 새 출제 입력의 이력은 유지되며, 화면에서 이를 끄는 선택은 없다. 같은 난이도 반복을 원할 때도 이 값이 자동으로 true가 되지는 않는다.

각 과제의 생성 당시 recent 전체는 저장하지 않았으므로 특정 결과가 이력 때문에 어느 정도 바뀌었는지를 소급 정량화할 수는 없다. 이번 검사는 영향 경로와 현재 입력을 입증한다. 이력 유무에 따른 실제 모델 결과 비교는 수행하지 않았다.

## 프롬프트 문제점

### 1. broad request 처리 원칙은 맞지만 선택 분야를 지나치게 좁힘

첫 단락은 에이전트가 업무 상황을 고르라고 한다. 그러나 후반 '최종 필수 확인'은 광범위한 실무 요청에 보스/스테이지 성공률·전투시간·장비/숙련도 비교를 선택하라고 지시하고 profiles/content/attempts 예시까지 제시한다. 이 문구 자체가 이번 여러 문제의 보스 분석 집중을 유도할 수 있다. 단, 특정 응답의 인과적 기여도는 모델 대조 실험 없이 확정하지 않는다.

지원 가능한 범위를 우선하는 목적은 타당하지만 이를 대표 예시로 분명히 표시하고, 실제 등록된 연산/관계로 가능한 업무 상황을 여러 후보에서 선정해야 한다.

### 2. recent의 사용 범위가 명확하지 않음

현재 지침은 반복 회피만 언급한다. 과거 주제를 사용자의 선호나 현재 요청의 도메인으로 추론하지 말라는 제한은 없다. 추상적 요청일수록 최근 이력의 구체적인 보스 주제가 선택에 영향을 줄 가능성이 있다. 이력은 중복 회피 자료이며 현재 명시 조건이 항상 우선이라는 규칙을 분명히 하는 편이 좋다.

### 3. 생성 그룹 예시가 의무처럼 쓰여 있음

'원본 Table에는 반드시 groups=[{name:sample,count:200,overrides:{}}]가 있어야 합니다'라고 되어 있다. 실제 schema는 여러 group과 overrides를 허용하며 직전 단락도 profile_a 예시를 쓴다. groups 필드가 필수라는 요구와 정확히 하나의 균일 sample을 강제하는 표현을 구분해야 한다. 이 literal을 따르면 교란·집단 관계를 위한 조건부 생성 설정을 쓰기 어렵다. 실제 성공 표본은 모두 sample/빈 overrides였다.

### 4. 요구 판단과 지원 지표의 간극

불확실성·교란·대안 설명을 필수화하지만, 검산 연산은 count/distinct/sum/avg/min/max/ratio뿐이다. 편차를 요구하며 평균만 검산하거나 교란 검토를 요구하며 각각의 주변 집계만 검산하는 문제가 이미 [이전 감사](verification-difficulty-audit-2026-10-06.md)에서 확인됐다. prompt가 '각 수치 비교를 검산하라'고 해도 서버는 조건·비교 차원의 전체 대응을 확인하지 않는다.

특히 고급의 대안 설명은 현상을 설명하는 가설 비교여야 한다. 자료 없는 조치 효과의 비교나 체감 영향 입증으로 치환하지 않도록 해야 한다.

### 5. ratio 지침과 공급자 schema 사이의 차이

텍스트에는 ratio 분자 조건의 의미와 성공=1 예시가 있다. 그러나 Metric.conditions는 기본 []이고 공급자 schema에서 ratio에 대한 조건부 비어 있지 않음 제약을 따로 넣지 않는다. 생성기는 schema를 만족하는 빈 conditions를 만들 수 있고 서버의 의미 검증에서 뒤늦게 실패한다. schema/출력 예시/수정 지침을 같은 요구로 맞추는 개선이 필요하다.

### 6. 생성 오류를 사용자 입력 부족으로 안내하는 문구

적합성 실패 시 '요청을 구체화하거나 다시 시도하세요', unsupported 시 '목표·기간·판단 범위를 구체화해 주세요'라는 안내가 있다. 어떤 추가 사실이 필요한지와 모델이 잘못 설계했는지를 구분하지 않는다. 가상 연습 상황을 보강하는 것은 에이전트 책임이라는 기준에 맞게, 모델 설계 오류는 내부 수정 대상으로 처리하고 실제 필요한 정보가 있을 때만 이유와 질문을 제시해야 한다.

## 개선할 지침 초안 (미적용)

```text
짧고 추상적인 연습 요청도 출제 가능한 요청으로 처리한다.
사용자가 제공하지 않은 가상 업무 배경·분석 대상·기간·판단 기준은
에이전트가 지원 기능 안에서 선정하고 '연습을 위해 설정한 조건'으로 공개한다.
상세 상황이 없다는 이유로 확인 질문을 하지 않는다.
현재 요청의 핵심 의도가 충돌하거나 가정하면 요청 목적이 달라지는 경우에만 질문한다.

recent는 중복 회피 자료다. 이전 주제를 현재 요청의 도메인이나 사용자 선호로 간주하지 않는다.
현재 사용자의 주제·난이도·조건을 우선한다.
보스/전투 예시는 지원 가능한 상황의 예시이며 모든 추상적 요청의 기본 주제가 아니다.

groups 필드는 필수지만 group 이름·수·count·overrides는 학습 목표에 맞춰 구성한다.
필요한 집단 관계·반례·조건부 비교 표본을 재현하고,
차이가 없거나 원인을 확정할 수 없는 상황도 타당한 결론으로 허용한다.

각 질문은 공개 컬럼뿐 아니라 필요한 필터·비교 차원·통제 조건·검산 지표와 연결한다.
지원 지표로 충분히 검증할 수 없는 판단은 관측 가능한 범위로 바꾸거나 검증 기능을 보강한다.
출력 오류를 사용자의 추상적인 요청 탓으로 처리하지 않는다.
```

프롬프트만 고쳐도 모든 품질 문제가 해결된다고 보지 않는다. 질문-검산 대응과 수준별 정보 제공은 서버 검증에 연결해야 한다. 위 초안은 검토용이며 현재 앱에 적용하지 않았다.
