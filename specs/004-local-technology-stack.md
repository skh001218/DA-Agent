## Docker 실행과 DB 분리

- 앱 서비스는 FastAPI와 웹 정적 파일을 제공한다. PostgreSQL 서비스 하나에 학습 DB와 기록 DB를 별도로 둔다. Docker 서비스는 컨테이너 내부 이름으로 연결한다.
- 학습 SQL에는 공개 표만 읽을 수 있는 전용 계정을 사용한다. 기록 저장 계정·데이터 준비 계정과 분리하고 관리자 자격 증명으로 학습 SQL을 실행하지 않는다.
- DB 연결 권한과 표·함수 권한을 제한하고 읽기 전용 트랜잭션·쿼리 시간 제한을 적용한다. 읽기 전용 설정 하나만으로 임의 SQL의 모든 위험을 막았다고 보지 않는다.
- DB는 컨테이너 내부 네트워크에서 접근한다. 로컬 웹 포트와 인증 콜백에 필요한 포트만 호스트의 루프백 주소에 연결한다. DB 포트의 호스트 공개는 기본 구성에서 하지 않는다.
- DB healthcheck를 통과한 뒤 앱을 시작하고, 시작 후 일시적 DB 장애도 재연결·실패 안내로 처리한다. Compose의 준비 상태 대기는 [공식 안내](https://docs.docker.com/compose/how-tos/startup-order/)를 따른다.
- Python·PostgreSQL 이미지와 의존성은 구현 시 검증한 정확한 버전으로 고정한다. latest 태그를 실행 기준으로 사용하지 않는다. Intel·AMD와 ARM 테스트 환경의 이미지 지원도 확인한다.
- DB 자료는 named volume에 보관한다. 중지·재시작 때 기존 자료를 유지하고 초기화·삭제 작업을 일반 시작 절차에 포함하지 않는다.
- 앱은 localhost에서 접근하는 로컬 단일 사용자 환경을 기본으로 한다. 인터넷 공개·다중 사용자 운영은 별도 범위다.

## Git과 다른 PC 테스트

Git에는 소스, Dockerfile·Compose 설정, 의존성 고정 파일, DB 스키마·변경 스크립트, 패키지 manifest, 데이터 준비·검증 스크립트, 설정 예시와 테스트 안내를 관리한다. 실제 파일은 구현 단계에서 만든다.

구체적인 절차는 같은 커밋/태그 받기 → Docker 실행 조건 확인 → PC별 설정 작성 → 검증된 데이터 패키지 준비 → Compose 시작 → 핵심 흐름 확인이다. Windows 절대 경로에 의존하지 않고 프로젝트 상대 경로와 설정값을 사용한다.

- 데이터 준비에는 seed뿐 아니라 생성기·스키마·패키지 버전과 해시를 확인한다. 새 PC에서 재생성한 결과가 기준 해시·정답과 다르면 출제하지 않는다.
- 앱 코드 버전과 콘텐츠 배포 버전은 별개다. 같은 Git 커밋을 사용했다는 사실만으로 문제·데이터 버전 일치를 가정하지 않는다.
- 새 PC의 기본 테스트는 빈 학습 기록으로 시작한다. 기존 기록을 이어가려면 별도 DB 백업·복원 절차와 기존 콘텐츠 패키지를 함께 제공한다.
- DB 볼륨, 개인 기록·백업, 로그, 비밀번호, OAuth 자격 증명과 호스트별 인증 정보는 Git에 넣지 않는다.
- 인증 정보와 host ID는 PC별로 관리한다. 새 PC에서는 해당 환경의 공식 로그인 절차를 수행한다. 컨테이너 재생성만으로 기존 host ID를 매번 바꾸지 않도록 호스트별 수명과 저장을 관리한다.

## ChatGPT 로그인과 AI 요청

공식 Sign in with ChatGPT의 로컬 앱 플랜 사용 경로를 채택한다. 로그인한 사용자에게 적격 플랜·모델 사용 권한이 있는지와 실제 요청 완료 여부를 확인한다. 로그인 성공만으로 코칭·리뷰 사용 가능으로 표시하지 않는다.

1. 앱에서 ChatGPT 연결을 선택하면 호스트 브라우저에서 공식 OAuth 로그인·사용 동의 절차를 연다.
2. 로그인 상태 검증, PKCE와 state·nonce 검증, 토큰 교환·신원 및 부여 권한 확인을 수행한다.
3. 별도의 플랜 사용 권한을 확인한 후 연결 완료를 표시하고, 해당 계정으로 사용 가능한 모델을 조회한다.
4. Python 서버가 OAuth access token으로 공개 Responses API를 호출한다. ChatGPT 웹의 내부 backend-api나 기존 Codex 인증 파일을 임의로 재사용하지 않는다.
5. 각 요청에는 필요한 공개 스키마·사용자 입력·선택한 결과와 규칙을 전달한다. 일반 코칭과 비공개 평가 경로를 분리한다.
6. 응답 완료 이벤트를 확인한 경우에만 코칭·리뷰 성공으로 처리한다. 부분 응답·중단·한도 초과는 별도 상태로 안내한다.

컨테이너 안의 인증 콜백이 호스트 브라우저에서 도달하도록 공식 로컬 콜백 방식과 포트 연결을 실제로 검증한다. 웹 포트 변경과 콜백 주소의 호환도 확인한다. 인증 토큰을 SQL·결과·보고서 저장 테이블이나 브라우저 저장소에 넣지 않으며, 앱의 보호된 별도 인증 저장소에서 갱신·연결 해제를 처리한다. 보호 방식·키 관리는 구현 전에 선택하고 검증한다.

현재 공식 미리보기 경로에 맞춰 `store: false`, `stream: true`와 필요한 input 배열을 사용한다. 대화 맥락은 앱이 필요한 부분을 구성해 전달한다. 지원하지 않는 일반 API 옵션·도구를 그대로 사용하지 않는다. 세부 구현 시 공식 계약을 다시 확인한다.

미저장 SQL을 사용하는 코칭은 ③의 규칙에 따라 일시적 처리만 한다. AI 응답·요청 로그를 통해 해당 SQL·결과가 영구 기록으로 남지 않도록 검사한다. 모델에게 임의 셸·DB 도구를 주지 않고 SQL 실행·검증은 앱의 제한된 경로에서 수행한다.

## 한도와 장애 대응

- 코칭·리뷰 요청 시에만 AI를 호출한다. 입력 자동 저장·SQL 실행마다 호출하지 않는다.
- ChatGPT 플랜 사용량·권한의 한계를 안내한다. 앱에서 실제로 조회할 수 없는 잔여량을 추정 수치로 표시하지 않는다. 확인할 수 있는 요청 사용량만 기록한다.
- 연결 실패·권한 부족·플랜 한도 초과 시 SQL, 선택 저장, 보고서 작성, 고정 힌트를 유지한다. 리뷰는 재시도 가능한 상태로 보존한다.
- 별도 유료 API 키로 자동 전환하지 않는다. 다른 인증·과금 경로를 추가하려면 별도 사용자 선택으로 처리한다.
- 사용할 모델은 계정별 목록과 리뷰 표본 검증으로 선정한다. 모델 이름을 로그인 이전에 사용 가능하다고 고정하지 않는다.
- 사용자 로그인은 LLM 연결에 필요한 인증이다. DA-Agent 자체의 다중 사용자 회원 시스템은 이번 범위에 추가하지 않는다.

## 구현 후 완료 조건

1. 신규 로컬 환경에서 Compose로 앱·DB가 정상 시작하고 건강 상태를 확인한다.
2. 문제 1의 콘텐츠 버전·해시와 기준 결과를 확인한다.
3. 실제 화면에서 문제 시작 → SQL 실행 → 실행 선택 저장 → 보고서 근거 연결 → 제출 → 리뷰 흐름을 확인한다.
4. 저장한 실행만 새로고침 후 복구하고 미저장 SQL·결과가 DB·파일·로그에 남지 않는지 확인한다.
5. 공식 ChatGPT 로그인·권한 승인·모델 조회·AI 응답 완료·토큰 만료·연결 해제·한도 오류를 확인한다. 실제 계정으로 확인하지 못한 항목은 검증 대기로 남긴다.
6. 다른 PC에서 같은 Git 커밋과 콘텐츠 버전으로 1~5의 핵심 흐름을 재확인한다. 다른 PC 확인을 하지 않았다면 이식성 검증 완료로 표시하지 않는다.

화면·로그인·Docker 실행 검증은 아직 수행하지 않았다. 다음 구현에서는 먼저 Docker 기본 실행과 데이터 준비를 연결하고, ChatGPT 인증·짧은 호출로 실제 사용 가능성을 확인한다. 데이터 기간·표본 수·생성 조건과 모델 품질 기준은 구현 전에 구체화한다.
