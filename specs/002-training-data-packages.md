## 확정 방향

2026-10-03 사용자는 공통 표 구조를 재사용하면서 문제 유형과 실제 데이터 상황을 바꾸는 방안을 선택했다. 같은 데이터로 문제 내용이 비슷해지는 상황을 우려하며, 데이터와 그 데이터로 만든 문제의 버전을 일치시키도록 요청했다.

데이터, 문제, 평가 자료를 하나의 **훈련 패키지**로 배포한다. 패키지 안의 데이터·모든 문제·모든 평가 자료에 동일한 `package_id`와 `release_version`을 사용한다. 예를 들어 `training-001 / v1`의 데이터에는 같은 묶음의 문제 v1과 평가 자료 v1만 연결한다. 서로 다른 패키지의 v1끼리도 연결하지 않는다.

버전은 데이터·문제·정답의 대응을 보장한다. 문제의 다양성은 분석 목표와 데이터 상황을 변화시켜 확보한다. 이 문서는 설계 명세이며 실제 데이터나 검증 완료 패키지는 아직 없다.

## 공통 표 구조

문제 1의 필수 표는 `users`와 `sessions`다. 문제 2·3에서 사용하는 `tutorial_attempts`는 해당 패키지에 추가한다. 문제별로 필요한 표를 선언하고, 사용하지 않는 영역의 로그는 먼저 생성하지 않는다.

| 표 | 행 단위 | 컬럼과 의미 |
| --- | --- | --- |
| users | 유저 1명 | user_id: 고유 ID; signup_at: 가입 시각; platform: 가입 플랫폼; country: 가입 국가; acquisition_channel: 유입 채널; signup_app_version: 가입 앱 버전 |
| sessions | 접속 세션 1회 | session_id: 고유 ID; user_id: 유저 참조; login_at: 로그인 시작; logout_at: 종료 시각, 종료 미기록이면 비어 있음; app_version: 세션 앱 버전 |
| tutorial_attempts | 단계 시도 1회 | attempt_id: 고유 ID; session_id: 세션 참조; user_id: 유저 참조; step_id: 단계; started_at: 시작; ended_at: 종료, 종료 미기록이면 비어 있음; result: success / failure / abandoned |

- ID는 문자열로 관리한다. `step_id`는 양의 정수다. 참조 ID는 연결 대상과 같은 형식을 사용한다.
- 학습 DB는 PostgreSQL을 사용한다. 시각 컬럼은 `timestamp with time zone`으로 저장하고 생성 데이터는 초 단위를 사용한다. 패키지 파일·API에서는 UTC ISO 8601 문자열 `YYYY-MM-DDTHH:mm:ssZ`로 교환한다. 날짜 집계 시 Asia/Seoul로 변환하며 SQL 환경 안내에 변환 방법을 제공한다. 참고: [PostgreSQL 시각 자료형](https://www.postgresql.org/docs/current/datatype-datetime.html).
- 필수 컬럼은 종료 시각을 제외하고 값을 요구한다. 범주 값과 의미는 패키지별 데이터 사전에 공개한다.
- 가입보다 이른 로그인, 시작보다 이른 종료, 없는 유저·세션 참조를 허용하지 않는다. 시도의 user_id는 연결 세션의 user_id와 같아야 한다.
- 동일 유저의 반복 접속·실패·재시도는 정상적인 여러 행으로 보존한다. 집계에서 고유 유저 단위로 처리한다.
- 이탈 여부나 정답 비율을 분석용 표의 컬럼으로 제공하지 않는다. 학습자가 공개 기록에서 직접 계산한다.
- 추후 구매·전투 등의 문제를 추가할 때 필요한 표를 확장한다. 기존 표의 의미를 바꾸는 경우 새 스키마 버전을 부여한다.

`schema_version`은 표 구조의 버전이며 패키지 배포 버전과 별도로 기록한다. 여러 데이터 변형이 같은 스키마 버전을 사용할 수 있다. 데이터와 문제의 버전 일치 요구는 동일한 `package_id + release_version`으로 충족한다.

## 공개·비공개 자료의 경계

| 구분 | 포함할 자료 | 접근 경로 |
| --- | --- | --- |
| 공개 | 학습 DB, 문제 설명, 표·컬럼 사전, 가입 범위, 수집 완료 경계, 지표 정의, 패키지·데이터·문제 식별 정보 | 학습자, SQL 조회, 일반 코칭 |
| 비공개 | 생성 사건·확률·seed, 생성기 버전, 기준 SQL, 검증된 분자·분모·결과, 기대 발견사항, 허용 대안, 단계별 힌트, 평가 기준 | 생성·검증 도구, 평가 경로, 선택한 수준의 힌트 제공 경로 |
| 해설 공개 | 해당 문제의 기준 SQL과 해설 | 학습자가 해설 보기를 선택한 뒤 제공하고 시도에 기록 |

학습 DB에는 공개 표만 둔다. 비공개 자료는 별도 저장 영역에 두고 공개 다운로드·정적 파일 제공·학습자 SQL에서 접근할 수 없게 한다. 단순히 파일 이름에 private을 붙이는 것만으로 분리 완료로 보지 않는다. 구체적인 저장 위치와 접근 구현은 기술 구성 단계에서 정한다.

일반 코칭에는 공개 자료와 사용자 입력·실행 결과만 전달한다. 힌트는 요청한 수준의 내용만 전달한다. 평가 경로는 비공개 기준을 사용하되 해설 보기 전 기준 SQL 전체나 생성 사건을 리뷰에 그대로 노출하지 않는다.

## 패키지 연결 정보

공개 manifest는 다음 정보를 포함한다. 아래 필드는 저장 형식 설계의 기준이며 파일 형식·로더는 후속 단계에서 구현한다.

| 필드 | 의미 |
| --- | --- |
| package_id | 내용이나 원인을 암시하지 않는 패키지 ID |
| release_version | 묶음 전체의 배포 버전, 초기에는 v1, v2처럼 증가 |
| dataset_id | 데이터 스냅샷 ID |
| dataset_version | release_version과 같은 값 |
| schema_version | 공통 표 구조의 버전 |
| timezone | Asia/Seoul |
| timestamp_format | UTC ISO 8601, 초 단위 |
| data_complete_before | 이 시각 미만의 로그가 모두 수집되었다는 UTC 경계 |
| data_files | 학습 데이터 경로와 내용 해시 |
| problems | 각 problem_id, problem_type_id, problem_version, 가입 범위, 문제 파일 경로·해시, 필요한 표 |

`problem_version`은 `dataset_version`과 같아야 한다. 비공개 manifest에도 같은 package_id, release_version, dataset_id, dataset_version, 각 problem_id와 `evaluation_version`을 기록하며 evaluation_version 역시 release_version과 같아야 한다. 공개 manifest에는 비공개 파일 경로와 생성 사건을 넣지 않는다.

생성 조건·seed·생성기 버전은 비공개 manifest에서 보존한다. 같은 seed만으로 동일 데이터를 보장한다고 가정하지 않는다. 생성기 버전과 데이터 파일 해시를 함께 확인한다.

## 버전 변경과 훈련 기록

1. 데이터 행, 스키마, 수집 완료 경계, 문제 설명·조건, 기준 SQL·정답·평가 기준 중 하나라도 변경하면 패키지의 새 배포 버전을 만든다.
2. 새 배포에서는 데이터·문제·평가 자료 버전을 모두 같은 값으로 올린다. 데이터 내용이 그대로면 같은 스냅샷과 해시를 재사용할 수 있지만 manifest의 배포 버전은 함께 갱신한다.
3. 배포된 버전의 내용은 수정하거나 덮어쓰지 않는다. 수정된 정답도 새 버전으로 제공한다.
4. 훈련 시작 시 package_id, release_version, dataset_id, problem_id를 고정한다. SQL 결과·보고서·리뷰도 이 연결 정보를 따른다.
5. 새 버전 배포 후에도 기존 훈련은 원래 버전으로 재개한다. 원래 자료가 없거나 검증 실패라면 재개할 수 없음을 알리고 최신 자료로 자동 교체하지 않는다.
6. 같은 데이터에 여러 문제를 연결할 수 있다. 문제 ID는 서로 달라도 같은 패키지에서는 데이터와 동일한 배포 버전을 사용한다. 새 문제를 추가해 배포할 때도 새 패키지 버전을 만든다.

[훈련 기록 명세](./003-training-record-contracts.md)에 따라 이 연결 정보를 사용자가 선택 저장한 실행·보고서·리뷰 기록에 반영한다. 미저장 실행은 영구 보관하지 않는다. 보고서 수정 버전과 코칭 모델·규칙 버전은 콘텐츠 배포 버전과 구분하여 기록한다.

## 문제 다양성

문제 유형은 학습 목표를, 데이터 변형은 상황을 구분한다. 숫자나 문구만 바꾸는 경우는 같은 분석 유형의 반복 연습으로 분류한다.

| 확장 방식 | 예시 | 관리 방식 |
| --- | --- | --- |
| 같은 문제 유형, 다른 데이터 | 이탈률 계산을 다른 접속 기록으로 연습 | 새 dataset_id와 별도 package_id |
| 같은 표 구조, 다른 상황 | 플랫폼별 변화, 유입 구성 변화, 뚜렷한 차이 없음 | 비공개 변형 정보와 새로운 데이터 스냅샷 |
| 다른 분석 목표 | 계산, 그룹 비교, 변화 진단 | 별도 problem_type_id와 평가 기준 |
| 새로운 분야 | 구매 전환·전투 실패 분석 | 필요한 표와 데이터 사전 추가 |

변형을 새 패키지로 관리하고 기존 패키지의 오류 수정·조건 변경은 새 배포 버전으로 관리한다. 숫자가 바뀌었다는 사실만으로 새로운 분석 역량을 훈련하는 문제로 보지 않는다.

초기에는 문제 1의 검증된 패키지 한 벌을 완성하고 이후 동일한 표 구조의 데이터 변형을 추가한다. 자동 출제 시 이전 package_id, dataset_id, problem_type_id와 해설 참조 이력을 활용하는 중복 방지 정책은 후속 확장으로 둔다. LLM의 문구 생성만으로 신규 검증 문제를 늘리지 않는다.

## 배포 전 검증 조건

- 모든 데이터·문제·평가 자료의 package_id와 배포 버전이 일치해야 한다. 같은 버전 문자열이어도 package_id가 다르면 차단한다.
- 선언한 데이터 파일과 문제 파일의 해시가 실제 내용과 같아야 한다. 비공개 파일도 비공개 manifest의 해시로 검증한다.
- 모든 문제에 같은 데이터 스냅샷을 대상으로 실행한 기준 SQL·결과가 있어야 한다. 하나라도 누락되거나 검증 실패면 해당 패키지는 출제하지 않는다.
- 기본 키·외래 키·시각 순서를 검사하고 문제 1의 관측 경계 사례를 확인한다.
- 공개 DB·다운로드·일반 코칭 입력에서 기준 SQL·정답·생성 사건을 조회할 수 없어야 한다.
- v2 배포 후 v1 시도를 재개해 v1 데이터와 평가 자료를 사용하는지 확인한다.

검증 상태는 작성 중 → 검증 대기 → 출제 가능으로 관리한다. 새 버전은 다시 검증한다. 이 검증 목록은 아직 실행하지 않았다.
