## 목적과 확정 범위

[PRD-v2](../docs/PRD-v2.md) 3·5·6·7·13·15절과 [Spec 006](006-request-training-contracts.md)을 확장한다. 2026-10-04 사용자는 개발 중 작은 데이터로 테스트하고 이후 다른 데이터를 추가해 테스트하기 위해 접속 데이터부터 완성하기로 결정했다.

이번 구현은 `users/sessions`로 가능한 미재접속 계산, 지표·집계 오류 검토, 업무 요청 구체화, 관측 조건 비교, 집단·기간별 현상 조사와 분석 설계를 지원한다. 서로 다른 판단을 제공하는 능력 단위이며 고정 문제 목록이 아니다. 매출·전투·경제·튜토리얼 신규 표는 이번 구현에서 제외하고 별도 생성·검증 능력 추가 시 지원한다. 지원 범위는 서버 능력 목록에서 읽고 화면·AI 입력에 동일하게 제공한다.

초기 생성은 기존 소규모와 같은 기본 유저 200명, 허용 50~1,000명, 세션 상한 10,000행이다. 이는 테스트용 구현 기본값이며 사용자가 정한 제품 성능 목표가 아니다. 설정 가능하되 범위 초과 계획은 안내·조정하고 상한을 조용히 넘기지 않는다. 생성 데이터 행 수와 SQL 결과 보관 상한은 별개다. 현재 SQL 5초·1,000행/1MiB·미리보기 200행 제한은 유지하고 집계 조회로 분석 가능하게 설계한다.

## 공통 계약 확장: request-v2

기존 request-v1·access-plan-v1·패키지 v1 로더와 기록을 유지한다. 신규 계약을 별도 판별 모델로 추가하며 기존 모델의 Literal을 일괄 변경해 기존 훈련을 새 기준으로 재해석하지 않는다.

| 계약 | 신규 필드와 검증 |
| --- | --- |
| 요청 | 기존 request_id/message/difficulty/task_kind에 분야·목표·선택 SQL 수준·시간 조건·반복 의도·recommendation_id 추가. 명시값 충돌은 질문 |
| 해석 결과 | 주제·수준·목표·형식·수행 조건, 알려진/기본 제안/미확정 값의 출처, 지원 능력 ID, 추가 질문, 해석 규칙·모델 버전 |
| 계획 | plan_id/revision, 능력·생성기·검증·평가 규칙 버전, 목표·요구 판단, 공개/질문시/비공개 정보, 모호함 조건·이유, 데이터 조건, 제출물·필수 판단·근거·허용 한계·양의 배점 합100, 검증 계획, 의미적 서명 |
| 과제 공개 | 패키지/release/dataset/problem ID, 콘텐츠 버전·스키마·데이터 사전·공개 표, 공개 조건·완료 조건·배점·난이도 이유·선택 이유·시험 운영 여부. 비공개 필드는 응답 모델에서 제외 |
| 생성 능력 | capability_id, 허용 목표/상황/표/매개변수/연산, 각 규칙 버전, draft/approved/disabled, 승인 표본·검토자·시각 |

과제 유형은 기존 calculation/review/design을 읽으며 신규 v2에 investigation을 추가한다. 업무 요청 구체화와 분석 설계는 design의 목표로 구분한다. 공개 표 목록은 승인된 스키마의 검증된 manifest에서 가져온다. 자유 문자열 목록을 받아 임의 표를 허용하지 않는다.

패키지 콘텐츠 결합은 Spec 002의 package_id+release_version+dataset_id를 유지한다. 데이터·문제·평가 자료의 콘텐츠 버전은 동일 release_version이며, 평가 방식 버전 `evaluation_rules_version`·모델·프롬프트는 별도 필드다. 기존 Spec 006의 evaluation_version은 규칙 버전으로 읽는 어댑터를 명시한다. 새 문서가 기존 필드 의미를 바꾸지 않는다. seed·생성 사건·기준 결과·검증 원문은 비공개 저장이다. 규칙 버전 등 운영 메타데이터는 로그에 저장할 수 있으나 원인을 암시하는 변형 이름은 공개하지 않는다.

## 요청 해석과 계획 확정

1. 서버가 입력 형식·명시 선택값·지원 능력·호출 한도를 검사한다. SQL/행을 포함한 자료는 임시 입력으로 분리하며 영구 요청 원문으로 우회 저장하지 않는다.
2. AI는 제한된 능력 목록 안에서 요청을 구조화하고 과제 계획을 제안한다. 서버가 타입·능력·수준·공개 경계·완료 조건·생성 매개변수·배점을 검증한다. 기존 단어 규칙만으로 자유 요청 해석이 완료됐다고 보지 않는다.
3. 출제 필수 정보가 빠지거나 명시 선택이 충돌하면 needs_clarification으로 질문한다. 시간·형식 등 합리적인 기본값은 선택 이유와 함께 제안한다. 지원 밖 분야는 이유·대안을 반환하며 동의 없이 분야를 변경하지 않는다.
4. 추가 답변은 같은 요청의 새 revision으로 반영한다. 해석 대기 상태에서만 계획 수정 가능하며 확정 후 입력 변경은 새 요청이다. 공개 정보와 평가·생성 조건을 고정하고 그 계획으로 데이터 생성·검증한다.

LLM이 SQL·DDL·Python 코드를 생성해 서버에서 임의 실행하는 방식은 사용하지 않는다. 기준 계산과 데이터 생성은 등록된 코드·검증 함수에만 매핑한다. 공개 설명의 숫자·현상 주장은 검증 후 확인된 수치로 바인딩하고 결과와 다른 설명은 출제 실패로 처리한다.

## 다양성과 난이도

다양성 서명은 분야·목표·요구 판단·형식·데이터 상황 계열·모호함·필수 평가 판단이다. 최근 공개 완료 5개를 비교하고 숫자·seed·문구만 바뀌면 같은 사고 과제로 처리한다. 자동 비교는 후보 추정이며 의미적 차이는 사람 검증 표본으로 확인한다. 최근 모두 중복이면 다른 목표를 제안하고 명시 반복은 허용·기록한다. Spec 012와 같은 서명·규칙을 사용한다.

모호함 조건에는 목표, 대상/기간/지표, 비교 기준, 원인 후보 각각의 초기 공개·질문 제공·사용자 판단 상태를 둔다. 초급은 분석 조건을 명확히, 중급은 일부 조건·비교를 결정하게, 고급은 업무 목표에서 문제·지표·우선순위를 결정하게 한다. 필수 데이터·사전·수집 경계는 확인 가능해야 한다. 고급의 원인을 직접 노출하지 않고 불확실성과 가능한 대안을 허용한다. 난이도는 SQL 길이·데이터량·문장 축약으로 판정하지 않는다.

초기 데이터 상황 생성 코드는 기준 상황, 집단별 차이, 시기별 변화, 집단 구성 변화, 관측 기간 부족, 뚜렷한 차이 없음을 작은 공개 데이터로 재현하도록 구성한다. 실제 원인이 입증되지 않는 관측 상황에서는 후보·한계가 목표다. 모든 상황을 모든 유형에 무조건 조합하지 않고 승인된 목표·상황 조합만 등록한다. 최소 3개 서로 다른 판단 과제를 사람 검토한다.

## 생성·검증·권한

- 신규 요청은 확정한 seed·생성기 버전·조건에서 데이터를 만들고 파일 정렬·직렬화 규칙을 고정해 재현 가능한 해시를 계산한다. 요청 재전송은 새 패키지를 만들지 않는다.
- 스테이징 패키지와 전용 학습 스키마에 생성·적재하고 DB 생성 권한은 별도 출제 계정만 사용한다. 검증 전 learner 권한과 카탈로그 공개를 하지 않는다. PK/FK·가입/로그인/종료 시각·수집 경계·범주·행 상한을 검사한다.
- 기준 SQL은 실제 DB에서 실행하고 정확한 계산은 별도 Python 집계로 대조한다. count는 정확 일치, 비율은 0~100 범위의 percentage point로 절대 오차 1e-6 이하를 초기 허용값으로 둔다. 분모 0은 null이며 정답 0%로 만들지 않는다.
- D1~D7 기간 내 미재접속과 특정 D7 일자 리텐션은 각각의 정의·분자/분모·관측 경계로 분리한다. 사용자 요청이 둘을 혼용하면 확인 질문한다.
- 열린 과제는 공개 자료로 가능한 결론·불가능한 단정·허용 대안·확인 필요한 업무 사실을 검증한다. 공개 신호·세그먼트별 표본 존재, 필요한 비교 계산과 주장 수치를 실제 대조한다. 생성자가 아는 원인을 정답으로 강요하지 않는다.
- 분석 설계·검토 과제의 제공 보고서/오류 SQL도 실제 실행과 검산으로 수치·오류 존재를 확인한다. 제목·파일명·ID·사전·공개 본문이 비공개 사건을 노출하지 않는지 검사한다.
- SQL 정책은 훈련의 검증된 공개 표·스키마와 승인 연산만 허용하도록 변경한다. 다른 훈련 스키마·시스템 표·쓰기·외부 접근은 AST 검사와 DB 최소 권한으로 차단한다. 필요한 연산 추가 시 등록·회귀 검증을 거친다.

## 상태·재시도·공개 원자성

신규 상태는 accepted→planning→preparing_data→validating→ready, 질문 필요 시 needs_clarification, 종료 상태 failed/cancelled/interrupted다. v1 상태 읽기는 유지한다. ready에서만 attempt_id와 공개 패키지를 반환한다.

request_id는 동일 본문 멱등 키이며 내용 충돌 409다. clarification과 retry는 별도 action_id·expected_revision을 사용한다. failed/interrupted에서 동일 고정 계획·새 operation_id/parent_operation_id로 수동 재시도 가능, cancelled/ready에서는 재시도 불가다. 자동 재시도는 기존대로 0회, 요청별 생성 시도 최대 2회(최초+수동1회)를 초기 설정으로 둔다. 두 번 실패 시 원인 안내와 새 요청을 제안한다. 재시도는 같은 계획·seed를 사용하며 계획/데이터 변경은 새 요청이다.

초기 요청당 설계 AI 최대 3회(추가 질문 해석 포함), AI 호출 90초, 생성/적재·검증 각 작업 60초, 준비 작업 1회 전체 300초를 설정값으로 둔다. 사용자 추가 답변 대기는 전체 준비 작업 시간에서 제외한다. 설계 호출도 요청 이벤트에 기록하고 출제 후 훈련의 AI 최대 30회 예산에 포함한다. 준비 동시 작업 1개·AI 직렬화를 유지한다. 슬롯이 없으면 고정 busy 응답으로 입력을 보존하고 무한 큐를 만들지 않는다. 취소해도 발생한 AI 사용량을 없던 것으로 처리하지 않는다.

파일·학습 DB·기록 DB를 하나의 DB 트랜잭션으로 묶을 수 있다고 가정하지 않는다. 스테이징→검증 완료 표식→읽기 전용 권한·카탈로그 등록→기록 DB의 요청 잠금/취소 재확인→attempt·고정 계획·ready 기록 순으로 진행한다. 공개 API는 ready와 연결된 검증된 패키지만 반환한다. 기존 패키지 목록도 검증 성공·사용 가능 범위를 검사한다.

각 단계는 작업·패키지 ID와 완료 표식을 남기고 재시작/실패 때 중간 산출물을 대조한다. 취소/실패 시 공개 목록에서 제외하고 learner 권한을 회수한다. attempt나 다른 훈련이 참조하는 자료는 정리하지 않는다. 미참조 실패 스테이징은 24시간 이후 작업 ID·경로·스키마 검사를 거쳐 정리한다. seed·조건·실패 코드 메타데이터는 기록 보관 정책에 따르며 행·파일은 운영 로그에 넣지 않는다. 공개된 콘텐츠는 수정하지 않고 변경은 새 release다.

## API·모듈·순서

기존 요청 생성/조회/취소 경로를 유지하고 `/api/training/capabilities` GET, `/api/training/requests/{request_id}/clarify` POST, `/retry` POST를 추가 설계한다. 응답은 상태·revision·진행 단계·고정 오류·재시도 가능 여부·ready일 때 공개 과제다. 신규 error_code는 unsupported_scope, clarification_required, plan_invalid, generation_limit, generation_failed, validation_failed, interrupted, busy, retry_limit를 포함하며 원문 DB/AI 예외를 반환하지 않는다.

권장 신규 모듈은 `task_planner.py`, `generators/access.py`, `package_validation.py`, `capabilities.py`다. 계약과 저장 migration→능력 등록→요청 계획→생성/검증→SQL 정책→공개 API 순으로 연결한다. 기존 app.py·training.py·store.py·api_provider.py 변경은 같은 파일을 동시에 수정하지 않고 통합 순서를 정한다.

## 검증과 완료

자동 계약·생성 재현·관계·경계·해시·비공개 필드 테스트, 실제 PostgreSQL 집계/독립 검산, 타 스키마 차단, 실패/취소 경쟁·재시작·중복/수동 재시도를 검증한다. 현재 모델의 자유 표현 요청과 실제 생성 결과를 연결하고 사람 검토에서 다양성·난이도·분석 가능성을 확인한다. 신규 생성·평가 규칙은 검토자·표본·규칙 버전·판정 시각으로 사용 가능 등록한 후 자동 출제한다. 화면 흐름은 Spec 011·013에 따라 검증하고 결과를 tests에 기록한다.
