## 요구사항

- 사용자의 목적: Git 반영과 운영 반영이 따로 움직이는 문제를 방지한다. 사용자는 보통 main 브랜치를 운영 기준으로 사용하는 점을 근거로 제시했다.
- 사용자 선택: main 병합 후 배포 명령을 실행한다. 이 PC에 GitHub 실행기를 등록하지 않는다.
- 기능 브랜치 수정 → 테스트 → PR → main 병합 → 해당 커밋 배포 → 실제 동작 확인을 따른다.
- main 이력에 포함되고 지정된 CI 검사가 모두 성공한 커밋만 배포한다. 로컬 작업 파일을 운영 빌드 소스로 사용하지 않는다.
- 공개 GitHub Actions는 테스트와 이미지 확인을 수행한다. 운영 비밀과 운영 DB는 제공하지 않는다.
- 배포는 기존 bot 서비스의 환경·비밀 마운트·영구 볼륨·네트워크를 재사용한다. 실행 중 작업·동시 배포·빌드 중 운영 변경을 감지하면 중단한다.
- 이미지의 커밋·지문을 실제 실행 파일과 대조한다. 배포 검증 실패 시 이전 봇 이미지·구성을 복구하며 DB·볼륨은 보존한다.
- GitHub main 상태, 배포 성공 상태, 실제 기능 검증 상태를 별도로 기록한다.

## 검증

자동 검증은 main 커밋 제한, CI 결과의 최신 성공 요구, 파일 수정/추가/삭제·경로 이탈 차단, 기존 볼륨·환경 유지, 동시 배포 거절, 재시작 상태 거절을 포함한다. 운영 연결 성공만으로 포럼 기능을 완료 처리하지 않는다.
