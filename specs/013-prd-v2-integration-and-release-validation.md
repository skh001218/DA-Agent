## 목적과 완료 구분

[PRD-v2](../docs/PRD-v2.md) 12절의 제품 완료 조건과 11개 개발 작업을 대조한다. Spec 작성, 자동 테스트 통과, AI 호출 성공, 모델 점수 상승은 각각 구현·제품 품질·학습 효과 완료를 대신하지 않는다. Spec 006의 100%와 Spec 007의 80%는 기존 범위의 기록으로 보존한다.

## 환경과 증거

각 실행에 코드 revision, 환경(OS·CPU 아키텍처·Docker·DB), 콘텐츠·생성기·검증·난이도·평가·프롬프트·모델 버전, 실행 일시, 표본 ID, 실제/모의 여부를 남긴다. API 키·사용자 미저장 SQL·결과·대화 원문은 검증 로그에 남기지 않는다. 명시적으로 저장한 검증 표본만 별도 관리한다.

실제 DB 테스트는 임시 기록 스키마와 검증용 패키지·학습 스키마를 사용한다. 실행 전 대상 식별자를 검사하고 사용자의 기록·공유 패키지·DB 볼륨을 초기화하지 않는다. 같은 훈련의 취소·재시작·삭제는 순차 실행한다. 종료 시 테스트가 생성한 대상만 정리한다.

## 품질 승인

Spec 010의 고정 표본을 현재 모델로 각 3회 실행하고 사람이 판정한다. 유효 형식·핵심 판정 유지, 총점 범위 10점 이하를 확인한다. 허위 수치 승인·오진·해설 전 정답 노출·검증 실패 과제 공개·미저장 근거 영구 저장은 검증 표본에서 허용하지 않는다. 실패는 개선 뒤 같은 표본과 관련 회귀 표본을 다시 확인한다. 다양성·난이도·코칭은 기계 통계와 별개로 사람 판정·학습자 응답을 수집한다.

새 생성·평가 규칙의 사용 가능 승인은 대상 규칙 버전·검토자·검토 표본·판정 시각·결과를 기록한다. 승인된 범위의 개별 과제는 자동 수치·구조 검증 뒤 출제한다. 모든 문제마다 승인을 요구하지 않는다. 새 규칙 승인과 실제 제품 출시 판정은 별개다.

## 이식성과 파일럿

다른 PC에서는 동일 코드·패키지·버전으로 Docker 실행부터 요청·실제 SQL·리뷰·재개까지 확인한다. ARM은 환경과 결과를 별도 기록한다. ARM 장비가 없으면 확인 대기로 남기고 ARM 지원 확인을 주장하지 않는다.

초기 파일럿은 기본 SQL 사용 가능한 실제 학습자 5명이다. 참가자별 요청·과제·수준·개입·중단 지점·다음 수정 행동·최초/수정 보고서·형식 반복 느낌·코칭 도움/방해와 이유를 명시적으로 기록한다. 최초 제출에서 핵심 조건 보완이 필요했는지도 사람이 판정한다.

초기 목표는 4명 이상 직접 개입 없이 리뷰까지 완료하고 수정 행동을 설명, 전체 5명 중 과반(3명 이상)이 놓친 핵심 조건을 수정 제출에 반영하는 것이다. 보완 필요자가 3명보다 적으면 원래 목표 판정의 한계를 표시하고 보완 대상 분모의 수정 효과를 함께 보고한다. 임의로 성공 처리하거나 참가자를 실패로 만들지 않는다. 표본·목표 조정은 사용자 결정과 근거를 기록한다. 점수 상승만으로 학습 효과를 확정하지 않는다.

## 실행 순서와 최종 기록

1. 계약·기록 마이그레이션·기존 훈련 호환을 검증한다.
2. 요청→고정 계획→신규 데이터→실제 검증→공개를 확인한다.
3. 공개 과제→SQL/설계→임시·저장 근거→누적 코칭을 연결한다.
4. 제출→리뷰→수정·재개와 이벤트·사용량을 확인한다.
5. 실제 이력 추천·최근 5개 비교·8종 지표를 대조한다.
6. 화면·장애·사람 품질·다른 PC·파일럿을 완료한다.

tests에 실행 결과·사람 판정·미확인 항목을 남기고 각 Spec의 작업 상태·분자/분모·갱신일·남은 작업·차단 사유를 갱신한다. PRD의 11개 완료 조건도 각각 근거를 대조해 갱신한다. 외부 환경이나 참가자 부재는 차단 이유로 기록하고 검증 대기 항목을 완료로 올리지 않는다.
