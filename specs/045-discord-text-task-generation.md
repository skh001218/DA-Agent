# Spec 045 — Discord 텍스트 요청 기반 문제 생성

`/training`의 고정 `topic` 선택을 필수 `text` 요청으로 바꾼다. 사용자가 연습하고 싶은 내용과 난이도를 입력하면 기존 요청 기반 출제 기능으로 문제·합성 데이터·검산 기준을 준비하고, 검증된 결과를 Discord 훈련에 연결한다.

## 구현 진행도

- 진행도: 6/7개 완료 (85.71%)
- 마지막 갱신일: 2026-10-07
- 남은 작업: 실제 모델 출제의 두 요청·세 난이도 및 Discord 분석 전체 흐름 검증, 사람 품질 검토
- 차단 사유: 필수 practice 누락·고급의 역량 이름만 있는 계약·공유 토큰 예산·수정 입력 누적 문제는 수정하고 회귀 검사·배포했다. 실제 모델의 설계에는 표본/집계 조건 불충족과 적합성 검토 거절이 남아 있다. 최신 실행 결과와 원인은 [이번 검증 보고](../tests/reports/verification-spec035-036-completion-2026-10-07.md)에 기록한다. 완성된 실제 모델 과제의 분석 전체 흐름을 확인하기 전까지 6/7을 유지한다.
- 추가 점검(2026-10-06): 두 요청×세 난이도 모두 첫 설계 호출에서 실패(HTTP500 2건·429 4건), 별도 중급도429였다. 응답은 모델별 분당 입력 토큰16000 제한을 명시했다. 구조 검사에서 같은 중급 집계에 고급 역량 이름을 붙인 반례가 통과하고 text 분석의 practice 누락이 accepted로 저장됐다. 실제 난이도 차이는 미확인이고 진행도5/7은 유지한다. [추가 점검 보고](../tests/reports/verification-spec035-036-levels-2026-10-06.md).

## 목적과 현재 구현

사용자는 기존 기능을 이용해 현재 `topic`에 있는 내용으로만 출제하는 제한을 바꾸고, `text` 요청으로 문제를 생성하도록 요청했다. 입력은 자유롭게 받되 실제 생성·조회·검산 기능으로 지원할 수 있는 과제만 공개한다.

현재 `discord_bot.py`는 topic choices에 tutorial 하나를 등록한다. `DiscordTrainingService.start`는 tutorial 외 주제를 거부하고 `representative_task`로 고정 문제를 선택한다. 웹의 `RequestV2`는 message·difficulty·data_mode를 받고, `TaskGeneration.prepare_adaptive`는 사례 검색·선정, 설계·수정, 적합성 검토와 데이터 준비를 수행한다. 이 흐름을 공통 서비스 또는 어댑터로 재사용한다.

## main SQL 연습 통합

PR #27 통합 당시 SQL 연습 문서와 번호가 겹쳐 이 문서를 Spec035에서 Spec036으로 변경했다. 2026-10-07 전체 번호 정리 후 SQL 연습은 Spec044, 텍스트 출제는 Spec045이다. 과거 검증 artifacts의 spec035 경로는 실행 당시 기록으로 보존한다. `/training`의 필수 practice 선택, `/sqlrun`, 실행 ID를 지정하는 `/submit`, SQL 코드 블록 답장과 기존 SQL 검산을 유지한다. 분석 연습의 text는 Gemma 출제로 연결한다. SQL 연습은 현재 튜토리얼 신규 가입자 3단계 완료율만 지원하며 다른 text 또는 생성 분석의 SQL 연결은 명시적으로 거부한다. 기존 튜토리얼 완료 분석의 SQL 연결은 유지한다.

## 명령 입력 계약

```text
/training practice:analysis text:게임 내 재화가 급격히 늘어난 원인을 분석하는 문제를 만들어줘 difficulty:intermediate
/training practice:analysis text:튜토리얼 완료율 하락을 분석하고 싶어 difficulty:beginner help_level:guided
```

예시는 요청 형식이며 해당 주제의 생성 성공을 보장하지 않는다.

- `text`: 필수 문자열. 앞뒤 공백 제거 후 1~4000자. 공백뿐인 입력은 모델 호출 전에 거부한다. 보고서나 SQL을 출제 요청에 붙이지 않도록 기존 임시 자료 검사를 재사용한다.
- `difficulty`: 초급·중급·고급 선택과 기본 중급을 유지한다. 선택한 난이도를 생성·평가 계약까지 보존한다. 요청문과 선택 난이도가 충돌하면 추가 질문으로 확인하고 임의 변경하지 않는다.
- `help_level`: 기존 guided·independent와 기본값을 유지한다. 도움 정도는 난이도나 출제 기준을 바꾸지 않는다.
- 공개 명령의 `topic`과 tutorial 기본값을 제거한다. `text` 누락을 tutorial 출제로 대체하지 않는다. 내부 topic은 생성 결과의 분류 정보로만 사용할 수 있다.
- `/tip training`, 첫 안내, 오류 예시, 실행 안내를 text 형식으로 갱신한다. 서버 명령 동기화 전후의 사용 가능 형식을 구분한다.

고정 접속 주제로 제한된 `task_planner` 경로를 자유 주제 생성기로 사용하지 않는다. `data_mode=adaptive`를 사용하고 필요한 store·catalog·provider·작업 실행을 Discord 환경에 연결한다. 웹 기록·DB·전역 최근 과제 목록을 그대로 공유하지 않으며 최근 과제 참고는 요청 소유자 범위로 제한한다.

사용자 요청에 따라 Discord는 Gemma API만 사용한다. DISCORD_MODEL(기본 gemma-4-26b-a4b-it)로 text·difficulty에서 가상 업무 문제를 직접 설계하고 검토한다. 실제 사례 검색·선정은 생략하며 별도 Gemini 검색 모델을 요구하거나 호출하지 않는다. sources는 빈 목록, searched_at은 null로 저장하고 실제 검색 사례로 표시하지 않는다. Gemma의 JSON 응답 처리와 설계·검토 호출을 검사하며 실패하면 요청을 보존한다. 출처를 만들거나 다른 모델·주제·고정 문제로 자동 대체하지 않는다. 웹의 검색 기반 출제는 기존 계약을 유지한다.

## 생성 상태와 복구

1. Interaction을 먼저 지연 응답하고 서버·소유권·입력·부모 채널 권한을 검사한다. 모델·DB 작업은 이벤트 루프에서 분리한다.
2. 원문·난이도·도움 수준과 owner_user_id·guild_id·parent_channel_id·event_id·request_id를 Discord 저장소에 기록한다. 같은 이벤트의 같은 입력은 상태를 재사용하며 새 호출·데이터·훈련을 만들지 않는다. 같은 ID의 다른 입력은 충돌로 처리한다.
3. text를 message로 전달해 기존 adaptive 생성 흐름을 실행한다. Gemma 설계·검토·수정 호출을 모두 Discord 일일 한도에 포함한다. 실제 사례 검색·선정은 호출하지 않는다.
4. 확인이 필요하면 needs_clarification으로 저장하고 원문·질문을 보존한다. 소유자의 `/answer text:...` 또는 기존 질문 답장을 요청 ID·수정 번호에 연결한다. 공간이 필요하면 기존 비공개 스레드를 요청용으로 사용하되 준비 완료된 분석 세션으로 표시하지 않는다.
5. 검증을 통과하면 공개 문제·사전·조건·루브릭을 고정하고 데이터 접근과 분석 세션을 연결한다. 요청용 스레드가 있으면 재사용하며 제목·안내는 생성 문제에서 만든다.
6. 이후 조회·질문·도움·보고·제출·재개는 해당 생성 과제와 저장 근거를 사용한다.

accepted·planning·needs_clarification·preparing_data·validating·ready·failed·cancelled·interrupted를 의미에 맞게 안내한다. 준비 중에는 analysis 상태를 부여하지 않는다. Interaction 만료 후에도 저장 상태와 소유자 전용 스레드에서 결과를 확인할 수 있어야 한다.

준비 중 `/end`는 취소, 준비 전 `/resume`은 요청 상태·확인 질문 복원으로 처리한다. 실패·중단 요청의 재개에는 명시적인 재시도 버튼을 제공한다. 버튼은 요청 ID·수정 번호를 검사하고 기존 재시도 기능을 호출한다. 재개만으로 모델을 호출하지 않는다. 고정 계획이 없으면 새 설계가 필요함을 안내한다. 취소 후 늦게 도착한 응답은 과제를 공개하지 않는다.

요청 수정 번호·상태·실패 이력·버전·seed·plan_id·package_id·session_id·스레드·호출 수·사용량을 연결한다. 비공개 설계·정답·기준 수치는 공개 문제·일반 로그와 분리한다.

| 중급 | 업무 문제·자료에서 비교 대상·조건을 선택하고 불확실성·다음 행동 설명 | 요구 비교 차원·필터·측정과 데이터·검산 계약 대응 |
| 고급 | 업무 목표에서 질문·지표·우선순위를 정의하고 대안 설명·교란·한계 검토 | 단순 집계 추가로 통과하지 않으며 필수 판단의 관측 근거 존재 |

[난이도 감사](../tests/reports/verification-difficulty-audit-2026-10-06.md)의 실패를 인수 기준에 반영한다. ratio 분자 조건과 질문의 analysis 지표 연결을 검사한다. 편차·분산 또는 조건부 비교를 요구하려면 실제 지원 연산과 검산 계약이 있어야 한다. 지원하지 않으면 원래 목표·난이도를 유지할 수 있는지 검토하고 불가능하면 한계를 안내한다.

무작위 자료에 효과·원인이 있다고 전제하지 않는다. 관계 미확인·판단 유보·추가 관측을 타당한 결론으로 허용한다. 원자료에 없는 체감·조치 효과는 추가 검증 제안으로 다룬다. Discord 과제는 가상 업무 조건·합성 자료임을 안내하고 실제 회사의 확인된 사실이나 검색 출처로 제시하지 않는다.

## 데이터 조회와 평가 계약

- 자료는 Discord 전용 환경에 준비하고 각 과제의 공개 표·컬럼·관계·기간·단위를 조회 허용 범위로 고정한다. 다른 사용자·과제·웹 자료 접근과 쓰기를 차단한다.
- 자연어 조회는 생성 데이터 사전을 사용한다. tutorial 전용 표·지표·SQL·검산기를 강제 적용하지 않는다. SQL·결과·저장 근거를 현재 세션과 실행 ID에 연결한다.
- 추가 질문은 고정 업무 조건에서 답하고 없는 사실을 만들지 않는다. 코칭·보고·후속 질문·평가는 공개 요구사항과 저장 근거를 사용한다.
- 공개 정의·완료 조건·평가 항목·배점·인정할 한계를 출제 전에 고정한다. 생성 결과와 Discord 교육 계약 사이의 변환을 검사하고 평가 중 기준을 추가하지 않는다.
- 지표·검산기는 Spec042 등록 계약을 사용한다. 지원 밖 지표는 미검산으로 남기며 학습자 오류로 판정하지 않는다. 점수 프로필에는 실제 평가 입력의 공개 정의 전체·난이도·자료·모델·평가 코드가 반영되어야 한다.
- 유형 검증 미등록·미통과·불일치이면 확정 총점을 보류하고 분석 피드백·사유를 제공한다. 생성 검증 통과를 평가 품질 승인으로 간주하지 않는다. Spec042의 프로필 지문 누락도 새 과제 승인 재사용 전에 보완한다.

## 실패 처리와 기존 기록 호환

지원 밖 요청·난이도 충돌·설계 오류·자료 검증 실패·Gemma 연결 불가·API 제한/실패·DB/전송 실패를 구별한다. 원인 범주와 다음 행동을 안내하고 운영 기록에 검증 이력을 남긴다. 정상 실패를 일반 DB 오류로 바꾸거나 tutorial 문제를 대신 제공하지 않는다.

호출 상한은 기존 adaptive의 `PLANNING_LIMIT`을 재사용한다. 현재 코드 값은 8회이며 설계·수정·적합성 검토를 포함한다. Discord 일일 제한도 적용하며 예산 부족 시 중단한다. API 실패에 무제한 자동 재시도를 추가하지 않는다. 실패·취소한 자료의 접근을 회수하고 기존 사용자 기록을 보존한다.

기존 tutorial 세션은 당시 문제·자료·루브릭·평가 버전으로 재개·수정·재제출한다. 신규 계약 버전으로 생성 요청을 구분하고 기존 세션을 재생성하지 않는다. 준비 성공 후 전송만 실패하면 저장된 결과를 재사용해 중복 생성 없이 전달을 복구한다.

## 검증과 완료 기준

자동 검증은 다음을 포함한다.

- SDK text 필수 등록·topic choices 제거·난이도/도움 기본값·도움말, 공백·누락·길이·난이도 충돌.
- 원문·난이도 전달, 서로 다른 주제의 성공·지원 밖 거부, Gemma 연결 불가·추가 질문·실패·취소·재시도·재시작·중복 이벤트의 상태·호출 수.
- 실제 PostgreSQL 생성 자료·관계·기간·공개 조회·접근 차단·검산, 질문과 지표 연결·난이도 조건 누락.
- 새 과제의 질문·코칭·보고·제출·보류·재개와 기존 tutorial 기록 회귀. 생성 오류를 학습자 감점으로 처리하지 않는지 확인.

실제 모델·Discord 화면에서 서로 다른 두 요청과 동일 요청의 초급·중급·고급을 확인한다. text 입력 → 생성 상태 → 문제·사전 → 자연어 조회·SQL 열람 → 보고·후속 답변·제출 → 재개를 수행한다. 확인 질문·실패·취소·전송 복구도 확인한다. 주제 다양성과 난이도 적합성을 결과 내용으로 검토하며 API 성공만으로 완료하지 않는다.

명령 재동기화·실행 이미지 코드 버전을 기록한다. 별도 worktree의 실행 봇에 문서 작성만으로 반영됐다고 표시하지 않는다. 결과는 tests/reports/에 남기고 환경상 미확인 항목은 검증 대기 또는 차단으로 유지한다.

## API 오류 재테스트 결과 (2026-10-06)

사용자 요청에 따라 동일한 Gemma 모델·중급 요청을 실제 API로 다시 실행했다. 첫 응답의 데이터 그룹 행 수가 허용치 500개를 넘어서 수정 요청을 보냈고, 두 번째 응답에서 `provider_invalid_json`이 재현됐다. 2회 모두 Gemma를 사용했으며 모델 전환은 없었다. 출제·검산 완료 조건은 미충족이고 진행도는 5/7개 완료(71.43%)를 유지한다. [검증 보고의 API 실패 재테스트](../tests/reports/verification-spec036-2026-10-06.md)와 호출 기록에 상세 결과를 남겼다. 남은 작업은 수정 응답의 JSON 오류 진단·수정과 실제 출제 재검증, 운영 반영·Discord 전체 흐름·난이도별 품질 검증이다.

## 원문 진단으로 확인한 실패 원인 (2026-10-06)

동일 조건 실제 호출의 수정 응답은 유효한 JSON 배열 `[{...}]`이었다. 단일 문제 객체 `{...}` 계약을 검사하는 코드가 배열을 거부했다. API는 HTTP200/STOP이며, JSON 구문 파싱은 성공했다. 현재 Gemma 요청은 responseJsonSchema를 제거하고 application/json MIME만 지정하므로 최상위 객체 형태를 강제하지 못한다. 실패 원문은 서버 전용 `.local`에 보관하고 공개 자료에는 자료형·길이·오류 정보만 기록했다. [진단 보고](../tests/reports/verification-spec036-2026-10-06.md)에 실행 근거·테스트 결과를 추가했다. 원인 확인과 진단 보완은 완료했으나 출제 계약 불일치 수정·실제 출제 검산·운영 Discord 검증이 남아 진행도 5/7(71.43%)는 유지한다.

## 2026-10-07 추가 구현·검증

- text의 practice 누락·지원 밖 값은 생성 전 거절하고 자료·기록·모델 호출을 만들지 않는다.
- 고급 confounding은 공개 근거 열과 실행 가능한 비교 지표에 연결한 judgment 계약을 요구한다. 조건부 비교는 통제 열을 포함한 2차원 집계, 식별 불가능 경로는 관측 근거·판단 유보·추가 관측 조건을 명시한다. 이름만 고급으로 붙인 반례는 거절된다. 의미 적합성과 사람 품질 검토는 별도로 유지한다.
- 비율의 분자는 분모 모집단의 부분집합이라는 계약을 설계 프롬프트에 명시했다. 튜토리얼 중도 이탈과 서비스 잔류 계산을 구분하고, 단순 업무 배경 언급을 계산 요구로 오인하지 않도록 보완했다.
- 수정 요청에는 최신 초안과 오류만 전송한다. 공유 모델/키 범위의 토큰 예산을 영구 SQLite에 저장하고 countTokens를 우선 사용하며, 실제 prompt 사용량·429 대기 시간을 반영한다. 실패 안내에는 KST 재시도 시각을 제공한다. 키나 프롬프트를 예산 DB에 저장하지 않는다.
- 전체 608 통과/79 생략, 격리 DB 관련 122 통과. 모델 실행과 사람 검토는 이 수치로 완료 처리하지 않는다.


## 출제 수정 요청 개선 통합 (2026-10-07)

최신 실패 초안과 현재 오류만 전달하고, 관계·행 단위에 맞는 수정 지시 및 전송 직전 사용량 차감을 추가했다. 기존 countTokens, pending 예약, SQL·고급 judgment 검사와 통합한다. 로컬 회귀 완료와 실제 운영 확인은 구분하며, 후속 검증은 [Spec046](046-discord-bounded-generation-repair.md)에 기록한다.
